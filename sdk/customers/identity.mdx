title: "Identity Verification"
description: "On-chain KYC verification, claims, status queries, and transfer compliance checks"

The `identity` sub-module works against the identity register your instance is bound to. Every write (`verify`, `verifyFromManifest`, `batchVerify`, `revoke`, `addClaimsFromProof`, `attestProofs`, `addClaim`, `revokeClaim`) is signed by a registered issuer wallet of your instance. Trusset builds the transaction. Your wallet signs it.

Every prepared write names the register in `registerKind`:

| `registerKind` | Register | Where it writes |
|---|---|---|
| `INSTANCE` | The [instance ID register](#instance-id-registers), the default. One `InstanceRegister` per instance, owned by your wallets, reading attestations from the shared `IdentityHub` | `attest`, `attestBatch` and `revoke` on the IdentityHub |
| `TREX` | Your own [ERC-3643 register](#own-erc-3643-registers) | The register's ONCHAINID and registration calls, in phases |
| `TRUSSET` | Your own register with the Trusset IdentityRegistry interface | One transaction on that register |

An instance on the default setting that has not created its register yet gets `409 INSTANCE_REGISTER_REQUIRED` from every identity call. Create the register in the instance settings of the issuer app.

## Sign, prepare, or confirm a write

Each write method takes the same three shapes. Without options it returns the unsigned transaction. With `{ signer }` it signs, broadcasts, waits for the transaction to mine and confirms it with Trusset. With `{ txHash }` it only confirms a transaction you broadcast yourself.

<Warning>
  Only a confirmed transaction updates the customer record, and the backend confirms nothing until it has read the mined receipt. If the confirm call fails after the transaction mined, the identity is on chain but the record is not. With `{ signer }` the SDK then throws a `ConfirmationError` whose `txHash` is the hash to confirm and whose `transactions` lists every hash it sent: confirm again with `{ txHash: err.txHash }` instead of repeating the write. When you broadcast yourself, confirm again with `{ txHash }`.
</Warning>

The signer must be a registered issuer wallet that the register accepts: a trusted attester on an instance ID register, or the role holder on your own register. Any ethers v5 `Signer` works, from a self-custody wallet or a regulated custodian, with no preference between them. The SDK never asks for, stores or sends a private key.

```typescript
import { Wallet, providers } from 'ethers'

const provider = new providers.JsonRpcProvider(process.env.RPC_URL)
const signer = new Wallet(process.env.ISSUER_WALLET_KEY!, provider)

const result = await trusset.customers.identity.verify({
  walletAddress: '0x1234567890abcdef1234567890abcdef12345678',
  country: 'DEU',
  kycHash: '0x591aa0f6c2a3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d',
}, { signer })
```

To sign in your own infrastructure instead, call the method without options. On an instance ID register the result has `action: 'SIGN_TRANSACTION'`, a `transaction` with `to` and `data`, and the `chainId` of your instance. Broadcast it, wait for it to mine, then call the same method again with the hash. An instance bound to its own ERC-3643 register answers with a phased plan instead, so check `action` before you broadcast; see [Own ERC-3643 registers](#own-erc-3643-registers).

```typescript
const prepared = await trusset.customers.identity.verify({
  walletAddress: '0x1234567890abcdef1234567890abcdef12345678',
  country: 'DEU',
  kycHash: '0x591aa0f6c2a3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d',
})

if (prepared.action !== 'SIGN_TRANSACTION') {
  throw new Error(`This instance writes to its own register: sign the ${prepared.phase} phase first`)
}

const tx = await signer.sendTransaction(prepared.transaction)
await tx.wait(1)

const confirmed = await trusset.customers.identity.verify({
  walletAddress: '0x1234567890abcdef1234567890abcdef12345678',
  country: 'DEU',
  kycHash: prepared.kycHash,
}, { txHash: tx.hash })
```

Confirm with the values the prepared response returned, here `kycHash`. The backend checks the mined transaction against them. A transaction the backend cannot read yet answers `TX_NOT_FOUND`; wait for it to mine and confirm again.

The SDK broadcasts the calldata the API returned without decoding it. If your compliance process requires checking calldata before signing, decode `transaction.to` and `transaction.data` in your own code before you broadcast.

With a signer, a write waits for the transaction to mine, so expect tens of seconds. The SDK raises its own request timeout for these calls to 60 seconds, and to 180 seconds for proof claims, because the backend verifies the proof bundle on both legs.

Before anything is built, the SDK checks that the signer is connected to your instance's network and refuses with a `ValidationError` otherwise; it never switches networks. It estimates each transaction and sends it with 50% gas headroom, so an identity update that lands a block after the previous write does not run out of gas. A transaction that reverts raises a `ConfirmationError` with code `TRANSACTION_FAILED`. Every signed result carries `transactions`, one entry per transaction sent, with its `functionName` and `txHash`.

## Verify an identity

Registers an address as KYC-verified on your instance's register. The address can then take part in compliant token transfers.

Pass `kycHash` with the root hash from the [KYC proof tool](/sdk/customers/kyc-proofs). It is stored on chain verbatim and later checked when adding proof-backed claims. If the address already has an active on-chain identity, it is updated instead of failing, and `result.operation` tells you which happened.

```typescript
const result = await trusset.customers.identity.verify({
  walletAddress: '0x1234567890abcdef1234567890abcdef12345678',
  country: 'DEU',
  investorType: 'RETAIL',
  kycHash: '0x591aa0f6c2a3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d',
  softExpiryDays: 365,
  hardExpiryDays: 730,
}, { signer })
```

The result carries `txHash`, `gasUsed`, the `kycHash` now stored on chain, and `operation`, which is `verify` for a new identity and `update` for an existing one.

  </ParamField>
  <ParamField body="country" type="string" required>

  </ParamField>
  <ParamField body="investorType" type="string" default="RETAIL">

  </ParamField>

  </ParamField>
  <ParamField body="hardExpiryDays" type="number">

  </ParamField>
  <ParamField body="kycHash" type="string">

  </ParamField>
  <ParamField body="kycData" type="object">

### Verify from a proof manifest

`verifyFromManifest` reads the wallet address, root hash and expiry days straight from the bundle's `manifest.json`. A 3.1.0 manifest carries no country or investor type, so pass them in the second argument, where overrides win over the manifest. The signing options go third.

```typescript
const result = await trusset.customers.identity.verifyFromManifest(manifest, {
  country: 'DEU',
  investorType: 'PROFESSIONAL',
  header,
  headerSignature: readFileSync(`${bundle}/header.sig`),
  verifier,
}, { signer })
```

`header` (`header.json` parsed), `headerSignature` (the bytes of `header.sig`) and `verifier` are optional here and work as on [claims from a proof](#claims-from-a-proof): the SDK checks that the header belongs to the manifest and names the same wallet, runs the verifier before any request, and sends the header with the request. The manifest itself is not sent by this call.

The root hash itself cannot be overridden. It must match the manifest, otherwise proof-backed claims fail later with `HASH_MISMATCH`.

## Batch verify

Verify up to 500 addresses in a single on-chain transaction. Give each entry its own `kycHash`: the rows of the proof tool's batch CSV map directly onto entries.

Entries that fail validation are left out of the transaction and reported one by one in `rejected`, each with its `index` in the array you sent, the `walletAddress`, a `code` and a `message`. The rest go on chain. On an instance ID register every entry is attested, replacing the signing attester's earlier attestation of that wallet. On a register with the Trusset IdentityRegistry interface, addresses that are already actively verified are skipped and keep their existing identity, and revoked identities are verified again.

```typescript
const result = await trusset.customers.identity.batchVerify([
  { walletAddress: '0xaaaa000000000000000000000000000000000001', country: 'DEU', kycHash: '0x591aa0f6c2a3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d' },
  { walletAddress: '0xbbbb000000000000000000000000000000000002', country: 'FRA', investorType: 'PROFESSIONAL', kycHash: '0x65c5e1f0a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f708192a3b4c5d' },
], { signer })
```

The result counts `submitted`, `accepted`, `totalEntries` and `rejectedCount`, and carries `rejected`, `onChainSkipped`, `txHash` and `gasUsed`. With `{ signer }`, `submitted` and `rejected` cover every entry you sent: an entry refused while the transaction was prepared stays in `rejected` with its index in your array. Use single `verify` calls when you need per-address update semantics.

When you confirm a batch yourself with `{ txHash }`, pass the `entries` from the prepared response, not the ones you submitted. Rejected entries never reached the transaction, and the confirm is checked against the accepted ones.

## Instance ID registers

<Note>
  Available from `@trusset/sdk` 0.9.0.
</Note>

An instance ID register keeps no personal data on chain. Each issuer wallet writes its own attestation about a customer wallet to the IdentityHub: the root hash, the investor class (`1` retail, `2` professional, `3` eligible counterparty), the expiries and a set of predicates. Your InstanceRegister lists the attesters it trusts and answers `isVerified` for your tokens and markets. The country never goes on chain: `verify` turns it into predicates.

| Method | Contract call |
|---|---|
| `verify`, `verifyFromManifest` | `attest` on the IdentityHub |
| `batchVerify` | `attestBatch` on the IdentityHub |
| `addClaim`, `revokeClaim`, `addClaimsFromProof` | `attest` again, with the claim's predicate set or cleared |
| `revoke` | `revoke` on the IdentityHub |

A prepared write carries `contractFunction`, the contract call, beside `functionName`, the identity operation such as `verifyIdentity`. It also carries `predicates`, the mask it attests. A claim change names the `attester` of the record it edits. Sign it with that wallet: any other trusted wallet writes a second attestation under its own address instead of changing the first.

The signer must be a trusted attester of your register. The build refuses with `ATTESTER_MISSING` when none of your instance's wallets is one, and the confirm with `UNTRUSTED_ATTESTER` when the transaction came from a wallet the register does not trust. A `verify` confirm also checks that the register now reports the wallet as verified.

Freezing a wallet for the whole instance is a call on the InstanceRegister (`freeze`, `unfreeze`), signed by a compliance officer. There is no API key route for it, so freeze in the issuer app.

### Predicates

A predicate is a yes or no fact, one bit of a 128-bit mask. The API sends masks as decimal strings, such as `'289'`. Bits 0 to 11 are defined:

| Bit | Name | Set by |
|---|---|---|
| 0 | `KYC_DONE` | Every verification |
| 1 | `AML_CLEAR` | `addClaim` with `AML` |
| 2 | `SANCTIONS_CLEAR` | `addClaim` with `SANCTIONS_CHECK` |
| 3 | `PEP_CLEAR` | `addClaim` with `PEP_CHECK` |
| 4 | `ADULT` | An age proof |
| 5 | `EEA_RESIDENT` | A verification with an EEA country, or a residency proof against a list of EEA countries |
| 6 | `NOT_US_PERSON` | No Trusset flow sets it yet |
| 7 | `CONTRACT_HOLDER` | Your own wallet, for a contract that holds collateral. Not set through the API |
| 8 | `RESIDENCY_ON_FILE` | Every verification, and the `RESIDENCY` proof claim |
| 9 | `CITIZENSHIP_ON_FILE` | The `CITIZENSHIP` proof claim |
| 10 | `TAX_RESIDENCY_ON_FILE` | `addClaim` with `TAX_RESIDENCY` |
| 11 | `ACCREDITED` | The `ACCREDITATION` proof claim, which also raises the investor class to the proved tier |

Bits up to 63 are kept for this public table. The bits above are defined by each attester, which publishes their meaning.

The SDK exports the table and three helpers. None of them reads the chain.

```typescript
import { PREDICATE_BITS, predicateMask, predicateNamesOf, hasPredicates } from '@trusset/sdk'

const mask = predicateMask(['KYC_DONE', 'RESIDENCY_ON_FILE', 'EEA_RESIDENT'])
const names = predicateNamesOf(mask)
const eea = hasPredicates(mask, ['EEA_RESIDENT'])
```

`mask` is `'289'`, and `names` is `['KYC_DONE', 'EEA_RESIDENT', 'RESIDENCY_ON_FILE']`, in bit order. `predicateNamesOf` leaves out bits it has no name for, and takes a decimal string, a `0x` hex string, a number or a bigint. An unknown name or a bit outside 0 to 127 throws a `ValidationError`. `predicateNameOfClaimType` maps a claim's `claimType` to its predicate.

### Revoking on an instance ID register

A `revoke` withdraws only the attestation of the wallet that signs it. When another trusted attester still vouches for the customer, the wallet stays verified, and the confirm returns `warnings` with the code `STILL_VERIFIED_BY_ANOTHER_ATTESTER` and that `attester`. To stop the wallet for the whole instance, freeze it.

```typescript
const prepared = await trusset.customers.identity.revoke(customerWallet, { signerAddress: issuerWallet })
```

Pass `signerAddress` when you prepare a revoke without a signer. The API then checks that this wallet holds an attestation about the customer, and refuses with `NOTHING_TO_REVOKE` before you sign a transaction that would revert. `revokeClaim` takes the same third argument.

## Holder claims

<Note>
  Available from `@trusset/sdk` 0.9.0, on instance ID registers only.
</Note>

KYC approvals that are not on chain yet wait in the pending queue. Usually your issuer wallet registers them itself and pays the gas, through [Build Pending Registration](/endpoints/customers/build-pending-registration). With holder claims your wallet signs once, and each customer submits their own attestation:

1. Your attester wallet signs one EIP-712 message over the whole batch. Nothing is broadcast and no gas is paid.
2. Each customer sends one transaction from their own wallet with their part of the batch. The hub accepts it only from the wallet it names, so the transaction is also the customer's consent.

```typescript
const { rows } = await trusset.customers.identity.listPending()

const batch = await trusset.customers.identity.buildHolderBatch({
  ids: rows.map(row => row.id),
  attester: await issuer.getAddress(),
})

const { domain, types, message } = batch.typedData
const signature = await issuer._signTypedData(domain, types, message)

const stored = await trusset.customers.identity.storeHolderSignature({
  ids: batch.ids,
  signature,
  attester: batch.attester,
})
```

The typed data is `AttestationBatch(address attester, bytes32 batchRoot, uint32 issuedAt, uint64 deadline)` in the domain `IdentityHub`, version `1`, with your instance's chain and the hub address. Sign it wherever your key lives. A Safe or another contract wallet can sign in its own flow, and the hub checks that signature through ERC-1271. The batch is valid for 30 days and holds 1 to 200 rows. `issuedAt` is the issue date the hub stores, also for a claim sent weeks later.

Each customer then claims in one of two ways:

- **On verify.trusset.org.** A customer who passed KYC through an ID link that names their wallet signs in on the verification page and sees "Claim your verified identity". The page sends the transaction and records it.
- **From their own wallet.** `stored.claims` holds one entry per wallet, with the `transaction` to send. The customer sends `transaction.transaction` from that wallet, and you confirm the hash.

```typescript
const confirmed = await trusset.customers.identity.confirmHolderClaim(holderTxHash)
console.log(confirmed.walletAddress, confirmed.status, confirmed.predicates)
```

The customer pays the gas of the claim. The confirm reads the hub's logs, so a claim sent from a Safe or a smart account is recorded too, and the queue row reads `CONFIRMED`. A claim becomes void when your attester acts on that wallet again, or when the batch passes its deadline. Build a new batch for those rows. Refusals are listed under [Holder claim codes](/sdk/customers/errors#holder-claim-codes).

`listPending` takes `status` (`PENDING` by default, `CONFIRMED` or `DISMISSED`), `page` and `limit`, at most 200, and returns `rows` and `pagination`.

## Own ERC-3643 registers

An instance can be bound to the issuer's own ERC-3643 (T-REX 3, 4 or 5) identity register instead of an instance ID register. There a verification is three things: an ONCHAINID contract for the wallet, a claim on it signed by a claim key of the register's trusted issuer, and the registration on the register. The API hands them out phase by phase, and each answer names the next step:

| Phase | `action` | What it holds |
|---|---|---|
| `DEPLOY_IDENTITY` | `SIGN_TRANSACTIONS` | One ONCHAINID deployment per wallet that has none |
| `CREATE_IDENTITY` | `SIGN_TRANSACTIONS` | T-REX 5 only, in place of `DEPLOY_IDENTITY`. One `createIdentityFor` per wallet that has no ONCHAINID, sent to the register's identity factory. Needs no confirm |
| `SIGN_CLAIMS` | `SIGN_MESSAGES` | One `messageHash` per claim, to sign as an EIP-191 personal message. On T-REX 5 the message has `scheme: 'eip712'`, a `typedData` to sign and an `issuedAt` to send back |
| `REGISTER` | `SIGN_TRANSACTIONS` | The claim transactions and the registration, in order, with `confirmStepIndex` |

With `{ signer }` the SDK runs the phases for you on `verify`, `verifyFromManifest`, `batchVerify`, `addClaim` and `addClaimsFromProof`: it deploys and records each missing ONCHAINID, signs each claim message, signs the remaining steps and confirms the step that registers the wallet. The signer must hold a CLAIM key (purpose 3) on the trusted issuer, since it signs the claims; otherwise the API refuses with `CLAIM_SIGNER_NOT_TRUSTED` before anything is signed. `revoke` and `revokeClaim` are one transaction on these registers as well.

```typescript
const result = await trusset.customers.identity.verify({
  walletAddress: '0x1234567890abcdef1234567890abcdef12345678',
  country: 'DEU',
}, { signer })

console.log(result.transactions?.map(t => t.functionName))
```

To run the phases yourself, call without options and repeat the call with what each phase produced: record each deployment with `deployOnchainId(wallet, { txHash })`, then pass `identities` (wallet to ONCHAINID), `claimSignatures` (`{ walletAddress, signature, claimType }`) and `signerAddress` in the input. `batchVerify` takes them as its second argument.

```typescript
const prepared = await trusset.customers.identity.deployOnchainId(walletAddress, { signerAddress: issuerWallet })

const recorded = await trusset.customers.identity.deployOnchainId(walletAddress, { txHash: deploymentTxHash })
```

`deployOnchainId` with `{ signer }` deploys and records the ONCHAINID in one call, and returns the existing one, with `exists: true`, when the wallet already has an identity.

### T-REX 5 registers

<Note>
  Available from `@trusset/sdk` 0.7.0.
</Note>

On a T-REX 5 register (ONCHAINID 3 identities) the plan carries `trexVersion: 5` and `identityFactory`, and every step names the wallet that must sign it in `signer`. With `{ signer }` the runner handles the differences for you:

- In `CREATE_IDENTITY` it sends each `createIdentityFor` and confirms nothing: the identity factory links the identity to the wallet, so the runner builds the next phase once the transactions are mined.
- It signs a message with `scheme: 'eip712'` with the signer's `_signTypedData` over the message's `typedData`, and sends the signature back with the message's `issuedAt`. EIP-191 messages are signed as before.
- Before it signs anything, it refuses with `SIGNER_ROLE_MISSING` when a step's `signer` is not the signer you passed. The API answers the same code when the signer lacks the role a phase needs. One signer therefore has to hold every role the run reaches: the IDENTITY_ISSUER role of the factory when a wallet has no ONCHAINID, a CLAIM_SIGNER and a MANAGEMENT key on the trusted issuer identity, and the AGENT role of the register.
- `revoke` and `revokeClaim` send the signer's address as `signerAddress`, so on a T-REX 5 register the signer must hold a MANAGEMENT key on the trusted issuer identity, which is what revokes the claim.

`deployOnchainId` accepts the T-REX 5 creation as well: with `{ signer }` it sends `createIdentityFor` from the signer, which must hold the IDENTITY_ISSUER role of the factory and be the wallet the answer names in `signer`, and records the identity. The result carries `trexVersion: 5` and `identityFactory`. The investor wallet becomes the only MANAGEMENT key of its ONCHAINID.

To run the phases yourself on a T-REX 5 register, sign each message's `typedData` and send `claimSignatures` entries as `{ walletAddress, signature, claimType, issuedAt }`, with `issuedAt` exactly as the message gave it.

```typescript
for (const message of plan.messages ?? []) {
  if (message.scheme === 'eip712' && message.typedData) {
    const { domain, types, message: value } = message.typedData
    const signature = await signer._signTypedData(domain, types, value)
    claimSignatures.push({ walletAddress: message.walletAddress, signature, claimType: message.claimType, issuedAt: message.issuedAt })
  }
}
```

The types for these plans are exported: `TrexVersion` (`4 | 5`), `RegisterPhase`, which includes `'CREATE_IDENTITY'`, `ClaimSignature` with its optional `issuedAt`, and `ClaimSigningRequest`, whose `scheme` is `'eip191' | 'eip712'` and which carries `typedData` and `issuedAt` for `'eip712'`.

## Revoke an identity

<Warning>
  Revocation takes effect for the address at once. A revoked address cannot send or receive compliant tokens until it is verified again.
</Warning>

```typescript
const result = await trusset.customers.identity.revoke('0x1234567890abcdef1234567890abcdef12345678', { signer })
```

The result carries `walletAddress`, `status`, `txHash` and `gasUsed`. On an instance ID register it can also carry `warnings`; see [Revoking on an instance ID register](#revoking-on-an-instance-id-register).

On a T-REX 5 register `revoke` revokes the wallet's KYC claim with `revokeClaimByDigest` instead of deleting the identity, so verifying the wallet again signs a new claim and reverses it. See [Revoke Identity](/endpoints/customers/revoke-identity#on-a-t-rex-5-register).

## Erase an identity

On an instance ID register an attester can erase its own attestation for a wallet, for example after a deletion request once no retention duty applies. Erasing deletes the entry from the hub; the events keep only the salted root and the predicate bits.

```typescript
const plan = await trusset.customers.identity.erase(walletAddress, signerAddress)
const txHash = await sendWithYourWallet(plan.transaction)
const result = await trusset.customers.identity.confirmErase(walletAddress, signerAddress, txHash)
```

`signerAddress` is the attester that holds the entry. `erase` answers `NOTHING_TO_ERASE` when that wallet holds none. The result carries `walletAddress`, `attester`, `status`, `erased`, `txHash` and `gasUsed`, plus `warnings` when another trusted attester still vouches for the wallet. See [Erase Identity](/endpoints/customers/erase-identity).

## Get identity status

Returns combined on-chain and off-chain status for an address. The on-chain part comes from your instance's register and the off-chain part from the customer record. It is a read and needs no signature.

```typescript
const status = await trusset.customers.identity.getStatus('0x1234567890abcdef1234567890abcdef12345678')
```

| Field | Holds |
|---|---|
| `status.onChain.isVerified` | `true` while the identity is active |
| `status.onChain.status` | `active`, `soft_expired`, `hard_expired`, `revoked`, or `none` |
| `status.onChain.frozen` | Whether a regulatory freeze applies |
| `status.onChain.kycHash` | The stored root hash |
| `status.onChain.investorType` | The numeric on-chain classification |
| `status.onChain.timestamp` | Unix time of the last verification |
| `status.offChain.status` | `pending`, `verified`, or `revoked` |
| `status.offChain.country`, `investorType`, `verifiedAt` | The customer record's values |

On an instance ID register, `onChain` also carries:

| Field | Holds |
|---|---|
| `status.onChain.registerKind` | `INSTANCE` |
| `status.onChain.attester` | The trusted attester whose attestation the register reads. `kycProvider` holds the same wallet |
| `status.onChain.predicates` | The attested mask, as a decimal string |
| `status.onChain.predicateNames` | The same mask as names |

`kycHash` is the attested root. If no customer record exists, `offChain` is `null`. If the address was never verified on chain, `onChain.isVerified` is `false` with a status of `none`. On an instance bound to a T-REX 5 register, `onChain.trexVersion` is `5`. When the register could not be read, `onChain.unavailable` is `true`: that is not a verdict, so read again.

## On-chain claims

Claims attach typed attestations to a verified identity. Four types derive from a KYC proof bundle, four are added manually:

| Proof-backed (via `addClaimsFromProof`) | Manual (via `addClaim`) |
|---|---|
| `KYC`, `RESIDENCY`, `CITIZENSHIP`, `ACCREDITATION` | `AML`, `TAX_RESIDENCY`, `SANCTIONS_CHECK`, `PEP_CHECK` |

The first four are reserved. `addClaim` refuses them with `PROOF_REQUIRED`, so a residency attestation always means a proof was verified rather than something written by hand.

### Read claims

```typescript
const { claims } = await trusset.customers.identity.getClaims('0x1234567890abcdef1234567890abcdef12345678')
```

Each active claim carries `claimType`, `claimTypeLabel` (for example `KYC`), `dataHash`, `issuer`, `issuedAt`, `expiry` and `active`.

On an instance ID register each predicate bit of the attestation reads as one claim. A predicate that matches one of the eight claim types keeps that type's number and label, so `RESIDENCY_ON_FILE` reads as claim type `3`, `RESIDENCY`. Any other predicate reads as claim type `100` plus its bit, with the predicate name as its label: `ADULT` is `104`. Every claim also carries `predicate`, its own name, and `predicates`, all names of the attestation. `dataHash` is the attested root and `issuer` the attester.

### Claims from a proof

Adds every claim the bundle can back, or a `selected` subset. The wallet must already be verified on chain with the manifest's root hash, and the backend compares them before preparing any transaction. One transaction is prepared per claim, to be signed in the order returned.

Verify the bundle locally first, with the proof tool or a `verifier`, then send the manifest and its signed header only. Proof bytes never go to Trusset: these STARKs are not zero-knowledge, so a proof reveals the value it proves, an age proof the date of birth and a set-membership proof the country. The SDK refuses `proofs`, `proof`, `proofBytes` and `zk` with `PROOFS_NOT_ACCEPTED` before any request. [KYC Proofs](/sdk/customers/kyc-proofs#verify-the-bundle-locally) shows a verifier built on the tool's WASM `verify_with_header`.

```typescript
const bundle = 'output/0xAbCd...'
const manifest = JSON.parse(readFileSync(`${bundle}/manifest.json`, 'utf8'))
const header = JSON.parse(readFileSync(`${bundle}/header.json`, 'utf8'))
const headerSignature = readFileSync(`${bundle}/header.sig`)

const result = await trusset.customers.identity.addClaimsFromProof({
  walletAddress: manifest.walletAddress,
  manifest,
  header,
  headerSignature,
  verifier,
  selected: ['KYC', 'RESIDENCY'],
}, { signer })
```

<Expandable title="ProofClaimsInput fields">
  <ParamField body="manifest" type="KycProofManifest" required>
    `manifest.json` from the bundle, parsed and unmodified.
  </ParamField>
  <ParamField body="header" type="KycProofHeader">
    `header.json` from the bundle, parsed: `version` (`3.1.0`), `root`, `wallet`, `epochDays`, `attester`, `chainId`, `hub`, `keyId`, `merkleVersion` (`3`) and `leafCount`, in lowercase hex as the tool wrote them. Required with a 3.1.0 manifest. From 0.10.0.
  </ParamField>
  <ParamField body="headerSignature" type="Uint8Array | string">
    `header.sig`: its 64 raw bytes, their hex or their base64. Sent as `0x` and 128 lowercase hex characters. Required with `header`. From 0.10.0.
  </ParamField>
  <ParamField body="verifier" type="ProofVerifier">
    Your local check, run before any request. It receives `{ walletAddress, manifest, header, headerSignature, manifestSig }` and returns `true` or `{ ok: true }` to go on; `false`, `{ ok: false, reason }` or a throw stops the call with `LOCAL_VERIFICATION_FAILED`. Never sent. From 0.10.0.
  </ParamField>
  <ParamField body="selected" type="ClaimType[]">
    The claim types to add. Default: every claim the bundle backs.
  </ParamField>
  <ParamField body="expiryDays" type="number">
    Claim expiry. Default: the identity's hard expiry. An instance ID register takes its expiries from the bundle instead and answers the warning `EXPIRY_FROM_BUNDLE`.
  </ParamField>
  <ParamField body="manifestSig" type="Uint8Array | string">
    Deprecated. A 3.1.0 bundle is checked through its signed header.
  </ParamField>
  <ParamField body="proofs" type="Record<string, string>">
    Deprecated, and refused with `PROOFS_NOT_ACCEPTED` whenever it holds a value.
  </ParamField>
</Expandable>

The SDK checks the header before anything is sent: exactly its ten keys, a 64-byte signature, the same root, wallet, date, leaf count and chain block as the manifest, and the same wallet as `walletAddress`. A manifest whose `passthrough` carries `country` or `investorType`, as 2.x and 3.0 bundles do, is refused with `PERSONAL_DATA_IN_MANIFEST`.

`result.added` counts the claims confirmed on chain and `result.total` the claims attempted. `result.claims` holds one entry per claim with `claimType`, `dataHash`, `status` (`confirmed`, `failed` or `skipped`), and `txHash` or `error`. `result.verification` reports how the bundle was checked: `operatorKey` (`source` `hub` or `instance`, `keyId`, `publicKey`, and a `message` when the instance key stood in for the hub's), the hub `attestation` the bundle derives, and `attestPredicateNames`, the predicates the plan sets.

Without options the method returns `action: 'SIGN_TRANSACTIONS'` with ordered `steps`. Broadcast them in order, then confirm all of them at once with `{ txResults }`, pairing the `claimType` of each step that writes a claim with its hash. On a T-REX 5 register the plan can also hold a `rotateClaim` step, which revokes the claim a new one replaces. Broadcast it, and leave it out of `txResults`. With `{ signer }` the SDK does this pairing itself. On an instance ID register the plan is a single `attest` step that sets every proved predicate at once, and its `claims` lists the claims it covers. Pair each of them with that step's hash, as below. On an [own ERC-3643 register](#own-erc-3643-registers) the first answer is the `SIGN_CLAIMS` phase instead, which carries no `verification` yet:

```typescript
const prepared = await trusset.customers.identity.addClaimsFromProof({ walletAddress, manifest, header, headerSignature })
if (!('verification' in prepared)) {
  throw new Error('Sign the claim messages first, then call again with claimSignatures')
}

const txResults = []
for (const step of prepared.steps) {
  const tx = await signer.sendTransaction(step.transaction)
  await tx.wait(1)
  if (step.stepType === 'ADD_CLAIM' || step.stepType === 'ROOT_ROTATION') {
    for (const claim of step.claims ?? [step]) {
      txResults.push({ claimType: claim.claimType, txHash: tx.hash })
    }
  }
}

const result = await trusset.customers.identity.addClaimsFromProof({ walletAddress, manifest, header, headerSignature }, { txResults })
```

On an instance ID register one transaction confirms every claim, so each entry of `txResults` carries the same hash.

Failure modes: `PROOFS_NOT_ACCEPTED`, `PERSONAL_DATA_IN_MANIFEST`, `LOCAL_VERIFICATION_FAILED`, `HEADER_REQUIRED`, `INVALID_HEADER`, `INVALID_HEADER_SIGNATURE`, `HEADER_MISMATCH`, `NOT_VERIFIED`, `IDENTITY_REVOKED`, `HASH_MISMATCH`, `WALLET_MISMATCH`, `ATTESTER_NOT_TRUSTED`, `ATTESTER_MISMATCH`, `OPERATOR_KEY_UNKNOWN`, `UNREGISTERED_OPERATOR_KEY`, `LEAF_HASH_MISMATCH`, `ROOT_MISMATCH`, `NOT_ATTESTABLE`, `LEAF_LAPSED`, `UNSUPPORTED_VERSION`, `STUB_NOT_ALLOWED`, `INVALID_MANIFEST`, `NO_SELECTED_CLAIMS`. See the [troubleshooting table](/sdk/customers/kyc-proofs#troubleshooting).

### Inspect a bundle and attest single proofs

<Note>
  Available from `@trusset/sdk` 0.10.0.
</Note>

`inspectManifest({ manifest, header, headerSignature, walletAddress?, verifier? })` checks a bundle the way a claim would and writes nothing. Each leaf of the answer carries `predicate`, `attestable`, `classOnly` and `blockedReason`, and the answer carries `operatorKey` and `attestation`.

`attestProofs({ walletAddress, manifest, header, headerSignature, entries, verifier? }, options?)` attests the data points you name in `entries` (`[{ fieldName, claimType?, expiryDays? }]`, one to eight) and rotates the registered root when the bundle is newer. It takes the same three call shapes as every write; confirm a plan you signed yourself with `{ txResults: [{ fieldName, txHash }], rootTxHash }`. Both are described on [KYC Proofs](/sdk/customers/kyc-proofs#inspect-a-bundle-before-filing-it), and both refuse proof bytes like `addClaimsFromProof`.

When every claim of a confirm fails, the API answers `NO_CLAIMS_ADDED` and the SDK throws. The per-claim reasons are on the error: `err.data.claims` holds the same entries a successful confirm returns in `result.claims`. With `{ txResults }` the error's `code` is `NO_CLAIMS_ADDED`. With `{ signer }` it is a `ConfirmationError` with the code `CONFIRMATION_FAILED`, and `NO_CLAIMS_ADDED` is on `err.failure.code`.

### Manual claims

For attestations from your own screening processes rather than the proof tool. Provide either a pre-computed 32-byte `dataHash` or a `dataInput` string the backend hashes for you.

```typescript
const added = await trusset.customers.identity.addClaim({
  walletAddress: '0x1234567890abcdef1234567890abcdef12345678',
  claimType: 'AML',
  dataInput: 'aml-screening-ref-2026-07-01',
  expiryDays: 365,
}, { signer })
```

The result carries `claimType`, `dataHash`, `expiry`, `txHash` and `gasUsed`. When you confirm yourself, send the `dataHash` from the prepared response. Adding a proof-backed type manually fails with `PROOF_REQUIRED`, and re-adding an existing claim type overwrites it.

On an instance ID register the claim is its [predicate](#predicates), for example `AML_CLEAR`. The result also carries the mined `predicates` and `root`. The `dataHash` is kept in the audit trail, not on chain. A claim change edits a live attestation, so it fails with `IDENTITY_SUSPENDED`, `IDENTITY_SOFT_EXPIRED` or `IDENTITY_EXPIRED` until the identity is unsuspended or verified again.

### Revoke a claim

```typescript
await trusset.customers.identity.revokeClaim('0x1234567890abcdef1234567890abcdef12345678', 'AML', { signer })
```

The result carries `claimType`, `txHash` and `gasUsed`. On an instance ID register the `KYC` claim cannot be revoked on its own, because `KYC_DONE` carries the verification: the API refuses with `BASE_PREDICATE_REQUIRED`. Revoke the identity instead.

## Check transfer compliance

Validates whether a token transfer between two addresses would be allowed. This runs the full compliance pipeline: identity checks for both parties, KYC expiry, freeze checks, and all registered [compliance modules](/endpoints/customers/can-transfer). Amounts and balances are integer strings in the token's smallest unit.

```typescript
const check = await trusset.customers.identity.canTransfer({
  from: '0xaaaa000000000000000000000000000000000001',
  to: '0xbbbb000000000000000000000000000000000002',
  amount: '1000000000000000000',
  fromBalance: '5000000000000000000',
  toBalance: '0',
})
```

`check.allowed` is the verdict and `check.reason` the numeric rejection code, `0` when there is none. `check.senderStatus` and `check.receiverStatus` hold each party's KYC status.

<Tip>
  Call `canTransfer` before submitting a transfer to get a specific rejection reason rather than a generic revert.
</Tip>

This is a read. It needs no signature and costs no gas.
