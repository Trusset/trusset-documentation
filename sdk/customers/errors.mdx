This page is for the engineer writing the catch blocks. After reading it you will know which errors are worth retrying, which are not, and why an ambiguous write failure needs a status check rather than a retry.

All SDK errors extend `TrussetError` and carry a machine-readable `code`, HTTP `statusCode`, and the server's `requestId` when available. Catch specific subclasses to handle different failure modes.

## Error hierarchy

```typescript
import {
  TrussetError,
  AuthError,
  ValidationError,
  NetworkError,
} from '@trusset/sdk'
```

`ValidationError` is the one that never reaches the network. The SDK raises it from client-side checks, so it costs no request and its message names the offending field.

| Class | Status | Fires when | Do |
|---|---|---|---|
| `ValidationError` | 400 | Input rejected before hitting the API | Fix the input. Retrying is pointless. |
| `AuthError` | 401 | API key is invalid, expired, or the instance is archived | Check the key and the instance state. |
| `NetworkError` | 0 | Timeout, DNS failure, connection refused | Retry a read. For a write, check status first. |
| `TrussetError` | 4xx / 5xx | Server returned a non-success response | Branch on `code`. |

Order the branches from most specific to least. `TrussetError` is the base class, so a leading `instanceof TrussetError` swallows every other case.

## Catch errors

```typescript
try {
  await trusset.customers.manage.get('0xinvalid')
} catch (err) {
  if (err instanceof ValidationError) {
    console.error(err.message)
    return
  }

  if (err instanceof AuthError) {
    console.error(err.message, err.requestId)
    return
  }

  if (err instanceof NetworkError) {
    console.error(err.message)
    return
  }

  if (err instanceof TrussetError) {
    console.error(err.code, err.statusCode, err.message, err.requestId)
  }
}
```

The `ValidationError` from that call reports `walletAddress must be a valid Ethereum address`.

## Error properties

Every `TrussetError` instance exposes:

| Property | Type | Description |
|---|---|---|
| `message` | `string` | Human-readable error description |
| `code` | `string` | Machine-readable error code (e.g. `NOT_FOUND`, `TX_REVERTED`) |
| `statusCode` | `number` | HTTP status code. `0` for network errors. |
| `requestId` | `string \| null` | Server-assigned request ID for support inquiries |

## Common error codes

| Code | Status | Meaning |
|---|---|---|
| `AUTH_REQUIRED` | 401 | No API key provided |
| `AUTH_FAILED` | 401 | Invalid or expired API key |
| `NOT_FOUND` | 404 | Resource does not exist |
| `CUSTOMER_EXISTS` | 409 | Duplicate wallet or externalId |
| `WALLET_IN_USE` | 409 | Wallet already assigned to another customer |
| `SERVICE_NOT_ENABLED` | 403 | Required service not enabled on this instance |
| `RELAYER_NOT_CONFIGURED` | 400 | No verified wallet is registered on this instance |
| `TX_NOT_FOUND` | 404 | The transaction being confirmed has no receipt yet |
| `TX_REVERTED` | 400 | The transaction being confirmed reverted on-chain |
| `VALIDATION_ERROR` | 400 | Client-side input validation failure |

## Hosted verification page codes

These come from the hosted ID link page and from a partner page that drives the same link endpoints. Show the message to the customer; the next step is theirs unless the row says otherwise.

| Code | Status | Meaning | Next step |
|---|---|---|---|
| `INVALID_TOKEN` | 400 | The token in the link is not 32 to 128 lowercase hex characters (`Invalid token format`), so the link was cut short or changed | Open the link exactly as it was sent |
| `NOT_FOUND` | 404 | No link has this token (`Verification link not found` on `GET /public/id-links/{token}`, `Link not found` on the other calls) | Open the whole link again, or ask the issuer for a new one |
| `EXPIRED` | 400 | The link passed its expiry date, or the issuer revoked it | Ask the issuer for a new link |
| `PAYMENT_REQUIRED` | 402 | The link carries a verification fee that is not paid yet, so the identity check does not open | Pay the fee in the checkout the hosted page offers (a partner page starts it with `POST /public/id-links/{token}/checkout`), then continue |
| `WALLET_SIGNATURE_REQUIRED` | 401 | The link is tied to a wallet, or a wallet is being tied to it, and the visitor has not signed in with that wallet | Connect the wallet the link names and sign the message it shows (not a transaction, no gas) |
| `WALLET_SIGNATURE_MISMATCH` | 403 | The visitor signed in with a different wallet than the one being tied to the link | Sign in with the wallet being tied |
| `WALLET_MISMATCH` | 400 | Attach wallet or the completion names a different wallet than the one the link is tied to | Use the wallet the link names |
| `WALLET_IN_USE` | 409 | Attach wallet names a wallet that a customer of this instance already holds under a different verification | Tie another wallet, or ask the issuer for a link bound to this one |
| `WALLET_NOT_LINKED` | 403 | The completion names a wallet that a customer of this instance already holds under a different verification | Ask the issuer for a new link bound to this wallet |
| `ID_CHECK_NOT_SUBMITTED` | 409 | The identity check was not submitted to Sumsub yet, or Sumsub asked for documents again, so the link stays open | Finish the identity check, then complete again |
| `ALREADY_USED` | 400 | The link was used. The holder of its wallet gets `details.outcome` (`APPROVED` or `IN_REVIEW`); anyone else gets `details.walletSignInRequired: true` and no outcome | The customer signs in with the wallet the link names to see the result |
| `LINK_CLOSED` | 403 | The identity check behind the link was refused. Anyone but the holder of its wallet gets this code with `details.walletSignInRequired: true` and no reason. The holder gets the reason as its own code instead: `COUNTRY_BLOCKED` when the country was refused, otherwise `ID_CHECK_REJECTED` | The customer signs in with the wallet the link names to see the reason, or contacts the issuer |
| `ID_CHECK_REJECTED` | 403 | The issuer could not accept the identity check through this link, so the link is closed. Only the holder of the wallet the link names gets this code, or any visitor when the link names no wallet. A completion whose check Sumsub rejected for good answers it too | Contact the issuer to learn more or to start a new check |
| `COUNTRY_BLOCKED` | 403 | The link's country, or the country declared at completion, is on the blocked list of the link's verification profile, so the check is closed. The holder of a link closed for its country gets this code too | Contact the issuer if the country is wrong |
| `COUNTRY_MISMATCH` | 400 | The completion declares a different country than the one the issuer issued the link for | Complete with the link's country, or contact the issuer if yours differs |
| `ISSUER_BINDS_WALLET` | 409 | The check is approved on a link that names no wallet, so the issuer binds the wallet | The issuer calls [Bind Link Wallet](/endpoints/customers/bind-link-wallet) |
| `KYC_UNAVAILABLE` | 503 | Sumsub could not be asked whether the check was submitted, or the identity check is not available for this link | Open the link again later; a submitted check is not lost |
| `KYC_LEVEL_UNAVAILABLE` | 409 | Sumsub does not know the identity check level the issuer set up, so the check cannot start. `POST /public/id-links/{token}/refresh-sumsub-token` answers it as an error, and `GET /public/id-links/{token}` returns it in `data.kycUnavailable` | Contact the issuer, who sends a new link once the level is fixed |

A link is never used up by any of these answers.

`GET /public/id-links/{token}` returns the link's `note` and `customMessage` to anyone who opens the link, before any wallet sign-in, so neither may carry personal data.

KYC proof flow codes (`NOT_VERIFIED`, `HASH_MISMATCH`, `WALLET_MISMATCH`, `STUB_NOT_ALLOWED`, `INVALID_MANIFEST`, `INVALID_HASH`, `PROOF_REQUIRED`, `INVALID_CLAIM_TYPE`, `NO_SELECTED_CLAIMS`) are documented with fixes in the [KYC proofs troubleshooting table](/sdk/customers/kyc-proofs#troubleshooting).

## Retry behavior

Read requests (GET) are retried on transient failures. Write requests are not - identity writes carry on-chain side effects, and blindly repeating an ambiguous failure (5xx, timeout) could submit the same transaction twice. Writes retry only on `429`, where the server rejected the request before doing any work.

| Status | GET | POST / PUT / DELETE |
|---|---|---|
| 408 Request Timeout | Retried | No |
| 429 Too Many Requests | Retried | Retried |
| 500 / 502 / 503 / 504 | Retried | No |
| Network errors (DNS, connection) | Retried | No |
| Timeouts (AbortError) | Retried | No |
| 400, 401, 403, 404, 409 | No | No |

<Tip>
  If an on-chain write fails ambiguously (timeout, 5xx), check `identity.getStatus` or `identity.getClaims` before repeating it - the transaction may have landed anyway. Verification and claim writes are safe to repeat: re-verifying updates the identity, re-adding a claim overwrites it.
</Tip>

Retries use exponential backoff: 1s, 2s, 4s, capped at 10s. Configure via `maxRetries` in the client constructor. Set to `0` to disable.

```typescript
const trusset = new TrussetClient({
  apiKey: '...',
  maxRetries: 5,
  timeoutMs: 60_000,
})
```

On-chain write methods enforce higher per-request timeout floors regardless of `timeoutMs` (180s; `addClaimsFromProof` 420s), because the backend waits for block confirmations inside the request.

## Enable logging

Pass a logger to surface retry attempts and request metadata during development:

```typescript
const trusset = new TrussetClient({
  apiKey: '...',
  logger: console,
})
```

The logger receives `debug` calls for retry attempts, including the URL and attempt number. No sensitive data (API keys, request bodies) is logged.
