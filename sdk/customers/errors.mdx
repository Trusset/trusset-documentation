All SDK errors extend `TrussetError` and carry a machine-readable `code`, HTTP `statusCode`, and the server's `requestId` when available. Catch specific subclasses to handle different failure modes.

## Error hierarchy

```typescript
import {
  TrussetError,
  AuthError,
  ValidationError,
  NetworkError,
  ConfirmationError,
} from '@trusset/sdk'
```

`ValidationError` is the one that never reaches the network. The SDK raises it from client-side checks, so it costs no request and its message names the offending field. Its `code` is `VALIDATION_ERROR`, or one of the [KYC proof bundle codes](#kyc-proof-bundle-codes) when a proof bundle is refused before it is sent.

| Class | Status | Fires when | Do |
|---|---|---|---|
| `ValidationError` | 400 | Input rejected before hitting the API | Fix the input. Retrying is pointless. |
| `AuthError` | 401 | API key is invalid, expired, or the instance is archived | Check the key and the instance state. |
| `NetworkError` | 0 | Timeout, DNS failure, connection refused | Retry a read. For a write, check status first. |
| `ConfirmationError` | from the API, or 0 | A signed write broadcast at least one transaction but could not finish | Read `transactions` and `txHash`, then confirm with `{ txHash }`. Do not repeat the write. |
| `TrussetError` | 4xx / 5xx | Server returned a non-success response | Branch on `code`. |

Order the branches from most specific to least. `TrussetError` is the base class, so a leading `instanceof TrussetError` swallows every other case.

`ConfirmationError` comes from every write signed with `{ signer }`, in the customers and the lending module alike. Its `code` is `TRANSACTION_FAILED` when a transaction reverted or a step failed after earlier steps were broadcast, and `CONFIRMATION_FAILED` when every step mined but Trusset could not record the result. `transactions` lists each step with its `functionName`, `txHash`, `optional` flag and `error`, and `txHash` is the hash to confirm. `failure` holds the underlying error, the API's own `TrussetError` when the confirm call failed.

A few codes come from the SDK itself and are raised before anything is signed:

| Code | Fires when |
|---|---|
| `UNSIGNABLE_PLAN` | The API answered a write with no transaction the SDK can sign, or with a contract creation that carries no code |
| `UNSIGNABLE_STEP` | A step of a multi-step plan carries no signable transaction |
| `UNSIGNABLE_MESSAGE` | An own register asked for a claim signature in a form other than an EIP-191 message hash or EIP-712 typed data, or sent an EIP-712 message without its `typedData` or `issuedAt` |
| `SIGNER_ROLE_MISSING` | A step of an own T-REX 5 register plan names another wallet in `signer` than the signer you passed, so your signer lacks the role the step needs. Sign with the wallet the step names (from 0.7.0) |
| `CLAIM_SIGNATURE_REFUSED` | An own register asked again for a claim the signer already signed, so the signer is not a claim key of its trusted issuer |
| `PLAN_DID_NOT_SETTLE` | An own register plan did not reach its transactions within six rounds |
| `CHAIN_MISMATCH` | A prepared transaction names a chain other than the instance's |

## Catch errors

```typescript
try {
  await trusset.customers.manage.searchByWallet('0xinvalid')
} catch (err) {
  if (err instanceof ValidationError) {
    console.error(err.message)
    return
  }

  if (err instanceof AuthError) {
    console.error(err.message, err.requestId)
    return
  }

  if (err instanceof NetworkError) {
    console.error(err.message)
    return
  }

  if (err instanceof TrussetError) {
    console.error(err.code, err.statusCode, err.message, err.requestId)
  }
}
```

The `ValidationError` from that call reports `walletAddress must be a valid Ethereum address`.

## Error properties

Every `TrussetError` instance exposes:

| Property | Type | Description |
|---|---|---|
| `message` | `string` | Human-readable error description |
| `code` | `string` | Machine-readable error code (e.g. `NOT_FOUND`, `TX_REVERTED`) |
| `statusCode` | `number` | HTTP status code. `0` for network errors. |
| `requestId` | `string \| null` | Server-assigned request ID for support inquiries |
| `details` | `unknown` | The API's `error.details`, such as the per-field list of a `VALIDATION_ERROR`, or `null` |
| `data` | `object \| null` | Every other field the API put on the error, such as `candidates` or `marketId` |
| `retryAfter` | `number \| null` | Seconds the server asked to wait, on a `429` |

## Instance ID register codes

`trusset.customers.identity` raises these on an [instance ID register](/sdk/customers/identity#instance-id-registers).

| Code | Status | Meaning |
|---|---|---|
| `INSTANCE_REGISTER_REQUIRED` | 409 | The instance has no ID register yet. Create it in the instance settings of the issuer app |
| `IDENTITY_HUB_NOT_CONFIGURED` | 501 | The IdentityHub is not deployed on the instance's network yet |
| `ATTESTER_MISSING` | 403 | None of the instance's registered wallets is a trusted attester of its register. The hub would accept the attestation, but it would not count for the instance. Trust a wallet on the wallet page of the issuer app, signed by a register admin |
| `UNTRUSTED_ATTESTER` | 403 | The confirmed transaction, or the holder batch, was signed by a wallet the register does not trust |
| `NOT_VERIFIED_ON_REGISTER` | 409 | The attestation mined, but no trusted attester vouches for the wallet with the predicates the register requires |
| `BASE_PREDICATE_REQUIRED` | 409 | `revokeClaim` was asked to clear `KYC_DONE`, which carries the verification. Revoke the identity instead |
| `IDENTITY_SUSPENDED` | 409 | The attestation is suspended, so its claims cannot change |
| `IDENTITY_SOFT_EXPIRED` | 409 | The identity passed its soft expiry. Verify it again before changing its claims |
| `IDENTITY_EXPIRED` | 409 | The identity passed its hard expiry. Verify it again before changing its claims |
| `IDENTITY_NOT_ACTIVE` | 409 | A claim change or proof claim for a wallet with no active attestation. Verify it first |
| `IDENTITY_NOT_REGISTERED` | 409 | A revoke or claim for a wallet the register holds no active attestation for |
| `NOTHING_TO_REVOKE` | 409 | The `signerAddress` of a revoke holds no attestation about the wallet, so its revoke would revert. Sign with the record's attester, or freeze the wallet |
| `KYC_HASH_MISSING` | 409 | A pending row has no root to attest. Dismiss it and verify the customer again |
| `KYC_HASH_REQUIRED` | 400 | A verify or batch-verify on the instance ID register carries `kycData`, or no `kycHash` on the calldata leg. Send the bundle root or your own salted commitment |
| `DATA_HASH_REQUIRED` | 400 | An add-claim on the instance ID register carries `dataInput`. Send `dataHash`, your own salted commitment |
| `NOTHING_TO_ERASE` | 409 | The `signerAddress` of an erase holds no entry about the wallet on the hub |
| `TX_ATTESTER_MISMATCH` | 400 | The erase confirm found an `Erased` event of another attester than `signerAddress` |
| `TX_PREDICATES_MISMATCH` | 400 | The mined attestation lacks a predicate the confirm expects, or still carries one it should have cleared |
| `TX_ROOT_MISMATCH` | 400 | The mined attestation carries another root than the confirm expects |
| `CHAIN_UNAVAILABLE` | 503 | The register or the chain could not be read just now. Not a verdict: retry |

A revoke that succeeds can carry the warning `STILL_VERIFIED_BY_ANOTHER_ATTESTER` in `result.warnings`. It is not an error: another trusted attester still vouches for the wallet.

## Hosted verification page codes

These come from the hosted ID link page and from a partner page that drives the same link endpoints. Show the message to the customer; the next step is theirs unless the row says otherwise.

| Code | Status | Meaning | Next step |
|---|---|---|---|
| `INVALID_TOKEN` | 400 | The token in the link is not 32 to 128 lowercase hex characters (`Invalid token format`), so the link was cut short or changed | Open the link exactly as it was sent |
| `NOT_FOUND` | 404 | No link has this token (`Verification link not found` on `GET /public/id-links/{token}`, `Link not found` on the other calls) | Open the whole link again, or ask the issuer for a new one |
| `EXPIRED` | 400 | The link passed its expiry date, or the issuer revoked it | Ask the issuer for a new link |
| `PAYMENT_REQUIRED` | 402 | The link carries a verification fee that is not paid yet, so the identity check does not open | Pay the fee in the checkout the hosted page offers (a partner page starts it with `POST /public/id-links/{token}/checkout`), then continue |
| `WALLET_SIGNATURE_REQUIRED` | 401 | The link is tied to a wallet, or a wallet is being tied to it, and the visitor has not signed in with that wallet | Connect the wallet the link names and sign the message it shows (not a transaction, no gas) |
| `WALLET_SIGNATURE_MISMATCH` | 403 | The visitor signed in with a different wallet than the one being tied to the link | Sign in with the wallet being tied |
| `WALLET_MISMATCH` | 400 | Attach wallet or the completion names a different wallet than the one the link is tied to | Use the wallet the link names |
| `WALLET_IN_USE` | 409 | Attach wallet names a wallet that a customer of this instance already holds under a different verification | Tie another wallet, or ask the issuer for a link bound to this one |
| `WALLET_NOT_LINKED` | 403 | The completion names a wallet that a customer of this instance already holds under a different verification | Ask the issuer for a new link bound to this wallet |
| `ID_CHECK_NOT_SUBMITTED` | 409 | The identity check was not submitted to Sumsub yet, or Sumsub asked for documents again, so the link stays open | Finish the identity check, then complete again |
| `ALREADY_USED` | 400 | The link was used. The holder of its wallet gets `details.outcome` (`APPROVED` or `IN_REVIEW`); anyone else gets `details.walletSignInRequired: true` and no outcome | The customer signs in with the wallet the link names to see the result |
| `LINK_CLOSED` | 403 | The identity check behind the link was refused. Anyone but the holder of its wallet gets this code with `details.walletSignInRequired: true` and no reason. The holder gets the reason as its own code instead: `COUNTRY_BLOCKED` when the country was refused, otherwise `ID_CHECK_REJECTED` | The customer signs in with the wallet the link names to see the reason, or contacts the issuer |
| `ID_CHECK_REJECTED` | 403 | The issuer could not accept the identity check through this link, so the link is closed. Only the holder of the wallet the link names gets this code, or any visitor when the link names no wallet. A completion whose check Sumsub rejected for good answers it too | Contact the issuer to learn more or to start a new check |
| `COUNTRY_BLOCKED` | 403 | The link's country, or the country declared at completion, is on the blocked list of the link's verification profile, so the check is closed. The holder of a link closed for its country gets this code too | Contact the issuer if the country is wrong |
| `COUNTRY_MISMATCH` | 400 | The completion declares a different country than the one the issuer issued the link for | Complete with the link's country, or contact the issuer if yours differs |
| `ISSUER_BINDS_WALLET` | 409 | The check is approved on a link that names no wallet, so the issuer binds the wallet | The issuer calls [Bind Link Wallet](/endpoints/customers/bind-link-wallet) |
| `KYC_UNAVAILABLE` | 503 | Sumsub could not be asked whether the check was submitted, or the identity check is not available for this link | Open the link again later; a submitted check is not lost |
| `KYC_LEVEL_UNAVAILABLE` | 409 | Sumsub does not know the identity check level the issuer set up, so the check cannot start. `POST /public/id-links/{token}/refresh-sumsub-token` answers it as an error, and `GET /public/id-links/{token}` returns it in `data.kycUnavailable` | Contact the issuer, who sends a new link once the level is fixed |

A link is never used up by any of these answers.

`GET /public/id-links/{token}` returns the link's `note` and `customMessage` to anyone who opens the link, before any wallet sign-in, so neither may carry personal data.

## KYC proof bundle codes

Trusset never receives proof bytes: the KYC tool's STARKs are not zero-knowledge, so a proof reveals the value it proves, an age proof the date of birth and a set-membership proof the country. `addClaimsFromProof`, `attestProofs`, `inspectManifest` and `verifyFromManifest` check the bundle before any request and raise these as a `ValidationError` with the code below. `statusCode` is `400` and nothing was sent.

| Code | Fires when |
|---|---|
| `PROOFS_NOT_ACCEPTED` | The input, the manifest or one of its leaves carries `proofs`, `proof`, `proofBytes` or `zk` with a value. The API answers a request that carries them with the same code |
| `PERSONAL_DATA_IN_MANIFEST` | The manifest `passthrough` carries `country` or `investorType`, as 2.x and 3.0 bundles do, or the `passthrough` of a 3.1.0 manifest carries anything besides `softExpiryDays` and `hardExpiryDays`. The API answers the same code. Re-issue the bundle with tool v3.1 |
| `LOCAL_VERIFICATION_FAILED` | The `verifier` you passed returned `false` or `{ ok: false }`, or threw. `details` holds what it returned or threw |
| `HEADER_REQUIRED` | A 3.1.0 manifest came without `header` and `headerSignature`, or one of the two came alone |
| `INVALID_HEADER` | `header` is not `header.json` parsed with exactly its ten keys and their formats, or a header came with a pre-3.1.0 manifest |
| `INVALID_HEADER_SIGNATURE` | `headerSignature` is not the 64 bytes of `header.sig`, as bytes, hex or base64 |
| `HEADER_MISMATCH` | The header and the manifest disagree on root, wallet, date, leaf count, Merkle version or chain block |
| `WALLET_MISMATCH` | The header names another wallet than `walletAddress` |

`ProofErrorCode` types these codes together with the header codes only the API raises: `CHAIN_MISMATCH`, `HUB_MISMATCH`, `ATTESTER_NOT_TRUSTED`, `ATTESTER_MISMATCH`, `OPERATOR_KEY_UNKNOWN`, `UNREGISTERED_OPERATOR_KEY`, `NOT_ATTESTABLE`, `LEAF_LAPSED` and `CHAIN_UNAVAILABLE`. With `{ signer }`, `attestProofs` raises `NO_PROOF_STEPS` when the signed plan held no step that attests a data point, wrapped in a `ConfirmationError` like any failed confirm.

The other KYC proof flow codes (`NOT_VERIFIED`, `HASH_MISMATCH`, `STUB_NOT_ALLOWED`, `INVALID_MANIFEST`, `INVALID_HASH`, `PROOF_REQUIRED`, `INVALID_CLAIM_TYPE`, `NO_SELECTED_CLAIMS`) are documented with fixes in the [KYC proofs troubleshooting table](/sdk/customers/kyc-proofs#troubleshooting).

## Retry behavior

Read requests (GET) are retried on transient failures. Writes are not: repeating an ambiguous failure, such as a 5xx or a timeout, could record or send the same thing twice. A write retries only on `429`, where the server refused the request before doing any work.

| Status | GET | POST / PUT / PATCH / DELETE |
|---|---|---|
| 408 Request Timeout | Retried | No |
| 429 Too Many Requests | Retried | Retried |
| 500 / 502 / 503 / 504 | Retried | No |
| Network errors (DNS, connection) | Retried | No |
| Timeouts (AbortError) | Retried | No |
| 400, 401, 402, 403, 404, 409 | No | No |

On a `429` the SDK waits as long as the server's `Retry-After` header says, at most 60 seconds, then sends the request again. Every write route shares a limit of 10 requests per minute per API key, so a burst of writes waits rather than fails. Other retries back off exponentially: 1s, 2s, 4s, capped at 10s. `maxRetries` in the client constructor caps the attempts, and `0` disables retries.

Confirm calls of on-chain writes also retry `TX_NOT_FOUND` up to three times, after 3, 6 and 12 seconds, because the node answering Trusset may not have seen a receipt your wallet already has. The lending module's confirm calls also retry `408`, `502`, `503`, `504` and network errors, because the backend records one mined transaction once. The customer identity confirms keep the other write rules above.

<Tip>
  If an on-chain identity write fails ambiguously, check `identity.getStatus` or `identity.getClaims` before repeating it, because the transaction may have landed anyway. Verification and claim writes are safe to repeat: re-verifying updates the identity, and re-adding a claim overwrites it.
</Tip>

```typescript
const trusset = new TrussetClient({
  apiKey: '...',
  maxRetries: 5,
  timeoutMs: 60_000,
})
```

On-chain write methods raise the request timeout to at least 60 seconds, and `addClaimsFromProof`, `attestProofs` and `inspectManifest` to 180 seconds, whatever `timeoutMs` says, because the backend checks a proof bundle against the IdentityHub on both legs.

## Enable logging

Pass a logger to surface retry attempts and request metadata during development:

```typescript
const trusset = new TrussetClient({
  apiKey: '...',
  logger: console,
})
```

The logger receives `debug` calls for retry attempts, including the URL and attempt number. No sensitive data (API keys, request bodies) is logged.
