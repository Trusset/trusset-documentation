This page is for the party that receives pledge events, most often a register provider. After reading it you can create a webhook, verify its deliveries and rely on their order.

A pledge webhook sends your server one signed `POST` for every change to a pledge on the lending markets your instance can read. It carries what a register entry needs: the holder, the pledgee, the amount, the transaction and whether the pledge still stands. A register provider enters and releases pledges from these deliveries without polling [List Pledges](/endpoints/asset-register/list-pledges). The register entry stays the register provider's own act: a delivery reports the chain, and no webhook writes to a register.

Deployers, lenders of record and register providers use the same webhooks. Each receives the events of the markets its own instance can read.

## Create a webhook

Webhooks are created and managed in the Issuer Portal, on the Webhooks page of the instance. No API key endpoint creates one.

<Steps>
  <Step title="Open Create Webhook">
    Choose **Pledge recording** as the source of events.
  </Step>
  <Step title="Enter the endpoint">
    An `https` URL on a public host, without credentials in the URL. Redirects are not followed.
  </Step>
  <Step title="Choose events and markets">
    All seven events and all markets by default. A webhook set to all markets also covers markets the instance imports or deploys later. A webhook that names markets takes at most 50 of them.
  </Step>
  <Step title="Save the signing secret">
    The secret is shown once, when the webhook is created. Store it where your receiver can read it.
  </Step>
</Steps>

An instance holds at most 10 pledge webhooks. The webhook's details list every delivery with its status and offer a test delivery, a replay per delivery, a new signing secret, a pause switch and deletion.

## Which markets a webhook covers

| Instance | Markets |
|---|---|
| The deployer of a market | Its own markets |
| The lender of record | The markets it took |
| An asset register | The markets it [imported](/endpoints/asset-register/import-market) |

A register stops receiving a market's events when it declines the market, and when the deployer clears or replaces the register for the token.

## Events

| `type` | Sent when | Extra fields in `data` |
|---|---|---|
| `pledge.created` | A loan opened, or collateral was added under a new reference, and the adapter locked it in favour of the pledgee | |
| `pledge.increased` | Collateral was added to an existing pledge | |
| `pledge.decreased` | Part of the collateral was returned to the holder | |
| `pledge.released` | The pledge ended and the remaining collateral was released to the holder | `shortfallBorne`, only when the adapter returned less than the pledge recorded |
| `pledge.enforced` | Collateral was seized in a liquidation | `to`, the recipient. `final`, `true` when the seizure took the last of the pledge |
| `pledge.split` | Part of a pledge moved to a new reference with the same holder and pledgee. The event describes the new pledge | `fromRef`, `toRef`, `parentCurrentAmount` |
| `pledge.shortfall` | A freeze market asked the token to unfreeze more than was still frozen for the holder | `requested`, `unfrozen` |

For a register, `pledge.created` opens an entry and `pledge.released` takes it off. `pledge.enforced` with `final: true` means the pledge was realized. A `pledge.enforced` with `final: false` is a partial seizure, and the pledge stands for `currentAmount`.

In a `CUSTODY` market the token moves to the adapter, which is a transfer for security and not a pledge. The events are sent all the same, with `collateralMode: CUSTODY`, so a register that records pledges can skip them. See [Collateral mode changes what to record](/endpoints/asset-register/introduction#collateral-mode-changes-what-to-record).

## Payload

<ResponseField name="id" type="string">The delivery ID. It stays the same across retries of one delivery. A replay gets a new one.</ResponseField>
<ResponseField name="type" type="string">One of the seven events, or `test` for a test delivery.</ResponseField>
<ResponseField name="webhookId" type="string">The webhook this delivery belongs to.</ResponseField>
<ResponseField name="instanceId" type="string">The instance that owns the webhook.</ResponseField>
<ResponseField name="idempotencyKey" type="string">One key per chain log and event type. Store it and skip a key you have already processed.</ResponseField>

<ResponseField name="data" type="object">
  <Expandable defaultOpen>

A test delivery carries `type: test` and `data.message`, and no `idempotencyKey`. A replay repeats the original payload with a new `id` and `emittedAt`, plus `replayed: true` and `replayOf` naming the delivery it repeats.

## Headers

| Header | Value |
|---|---|
| `x-webhook-signature` | HMAC-SHA256, hex, keyed with the signing secret exactly as shown, over the `x-webhook-timestamp` value, a dot and the raw body |
| `x-webhook-timestamp` | Unix seconds when the attempt is sent. Each retry carries a fresh one, and a fresh signature |
| `x-trusset-event` | The event `type` |
| `x-trusset-webhook-id` | The webhook |
| `x-trusset-delivery-id` | The delivery `id`. The same across retries |
| `x-trusset-idempotency-key` | The payload's `idempotencyKey`. A replay carries the key of the delivery it repeats. Absent on a test delivery |
| `user-agent` | `Trusset-Pledge-Webhook/1.0` |

## Verify a delivery

Compute the signature over the body bytes as they arrived, before any JSON parsing, and compare in constant time. Refuse a timestamp that is more than a few minutes off.

```typescript
import { createHmac, timingSafeEqual } from 'node:crypto'

function isFromTrusset(rawBody: string, timestamp: string, signature: string, secret: string): boolean {
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false
  const expected = createHmac('sha256', secret).update(`${timestamp}.${rawBody}`).digest()
  const received = Buffer.from(signature, 'hex')
  return received.length === expected.length && timingSafeEqual(received, expected)
}
```

The SDK does the same with [`readPledgeWebhook`](/sdk/asset-registers/webhooks).

Rotating the secret in the Issuer Portal stops the previous secret at once, with no overlap. Every attempt sent afterwards is signed with the new secret, including retries of deliveries queued earlier.

## Delivery, retries and order

Answer with any `2xx` within 10 seconds to accept a delivery. Do the work after you answered.

| Your answer | What happens |
|---|---|
| `2xx` | Delivered |
| `408`, `425`, `429`, any `5xx`, no answer in 10 seconds, or a connection error | Retried |
| Any other `4xx`, or a redirect | Failed at once, without a retry. The queue moves on to the next event |

A delivery gets up to 10 attempts over about 24 hours. The waits between them are 30 seconds, 2 minutes, 10 minutes, 30 minutes, 1 hour, 2 hours, 4 hours, 8 hours and 8 hours.

**Order.** The events of one webhook leave in chain order, by block and log position. While a delivery waits for its retry, the later events of the same webhook wait behind it. Once it is delivered, or marked failed, the queue moves on. Replays are sent at once and hold nothing back.

**At least once.** A delivery can reach you more than once, for example when your `2xx` was lost on the way. Process each `idempotencyKey` once.

**Pausing.** When the tenth attempt of a delivery fails too, the webhook pauses itself and the delivery stays queued. Nothing is dropped: switch the webhook back on and the queue is sent in order, starting with that delivery. A webhook also pauses after 25 deliveries in a row that your endpoint refused without a retry. A paused webhook, whether paused by you or by itself, keeps collecting events.

**Retention.** Deliveries are kept for 30 days, delivered or not, and are then deleted. A failed delivery can be replayed from the webhook's details within that time.

**Starting point.** A webhook receives events that happened on chain after it was created. Read [List Pledges](/endpoints/asset-register/list-pledges) once for the pledges that already stand.

## When an event arrives

An event is sent once its transaction has three confirmations and the market's adapter logs have been read. Take a transaction that an instance holding the market's record confirms through Trusset. The market is read about 45 seconds and again about two minutes after that confirmation. Every watched market is also read every ten minutes, which picks up transactions that did not pass through Trusset. Markets are read only while at least one active webhook covers them.

A read that fails is repeated, first after a minute and then at growing intervals up to 30 minutes. No event is lost by a failed read: the position in the chain moves only together with the events queued for it.

A webhook is the fast path, and [List Pledges](/endpoints/asset-register/list-pledges) stays the record to reconcile against. Its `index` fields say how far the chain has been read.

Three confirmations are the only guard against a chain reorganisation. An event whose transaction a deeper reorganisation removes is not withdrawn by a later event. Check `transaction.hash` on chain before a step that cannot be undone.
