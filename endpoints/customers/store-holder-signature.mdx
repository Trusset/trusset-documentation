---
title: 'Store Holder Signature'
api: 'POST /customers/api/identity/pending/holder-batch/signature'
description: 'Check the batch signature and prepare one claim per customer'
---

Takes the signature over the batch from [Build Holder Batch](/endpoints/customers/build-holder-batch), checks it, and stores one claim on each row. Each claim is the transaction the customer sends from their own wallet to put their attestation on the identity hub. See [Holder claims](/endpoints/customers/introduction#holder-claims).

Nothing is sent on chain here, and the rows stay `PENDING` until a claim is recorded.

## Where the claims go

A customer whose row came from an [ID link](/endpoints/customers/create-id-link) with their wallet bound sees a Claim step on verify.trusset.org when they open the link again with that wallet. Their wallet switches to the hub's chain, sends the claim, and the app records it. Nothing else is needed from you.

For any other row, hand the customer the `transaction` from `claims` yourself, for example in your own app. It must be sent from the customer's wallet, the `walletAddress` of the claim: the hub refuses it from any other sender. Record it afterwards with [Confirm Holder Claim](/endpoints/customers/confirm-holder-claim).

The customer pays the gas. A claim can be sent until the batch's `deadline`, and any later write by your attester about the same wallet on the hub voids it.

## How the signature is checked

The signature must be the 65-byte signature of `attester` over the batch's typed data, with `v` 27 or 28 and a low `s`, as the identity hub requires. When `attester` is a contract wallet, such as a Safe, the contract is asked with ERC-1271 `isValidSignature` over the same digest, and `signatureCheck` is `CONTRACT`.

The signature is written to the customer audit log of each row as `HOLDER_CLAIM_SIGNED`, with the attester, the `batchRoot`, the `deadline` and the check that passed.

## Body Parameters

<ParamField body="ids" type="array" required>
  1 to 200 row ids, the same batch you built. Only rows still `PENDING` on your instance are used, and any other id is dropped without an error. Every row used must carry the same batch.
</ParamField>

<ParamField body="signature" type="string" required>
  The signature over `typedData`, as a hex string.
</ParamField>

<ParamField body="attester" type="string" required>
  The wallet that signed. It must be the `attester` the batch was built for, and your instance ID register must still trust it.
</ParamField>

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `attester` is missing or not a wallet address |
| `VALIDATION_ERROR` | `400` | `ids` is not an array of 1 to 200 ids |
| `ATTESTER_MISMATCH` | `400` | The batch was built for another attester |
| `INVALID_SIGNATURE` | `400` | `signature` is not a hex string, is not a 65-byte low-s signature of `attester`, or the `attester` contract does not accept it |
| `NOT_FOUND` | `404` | None of the ids is a `PENDING` row of your instance, or the instance no longer exists |
| `UNTRUSTED_ATTESTER` | `403` | Your instance ID register no longer trusts `attester` |
| `HOLDER_BATCH_MISSING` | `409` | A row carries no batch. Build it first with Build Holder Batch |
| `HOLDER_BATCH_MISMATCH` | `409` | The rows belong to different batches. Store each batch with its own ids |
| `HOLDER_BATCH_EXPIRED` | `409` | The batch has passed its `deadline`. Build it again |
| `HOLDER_PATH_UNAVAILABLE` | `409` | Your instance writes to a register of its own, not to an instance ID register |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance has no instance ID register |
| `IDENTITY_HUB_NOT_CONFIGURED` | `501` | The identity hub is not deployed on your instance's network |
| `CHAIN_UNAVAILABLE` | `503` | The `attester` contract could not be asked to check the signature. Retry shortly |
| `HOLDER_SIGNATURE_FAILED` | `400`, `500` | The signature could not be stored, for example because a chain read failed |
