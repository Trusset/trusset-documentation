Checks a [KYC-STARKs](/tools/kyc-starks/overview) 3.1 bundle against its signed header, derives the claims it backs, and returns the calldata that writes them on chain.

<Warning>
  Trusset never receives proof bytes. A 3.1 proof is not zero-knowledge: an age proof reveals the date of birth, a set-membership proof the country, a tier proof the investor class. Verify the proofs on your side with the tool or the SDK, then send the manifest and its signed header only.

  A body that carries `proofs`, `proof`, `proofBytes` or `zk`, at the top level, in the manifest or in a leaf, is refused with `400 PROOFS_NOT_ACCEPTED` before anything else is read. A 2.x or 3.0 bundle carries the country and the investor type in clear text and is refused with `400 PERSONAL_DATA_IN_MANIFEST`. Re-issue it with tool 3.1.
</Warning>

## What Trusset checks

Trusset runs no STARK. It checks everything around the proofs:

- **The header signature.** The header names an attester, a chain, an identity hub and a key id. Trusset reads the operator key the hub publishes for that attester under that key id (`operatorKeyAt`) and checks `header.sig` against it. When the attester has published no key on the hub, the key registered on this instance with [Set Operator Key](/endpoints/customers/set-operator-key) is used instead, and `verification.operatorKey.source` reads `instance`. An attester that publishes keys on the hub but not the one the header names is refused with `OPERATOR_KEY_UNKNOWN`.
- **The binding.** The header must name your instance's chain and identity hub, and an attester your register trusts. On a register of your own the attester must be a verified wallet of your instance.
- **Every leaf.** Its public digest, binding digest, parameters and predicate, its leaf hash under the header's wallet and date, and the Merkle root of all leaves against the header's root. The attestation derived from the manifest must match the header.
- **The trust anchors.** The approved lists and parameter sets of your network, the bundle's age against the staleness bound, and the validity window of each leaf you file.

Each leaf's `proofDigest` is inside its leaf hash, so the attester's signature over the root covers the proof bytes the attester hashed. Whether those bytes verify is the check you run before you send.

## Which claims a bundle backs

A bundle always backs a `KYC` claim, whose `dataHash` is the root. Each leaf whose `binding.predicate` names a hub predicate backs one more, with the leaf hash as its `dataHash`:

| Leaf predicate | Leaf | On the instance ID register | On a register of your own |
|---|---|---|---|
| `ADULT` | `age_threshold`, `minAgeDays` at least 6570 | `ADULT` | No slot. File it with [Attest Proofs](/endpoints/customers/attest-proofs) |
| `EEA_RESIDENT` | `set_membership` on the `eea` list | `EEA_RESIDENT` | `RESIDENCY`, when no `RESIDENCY_ON_FILE` leaf takes it |
| `RESIDENCY_ON_FILE` | `set_membership` on an approved list | `RESIDENCY` | `RESIDENCY` |
| `CITIZENSHIP_ON_FILE` | `set_membership` on an approved list | `CITIZENSHIP` | `CITIZENSHIP` |
| `TAX_RESIDENCY_ON_FILE` | `set_membership` on an approved list | `TAX_RESIDENCY` | `TAX_RESIDENCY` |
| `ACCREDITED` | `tier_threshold`, `minTier` at least 2 | `ACCREDITATION` | `ACCREDITATION` |
| `INVESTOR_CLASS` | `tier_threshold`, `minTier` is the subject's class | No claim: it sets the attestation's investor class | `ACCREDITATION`, when no `ACCREDITED` leaf takes it |

A leaf with no predicate, such as a `commitment_only` leaf, backs nothing. On the [instance ID register](/endpoints/customers/introduction#the-instance-id-register) each claim is a [predicate](/endpoints/customers/introduction#predicates) bit on the wallet's attestation. Nothing is verified on chain: the identity hub stores the root, the investor class and the predicate bits, and the leaf hashes stay in Trusset's proof ledger.

<Warning>
  On the instance ID register the plan is one `attest` that writes the attestation the bundle describes: its root, its investor class, its soft and hard expiries, `KYC_DONE` and the predicates you file. From the attester's current attestation for this wallet it keeps the attester statements (`AML_CLEAR`, `SANCTIONS_CLEAR`, `PEP_CLEAR`, `NOT_US_PERSON`, `CONTRACT_HOLDER`) and any predicate of this bundle it already carries. Any other predicate it carries is not written again. The hub stores the attestation under the wallet that sends it, so send the step from the attester the header names.

  On a register of your own with the Trusset interface (`registerKind: TRUSSET`) the register keeps one claim per slot, and filing a slot replaces the claim already there, whoever wrote it. Use `selected` to file only the slots you mean to overwrite.
</Warning>

The subject must already be verified on chain, and a wallet whose `kycHash` on the register is zero is refused with `NOT_VERIFIED`. Verify first with [Verify Identity](/endpoints/customers/verify-identity). The bundle's root must be the root the register holds, or the call fails with `HASH_MISMATCH`; [Attest Proofs](/endpoints/customers/attest-proofs) rotates the root to a newer bundle. A revoked identity keeps its `kycHash`, but the calldata leg refuses it with `IDENTITY_REVOKED`; re-verify it first. The confirm leg still records claims that mined before the revocation. On the instance ID register a suspended attestation answers `409 IDENTITY_SUSPENDED`.

<Note>
  This endpoint, [Inspect Manifest](/endpoints/customers/inspect-manifest) and Attest Proofs share one rate limit per instance: 30 requests in a 60-second window, both legs counted. Past it, they answer `429 RATE_LIMITED` with a `Retry-After` header in seconds.
</Note>

## Body Parameters

<ParamField body="walletAddress" type="string" required>
  The subject. Must already carry a non-zero `kycHash` on the register.
</ParamField>

<ParamField body="manifest" type="object" required>
  The bundle's `manifest.json`, parsed, version `3.1.0`. At most 64 KiB serialized and 32 leaves. Its `passthrough` holds `softExpiryDays` and `hardExpiryDays` only, and no part of it may carry proof bytes.
</ParamField>

<ParamField body="header" type="object" required>
  The bundle's `header.json`, parsed: `version`, `root`, `wallet`, `epochDays`, `attester`, `chainId`, `hub`, `keyId`, `merkleVersion` and `leafCount`.
</ParamField>

<ParamField body="headerSignature" type="string" required>
  The bundle's `header.sig`, the 64-byte ed25519 signature over the header, as `0x` followed by 128 lowercase hex characters.
</ParamField>

<ParamField body="signerAddress" type="string">
  The wallet you will sign with. Every plan is built for the attester the header names, so when you send it, it must be that attester or the call answers `ATTESTER_MISMATCH`.
</ParamField>

<ParamField body="selected" type="array">
  Claim type names or predicate names to file, for example `["KYC", "RESIDENCY", "ADULT"]`. Indices are not matched. Omit it, or send an empty array, to file every claim the bundle backs. A selection that matches nothing the bundle backs is refused with `NO_SELECTED_CLAIMS`.
</ParamField>

<ParamField body="expiryDays" type="integer">
  Register of your own only. Days until the claims expire, between 0 and 36500. Omit it, or send `0`, and the identity's own hard expiry is used if it is still in the future. Otherwise the claims do not expire.

  On the instance ID register the expiries come from the bundle, and a value here only adds an `EXPIRY_FROM_BUNDLE` warning.
</ParamField>

<ParamField body="txResults" type="array">
  Send this to confirm. An array of `{ claimType, txHash }`, with `claimType` as a name or an index. On the instance ID register one transaction writes every claim, and the first hashes you send, at most three, are read for all of them. On a register of your own name the transaction that wrote each claim; a claim type you leave out comes back `skipped`. A step that only revokes the claim being replaced, `rotateClaim` on a T-REX 5 register, is broadcast but does not belong here. Omit it to receive the calldata.
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 register only. One `{ walletAddress, claimType, signature }` per message from a `SIGN_MESSAGES` answer, with `claimType` by name. See [On an ERC-3643 register](#on-an-erc-3643-register). On a T-REX 5 register each entry also carries `issuedAt`, exactly as its message gave it.
</ParamField>

## The two calls

Without `txResults` the response is `SIGN_TRANSACTIONS`. Broadcast the steps, then send the same body again with `txResults`.

On the instance ID register there is one step, `stepType: ADD_CLAIM`, an `attest` call on the identity hub built from the attestation the manifest describes (`source: attestation_from_manifest`). It lists every claim it writes in `claims` and carries `predicates`, `predicateNames`, `investorClass`, `softExpiry`, `hardExpiry` and `attester`. Send it from that attester. Before handing out calldata, the API checks that one of your instance's registered wallets is a trusted attester, and refuses with `403 ATTESTER_MISSING` otherwise. See [Attesters and trust](/endpoints/customers/introduction#attesters-and-trust).

On a register of your own with the Trusset interface there is one `addClaim` step per derived claim, `KYC` first, each with its `claimType`, `dataHash` and `expiry`. Broadcast them from the attester the header names, which must hold `KYC_PROVIDER_ROLE` on that register. The API refuses with `KYC_PROVIDER_ROLE_MISSING` when none of your instance's registered wallets holds it. The register's owner grants the role.

Both role checks are skipped when the instance has no registered wallet or the role cannot be read.

The confirm leg checks the bundle again, then each receipt. On the instance ID register a receipt must be a mined, successful `attest` on the identity hub for this wallet, sent by the bundle's attester, carrying the bundle's root, its investor class and the predicates you filed. On your own Trusset-interface register it must be a mined, successful `addClaim` on that register for this wallet, writing the claim type and data hash derived from the bundle. A claim whose hash you omit comes back `skipped`; one that fails a check comes back `failed` with a reason; neither stops the others.

A confirmed claim writes a ledger row and an `ADD_CLAIM` audit entry, so [List Proofs](/endpoints/customers/list-proofs) labels it `source: proof`.

<Note>
  `success` is `false` when no claim was confirmed, with `NO_CLAIMS_ADDED`, even though the HTTP status is `200`. Read `added` against `total`.
</Note>

## On an ERC-3643 register

When the instance is bound to an ERC-3643 register, each claim is written to the subject's ONCHAINID. It must carry a signature from a CLAIM key on the register's trusted issuer, so the flow gains one round. The plan is built for the bundle's attester, so that wallet signs.

1. The first call answers `SIGN_MESSAGES`, with one entry in `messages` per claim. Sign each `messageHash` as an EIP-191 personal message with a wallet that holds a CLAIM key on `claimIssuer`.
2. Call again with `claimSignatures`. The answer is `SIGN_TRANSACTIONS`, with one `addClaim` step per claim addressed to the subject's ONCHAINID.
3. Broadcast the steps from the wallet the answer names in `signerAddress`, then confirm with `txResults` as above.

An ONCHAINID claim carries no expiry, so `expiry` is not written on chain. The role check becomes an agent check: one of your instance's wallets must be an agent of the register. The confirm leg checks that each transaction wrote to this wallet's ONCHAINID.

On a T-REX 5 register (`trexVersion: 5`) the messages carry `scheme: eip712`, `typedData` and `issuedAt`. Sign each `typedData` as EIP-712 typed data with a CLAIM_SIGNER key on `claimIssuer`, and send `issuedAt` back with each signature. The steps are then one `addClaimTo` per claim, addressed to the trusted issuer identity and sent by a MANAGEMENT key of it, which each step names in `signer`. A wallet with no ONCHAINID on the register's identity factory yet is refused with `NOT_REGISTERED`.

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_CLAIM_SIGNATURE` | `400` | A signature is not 65-byte hex, or does not recover for this identity, topic and data |
| `REGISTRY_AGENT_MISSING` | `403` | None of your instance's wallets is an agent of the register |
| `CLAIM_SIGNER_MISSING` | `403` | None of your instance's wallets holds a CLAIM key on the register's trusted issuer |
| `CLAIM_SIGNER_NOT_TRUSTED` | `403` | The attester, or the wallet a signature recovers to, holds no CLAIM key on the trusted issuer |
| `CLAIM_MANAGER_MISSING` | `403` | T-REX 5: none of your instance's wallets holds a MANAGEMENT key on the trusted issuer identity |
| `SIGNER_ROLE_MISSING` | `403` | T-REX 5: the signing wallet lacks the key this answer needs. The message names the wallets that hold it |
| `NOT_REGISTERED` | `409` | T-REX 5: the wallet has no ONCHAINID on the register's identity factory yet |
| `CLAIM_NOT_VALID` | `409` | T-REX 5: the trusted issuer does not accept a signed claim. Sign it again |
| `REGISTRY_NO_CLAIM_TOPICS` | `409` | The register requires no claim topics, so there is nothing to file |
| `REGISTRY_NO_TRUSTED_ISSUER` | `409` | The register names no trusted issuer for its claim topic |
| `REGISTRY_PROBE_FAILED` | `503` | The register or its trusted issuer could not be read |

## Verification failures

Every code below means the bundle was rejected and nothing was written on chain. Failures found before the wallet check are never stored: refusals of proof bytes and personal data, size, shape, version, header and stub failures, and an empty selection. Every other verdict, pass or fail, is stored on a verification report.

| Code | HTTP | What failed |
|---|---|---|
| `PROOFS_NOT_ACCEPTED` | `400` | The body carries `proofs`, `proof`, `proofBytes` or `zk`. Verify the proofs locally and send the manifest and its signed header only |
| `PERSONAL_DATA_IN_MANIFEST` | `400` | The manifest's `passthrough` carries `country`, `investorType` or any key besides the two expiry days. Re-issue the bundle with tool 3.1 |
| `INVALID_MANIFEST` | `400` | The manifest is malformed, has keys or values outside the 3.1.0 format, has no `chain` block, has no single `INVESTOR_CLASS` leaf, or its `epochDays` is missing or in the future. Also when the attestation derived from it does not match the header |
| `UNSUPPORTED_VERSION` | `400` | The manifest version, STARK library or security level is not one this verifier accepts |
| `UNSUPPORTED_CIRCUIT` | `400` | A leaf names a circuit this verifier does not know |
| `STUB_NOT_ALLOWED` | `400` | A `stub` bundle was sent to a production instance, or to a development instance on which proof verification is enforced |
| `HEADER_REQUIRED` | `400` | `header` or `headerSignature` is missing |
| `INVALID_HEADER` | `400` | The header is malformed or not version `3.1.0`, or a header was sent with a pre-3.1 manifest |
| `INVALID_HEADER_SIGNATURE` | `400` | `headerSignature` is not `0x` and 128 lowercase hex, or does not verify under the operator key |
| `HEADER_MISMATCH` | `400` | The header's root, wallet, date, leaf count, Merkle version, attester, chain, hub or key id differ from the manifest |
| `WALLET_MISMATCH` | `400` | The bundle was built for a different wallet |
| `NO_SELECTED_CLAIMS` | `400` | Nothing in `selected` is backed by this bundle |
| `HASH_MISMATCH` | `400` | The bundle's root is not the root the register holds for this wallet |
| `CHAIN_MISMATCH` | `400` | The header names a chain your instance does not write to |
| `HUB_MISMATCH` | `400` | The header names an identity hub your instance does not use |
| `ATTESTER_NOT_TRUSTED` | `403` | The header's attester is not a trusted attester of your instance ID register, or on a register of your own not a verified wallet of your instance |
| `ATTESTER_MISMATCH` | `400` | `signerAddress` is not the attester the header names |
| `OPERATOR_KEY_UNKNOWN` | `400` | The hub publishes keys for this attester but none under the header's key id. Sign the header with a key the hub publishes |
| `UNREGISTERED_OPERATOR_KEY` | `400` | The hub holds no operator key for this attester and none is registered on this instance |
| `PROOF_STALE` | `400` | The batch date is older than the instance's staleness bound |
| `LEAF_INVALID` | `400` | A leaf's public digest does not recompute, its parameters, list version or predicate do not fit its circuit, or its proof digest is empty where a proof is required |
| `LEAF_HASH_MISMATCH` | `400` | A leaf hash, or a leaf's binding digest, does not recompute from its own fields |
| `ROOT_MISMATCH` | `400` | The leaves do not recompute to the root the header signs |
| `NOT_ATTESTABLE` | `400` | A leaf you file, or the class leaf, carries no predicate |
| `UNAPPROVED_PARAMS` | `400` | A leaf's predicate parameters are outside the network's trust anchors |
| `UNAPPROVED_LIST` | `400` | A leaf's list root, depth or list content is not one this network accepts |
| `LEAF_LAPSED` | `400` | A leaf you file, or the class leaf, is outside its validity window. Re-issue the bundle |
| `PROOF_TOO_LARGE` | `413` | The manifest is over 64 KiB |
| `TOO_MANY_LEAVES` | `413` | The bundle carries more than 32 leaves |

BUNDLE=output/0xabCDeF0123456789AbcdEf0123456789aBCDEF01

curl -X POST "https://api.trusset.org/customers/api/identity/claims/from-proof" \

  -H "Content-Type: application/json" \
  -d "{
    \"walletAddress\": \"0xabCDeF0123456789AbcdEf0123456789aBCDEF01\",
    \"manifest\": $(cat "$BUNDLE/manifest.json"),
    \"header\": $(cat "$BUNDLE/header.json"),
    \"headerSignature\": \"0x$(xxd -p -c 64 "$BUNDLE/header.sig")\",
    \"selected\": [\"KYC\", \"RESIDENCY\", \"ADULT\"]

```typescript TypeScript
import { readFile } from 'node:fs/promises';

const bundle = 'output/0xabCDeF0123456789AbcdEf0123456789aBCDEF01';
const manifest = JSON.parse(await readFile(`${bundle}/manifest.json`, 'utf8'));
const header = JSON.parse(await readFile(`${bundle}/header.json`, 'utf8'));
const headerSignature = '0x' + (await readFile(`${bundle}/header.sig`)).toString('hex');
const walletAddress = manifest.walletAddress;
const selected = ['KYC', 'RESIDENCY', 'ADULT'];

const url = 'https://api.trusset.org/customers/api/identity/claims/from-proof';
const headers = { 'X-API-Key': 'trusset_your_key_here', 'Content-Type': 'application/json' };
const body = { walletAddress, manifest, header, headerSignature, selected };

const built = await fetch(url, { method: 'POST', headers, body: JSON.stringify(body) }).then(r => r.json());

const txResults = [];
for (const step of built.data.steps) {
  const tx = await signer.sendTransaction(step.transaction);
  await tx.wait();
  if (step.stepType !== 'ADD_CLAIM') continue;
  const claimTypes = step.registerKind === 'INSTANCE'
    ? step.claims.map((claim: { claimType: string }) => claim.claimType)
    : [step.claimType];
  for (const claimType of claimTypes) txResults.push({ claimType, txHash: tx.hash });
}

const confirmed = await fetch(url, {
  method: 'POST',
  headers,
  body: JSON.stringify({ ...body, txResults })
}).then(r => r.json());

console.log(`${confirmed.data.added} of ${confirmed.data.total} claims filed`);
```
</RequestExample>
