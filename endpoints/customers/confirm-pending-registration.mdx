---
title: 'Confirm Pending Registration'
api: 'POST /customers/api/identity/pending/confirm'
description: 'Check the signed registration and mark the queued approvals verified'
---

Checks the transactions your wallets broadcast for a set of queued rows, then closes every row whose wallet the transaction put on your register. A confirmed row marks its customer `verified`, and creates the customer record when there is none.

This confirms the issuer path, where your wallet sent the batch. A customer who submits their own claim on the [instance ID register](/endpoints/customers/introduction#the-instance-id-register) is confirmed with [Confirm Holder Claim](/endpoints/customers/confirm-holder-claim) instead. See [Holder claims](/endpoints/customers/introduction#holder-claims).

<Warning>
  On the instance ID register each row confirms when the mined attestation for its wallet carries the row's `kycHash` as its root and every predicate the row was built with. A row whose attestation differs comes back `NOT_REGISTERED_ON_CHAIN`, stays queued, and its `error` says what differed. Build it again and sign the new batch.

  On a register of your own with the Trusset interface, [Build Pending Registration](/endpoints/customers/build-pending-registration) puts a wallet that already holds an active identity into its own `updateIdentity` step, so the queued hash, investor type and expiries replace what the register held. Send each of those as `updateTxResults`. The batch still skips a row whose expiry has passed and any entry it runs out of gas for.

  A batch built there before a wallet's identity became active can still skip it. Such a wallet that the register reports as verified confirms anyway: its row closes, the register keeps the hash, investor type and expiries it held, and the customer record takes that hash. `investorTypeMismatch` flags a different investor type, but nothing in the response flags a different hash or expiry. Build the row again instead, so it is renewed.

  Any other skipped row comes back `NOT_REGISTERED_ON_CHAIN` and stays queued. A row skipped for gas, or one whose identity has since become active, can be built again. A row whose own expiry has passed is skipped again every time, and a frozen wallet stays `NOT_REGISTERED_ON_CHAIN` until it is unfrozen.

  To put a skipped approval on the register, use [Verify Identity](/endpoints/customers/verify-identity) with the row's `kycHash`. It verifies the wallet or updates the identity it already holds, and closes the row if it is still queued.
</Warning>

## Body Parameters

<ParamField body="ids" type="array" required>
  1 to 200 row ids, normally `ids` from the build. Only rows still `PENDING` on your instance are checked, and any other id is dropped without an error.
</ParamField>

<ParamField body="txHash" type="string">
  The registering transaction. On the instance ID register it is the `attestBatch`, or an `attest`, on the identity hub. On a register of your own with the Trusset interface it is the batch, or a `verifyIdentity` or `updateIdentity` call. On both it is required unless every row is confirmed through `updateTxResults`. On an ERC-3643 register it is the `registerIdentity` or `batchRegisterIdentity` step. Omit it there when every wallet was already registered.
</ParamField>

<ParamField body="updateTxResults" type="array">
  Register of your own with the Trusset interface. The renewal steps you broadcast, as `[{ id, txHash }]` with the row `id` each `updateIdentity` step carried. Each must be a mined, successful `updateIdentity` for the row's wallet, carrying the row's queued `kycHash`, or the whole call fails with `TX_ENTRIES_MISMATCH`. A confirmed renewal also writes the row's investor type name to the customer record, and its history entry carries `operation: update`. The build for the instance ID register has no renewal steps.
</ParamField>

<ParamField body="claimTxResults" type="array">
  Not used on the instance ID register, where the batch carries the residency predicate.

  The claim steps you broadcast, as `[{ id, txHash }]` with the row `id` each step carried. Entries are kept per `id`, so for a row with two claim steps only the last entry sent is checked. A claim that fails its check is left out of the record and fails nothing else.
</ParamField>

## What the confirm checks

| Check | Instance ID register | Your own Trusset-interface register | ERC-3643 register |
|---|---|---|---|
| `txHash` | Required. A mined, successful `attestBatch` or `attest` on the identity hub | Required. A mined, successful `batchVerifyIdentities`, `verifyIdentity` or `updateIdentity` call to your register | Optional. A mined, successful `registerIdentity`, `batchRegisterIdentity`, `updateCountry` or `updateIdentity` call to your register. Without it, `claimTxResults` is required |
| Signer of `txHash` | A wallet your register trusts as an attester, or the call fails with `403 UNTRUSTED_ATTESTER` | Logged, not enforced | Logged, not enforced |
| Coverage | Every selected wallet must be named by `txHash`, or the call fails with `TX_ENTRIES_MISMATCH` | Every selected wallet must be named by `txHash` or renewed by its entry in `updateTxResults`, or the call fails with `TX_ENTRIES_MISMATCH` | Not checked |
| `claimTxResults` | Not read | Read only for rows with a `residencyClaim`. Recorded when the receipt is an `addClaim` on your register for the row's wallet, carrying the queued residency hash | Recorded when the receipt is an `addClaim` on the wallet's ONCHAINID |
| A row confirms when | The mined attestation carries the row's `kycHash` and predicates | The transaction verified or updated the wallet, or the register reports it verified | The register's `isVerified` answers `true` for the wallet, whatever transactions put it there |

A failed check of `txHash` refuses the whole call before any row changes. The per-row outcome comes back in `results`, and one row's outcome does not affect another's.

## What a confirmed row changes

- The row turns `CONFIRMED`, with the transaction, its signer and the time.
- The customer record with this wallet becomes `verified`, with the `kycHash` the register holds and the transaction. On the instance ID register the row also records the mined `predicates`. Without a record, one is created from the row's metadata. On an ERC-3643 register the record also gets `metadata.onchainId`.
- The customer audit log gets `ON_CHAIN_VERIFIED`, with the queued and the registered hash.
- A hosted verification checkout behind the row turns `VERIFIED`, and stock escrow deposits waiting on its ID link are bound to the wallet.
- When the ID link or checkout behind the row still holds an email address, the customer is emailed that verification is complete.
- When the verification profile the row was queued under has an eligibility register, the wallet's admission to it is queued for your wallet to sign. See [Eligibility registers](/endpoints/customers/introduction#eligibility-registers).

The customer write is best effort. A failure there is logged, and the row still confirms.

A row that does not confirm stays `PENDING`, and its `error` says why. Build and confirm it again once the cause is fixed. A repeat call for rows that all confirmed answers `NOT_FOUND`, because none of them is `PENDING` any more.

<Note>
  The HTTP status is `200` and `success` is `true` even when no row confirmed. Read `confirmed` and each entry of `results`.
</Note>

## Response Fields

<ResponseField name="data" type="object">
  <Expandable>
    <ResponseField name="confirmed" type="integer">Rows that confirmed.</ResponseField>
    <ResponseField name="notRegistered" type="integer">Rows that did not, for either reason in `results`.</ResponseField>
    <ResponseField name="txHash" type="string">The checked `txHash`, or `null` on an ERC-3643 register when none was sent.</ResponseField>
    <ResponseField name="signedBy" type="string">The wallet that signed it, or `null`.</ResponseField>
    <ResponseField name="registerKind" type="string">`INSTANCE` on the instance ID register, `TREX` on an ERC-3643 register. Absent on a register of your own with the Trusset interface.</ResponseField>
    <ResponseField name="results" type="array">One entry per row checked. See below.</ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="results" type="array">
  <Expandable>
    <ResponseField name="id" type="string">The row.</ResponseField>
    <ResponseField name="walletAddress" type="string">Its wallet, lowercased.</ResponseField>
    <ResponseField name="status" type="string">`CONFIRMED`; `NOT_REGISTERED_ON_CHAIN` when the register does not report the wallet as verified, or on the instance ID register when the mined attestation differs from the row; `CHAIN_READ_UNAVAILABLE` when the register could not be read, which says nothing about the wallet. Both of the latter leave the row queued.</ResponseField>
    <ResponseField name="txHash" type="string">The transaction recorded for the row. On an ERC-3643 register without `txHash`, its claim transaction.</ResponseField>
    <ResponseField name="operation" type="string">`verify`, or `update` for a renewal. Not on an ERC-3643 register. `CONFIRMED` only.</ResponseField>
    <ResponseField name="claimTxHash" type="string">The claim transaction that passed its check, or `null`. Always `null` on the instance ID register. `CONFIRMED` only.</ResponseField>
    <ResponseField name="predicates" type="string">Instance ID register only. The predicates the mined attestation carries, as a decimal string. `CONFIRMED` only.</ResponseField>
    <ResponseField name="investorTypeMismatch" type="boolean">Not on an ERC-3643 register. Present and `true` when the register holds a different investor type than the row queued. The row still confirms.</ResponseField>
    <ResponseField name="onchainId" type="string">ERC-3643 register only. The wallet's ONCHAINID. `CONFIRMED` only.</ResponseField>
  </Expandable>
</ResponseField>

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `VALIDATION_ERROR` | `400` | `ids` is not an array of 1 to 200 ids, on the instance ID register or your own Trusset-interface register neither `txHash` nor `updateTxResults` was sent, or on an ERC-3643 register neither `txHash` nor `claimTxResults` was sent |
| `INVALID_TX` | `400` | `txHash` is not a 32-byte hex hash |
| `TX_REVERTED` | `400` | The transaction reverted |
| `TX_WRONG_TARGET` | `400` | Instance ID register: the transaction was not sent to the identity hub. Your own Trusset-interface register: it was not sent to your register. ERC-3643 register: it created a contract |
| `TX_WRONG_FUNCTION` | `400` | The transaction calls a function this confirm does not accept |
| `TX_TARGET_MISMATCH` | `400` | ERC-3643 register: `txHash` is a claim transaction. Send it in `claimTxResults` |
| `TX_ENTRIES_MISMATCH` | `400` | The transactions do not cover every selected wallet, or a renewal renews a different wallet or carries a different hash than its row queued. Not on an ERC-3643 register |
| `UNTRUSTED_ATTESTER` | `403` | Instance ID register: the transaction was sent by a wallet your register does not trust as an attester. The rows stay queued. Trust that wallet, then confirm the same `txHash` again |
| `NOT_FOUND` | `404` | None of the `ids` is a `PENDING` row of your instance, or the instance no longer exists |
| `TX_NOT_FOUND` | `404` | The transaction is not mined yet, or does not exist |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance has no instance ID register yet |
| `OWN_REGISTRY_NOT_CONFIGURED` | `409` | Your instance is set to its own register but holds no valid register address |
| `CHAIN_UNAVAILABLE` | `503` | ERC-3643 register: the transaction could not be read. Retry shortly |
| `REGISTRY_PROBE_FAILED` | `503` | The register could not be read to tell its interface. Retry shortly |
| `IDENTITY_HUB_NOT_CONFIGURED` | `501` | The identity hub is not deployed on your instance's network |
| `PENDING_CONFIRM_FAILED` | `400` | A chain read failed, including a transaction that could not be read outside an ERC-3643 register |
| `PENDING_CONFIRM_FAILED` | `500` | Any other failure |
