---
title: 'List Verification Profiles'
api: 'GET /customers/api/verification-profiles'
description: 'The verification levels configured for your instance'
---

Returns the verification profiles your instance runs. A profile ties a verification level to the investor type it results in, the documents it requires, the countries it refuses, and who it admits: individuals or companies, and whether only professional clients.

That lets a hosted [ID Link](/endpoints/customers/create-id-link) be issued against a named level rather than an ad-hoc set of requirements.

## Who a profile admits

`entityType` decides which applicant the identity check runs for. An [ID link](/endpoints/customers/create-id-link) under a `COMPANY` profile creates a company applicant, and a review of the other kind of applicant is refused. A wallet is admitted to the profile's eligibility register only when the customer record holding it has the same `customerType`.

`professionalOnly` matters to lending. A market that prices its collateral from a live market price (`MARKET`) lends to professional borrowers only, so its borrower gate must be a register admitted to only by profiles with `professionalOnly: true` in the `REGISTER` mode, at least one of them. Profiles of other instances bound to the same register count too, and a profile in the `EXTERNAL` mode does not. See [Set Identity Gates](/endpoints/lending/set-identity-gates#professional-borrowers).

`reverifyDays` limits how long an admission lasts. Once that many days have passed since a wallet was admitted or its customer was last verified, the admission lapses and its removal from the register is queued. An ID link under the profile also queues its on-chain registration with a hard expiry of `reverifyDays`, and a soft expiry of 180 days or `reverifyDays`, whichever is shorter.

## Eligibility registers

A profile with an eligibility register is what lending markets and vaults can gate on. The register is an on-chain identity register that holds exactly the wallets admitted under the profile, so a gate that reads it admits the customers of that profile and nobody else.

Name the profile by its key wherever a market or vault takes a register: `identityRegistryProfile` and `providerRegistryProfile` on [Deploy Market](/endpoints/lending/deploy-market) and [Accept Lender Role](/endpoints/operators/accept-lender-role), and `borrowerProfile` and `providerProfile` on [Set Identity Gates](/endpoints/lending/set-identity-gates). [Get Deployment Options](/endpoints/lending/get-deployment-options) lists the profiles that have one.

A register is deployed for a profile, or an existing one bound to it, in the Issuer Portal. One register stands for one profile of your instance, and a profile limited to professional clients takes only a register in the `REGISTER` mode. Who is on it is managed through [Eligibility registers](/endpoints/customers/introduction#eligibility-registers).

## Requirements hash

`requirementsHash` is keccak256 of a canonical JSON of what the profile requires: its `key`, `entityType`, `professionalOnly`, `onChainInvestorType`, `sumsubLevelName`, the document sets with their accepted types and whether each is required, `blockedCountries` and `reverifyDays`. The name, the description, `enabled` and the field labels are not part of it.

Every admission records the hash it was requested under. An admission whose hash differs from the profile's current one was made under requirements that have changed since, and [List Admissions](/endpoints/customers/list-admissions) reports it with `current: false`.

## Blocked countries

A customer from a country on `blockedCountries` is refused with `403 COUNTRY_BLOCKED` wherever the profile applies. That covers ID links and customer records that name it, the pending verification queue, and admissions to the profile's eligibility register.

[Verify Identity](/endpoints/customers/verify-identity) and [Batch Verify](/endpoints/customers/batch-verify) check the profile whose key matches the request's `investorType`, preset or custom.

Changing a profile's list in the Issuer Portal also queues the removal of every wallet on its eligibility register whose customer's country the new list blocks.

<RequestExample>
```bash cURL
curl "https://api.trusset.org/customers/api/verification-profiles" \
  -H "X-API-Key: trusset_your_key_here"
```
```typescript TypeScript
const response = await fetch('https://api.trusset.org/customers/api/verification-profiles', {
  headers: { 'X-API-Key': 'trusset_your_key_here' }
});
const { data: profiles } = await response.json();

const professional = profiles.find((profile: { key: string }) => profile.key === 'PROFESSIONAL');
const gateable = profiles.filter(
  (profile: { eligibilityRegister: object | null }) => profile.eligibilityRegister !== null
);
```
</RequestExample>
