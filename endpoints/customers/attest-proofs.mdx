---
title: 'Attest Proofs'
api: 'POST /customers/api/identity/proofs'
description: 'File proof-backed claims and rotate the on-chain root when the bundle is newer'
---

Files claims from a bundle and, unlike [Add Claims from Proof](/endpoints/customers/add-claims-from-proof), can rotate the identity's on-chain root to this bundle's root in the same flow. Use it when re-proving a subject against a new batch, where the root on the registry is the old one.

It also records a ledger row per confirmed claim, so [List Proofs](/endpoints/customers/list-proofs) can later say which proof backs which slot.

<Warning>
  The registry keeps one claim per slot. Filing a slot replaces the claim already there, whoever wrote it.

  A root rotation rewrites the identity record, not only its root. [Root rotation](#root-rotation) lists what it keeps and what it resets.
</Warning>

<Note>
  This endpoint, [Inspect Manifest](/endpoints/customers/inspect-manifest) and Add Claims from Proof share one rate limit per instance: 30 requests in a 60-second window, both legs counted. Past it, they answer `429 RATE_LIMITED` with a `Retry-After` header in seconds.
</Note>

## Body Parameters

<ParamField body="walletAddress" type="string" required>
  The subject. Must already be verified on chain and not revoked.
</ParamField>

<ParamField body="manifest" type="object" required>
  The bundle's `manifest.json`, parsed. At most 64 KiB serialized and 32 leaves.
</ParamField>

<ParamField body="manifestSig" type="string">
  The 64 raw bytes of `manifest.sig`, base64-encoded. Required whenever an operator key is registered, as on Add Claims from Proof.
</ParamField>

<ParamField body="proofs" type="object">
  A map of field name to base64 STARK bytes. Under enforcement, verification needs one for every leaf you file. The size caps are those of Add Claims from Proof.
</ParamField>

<ParamField body="entries" type="array" required>
  Which leaves to file and where, 1 to 8 entries. Each names a `fieldName` from the manifest, optionally a `claimType` slot by name, and optionally `expiryDays` for that claim alone.

  A canonical field always files under its own slot. `country` files as `RESIDENCY`, `nationality` as `CITIZENSHIP` and `investorType` as `ACCREDITATION`, and naming another slot is refused with `SLOT_LOCKED`. A leaf with no canonical meaning has no default slot, so it needs an entry naming one of `AML`, `TAX_RESIDENCY`, `SANCTIONS_CHECK` or `PEP_CHECK`.

  `expiryDays` runs from 0 to 36500, where `0` means no expiry. Omitted, the claim inherits the identity's hard expiry when that is in the future, and the rotated one when the root rotates.
</ParamField>

<ParamField body="rootTxHash" type="string">
  The hash of the mined transaction that registered this bundle's root on the identity. Required on the confirm leg when the bundle's root differs from what the registry holds.
</ParamField>

<ParamField body="txResults" type="array">
  Send this to confirm. An array of `{ fieldName, txHash }`, one per claim you broadcast.
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 register only. One `{ claimType, signature }` per message from a `SIGN_MESSAGES` answer, with `claimType` by name. `walletAddress` is optional and defaults to the subject.
</ParamField>

<ParamField body="signerAddress" type="string">
  ERC-3643 register only. The instance wallet that signs the claims. It must hold a CLAIM key on the register's trusted issuer.
</ParamField>

## Root rotation

The registry holds one root per identity. A bundle proved in a later batch has a different root, and its leaves cannot be checked against the old one.

When the bundle's root differs from the chain's, the calldata leg returns the root-rotation transaction as the first step and the claim transactions after it. Broadcast the rotation first, then pass its hash back as `rootTxHash` alongside `txResults`.

On the Trusset register the rotation is `updateIdentity`, which rewrites the whole identity record:

- The investor type stays as it is, or comes from the bundle's `passthrough.investorType` when the record has none, and defaults to `RETAIL`.
- The expiries become the bundle's `softExpiryDays` and `hardExpiryDays` counted from now. Where the bundle states none, the current expiry is kept.
- The signing wallet becomes the identity's KYC provider.

An identity whose kept expiry has already passed is refused with `IDENTITY_EXPIRED` and must be re-verified instead. A bundle whose soft expiry is not earlier than its hard expiry is refused with `INVALID_EXPIRY`.

Confirming without `rootTxHash` is refused with `ROOT_ROTATION_REQUIRED`. The rotation receipt must be a mined `updateIdentity` or `verifyIdentity` on this instance's register. It must target this wallet (`TX_TARGET_MISMATCH`) and register this bundle's root (`TX_ROOT_MISMATCH`). A rotation signed by a wallet outside your instance is logged but not refused. Once it is confirmed, the customer record takes the new root.

## Sign and confirm

Before handing out calldata, the API checks that one of your instance's registered wallets holds `KYC_PROVIDER_ROLE` on the register, which `addClaim` and `updateIdentity` both require. It refuses with `KYC_PROVIDER_ROLE_MISSING` otherwise, and skips the check when the instance has no registered wallet or the role cannot be read.

The confirm leg verifies the bundle again, then each claim receipt independently. A receipt must be a mined, successful `addClaim` on this instance's register for this wallet, writing the slot and data hash the server derived. It does not check who signed. A claim whose hash you omit comes back `skipped`, and one that fails a check comes back `failed` with a reason. Only a confirmed claim writes its ledger row and an `ADD_CLAIM` audit entry.

<Note>
  `success` is `false` with `NO_PROOFS_ADDED` when the confirm leg files nothing, on a `200`. Read `added` against `total`.
</Note>

## On an ERC-3643 register

When the instance is bound to an ERC-3643 register, each claim is written to the subject's ONCHAINID. It carries a signature from a CLAIM key on the register's trusted issuer, so the first call answers `SIGN_MESSAGES`. Sign each `messageHash` as an EIP-191 personal message and call again with `claimSignatures` to receive the transactions.

The rotation step is then a new `KYC` claim on the ONCHAINID carrying the bundle root, and it writes no investor type or expiry. Claims carry no expiry either. The role check becomes an agent check on the register, and `IDENTITY_REVOKED` also covers any identity the register does not count as verified. The ERC-3643 codes on [Add Claims from Proof](/endpoints/customers/add-claims-from-proof#on-an-erc-3643-register) apply here too.

## Error Codes

Every verification failure from [Add Claims from Proof](/endpoints/customers/add-claims-from-proof#verification-failures) applies here too, stored verdicts included, except `HASH_MISMATCH` and `NO_SELECTED_CLAIMS`. A root that differs from the chain's leads to a rotation instead. On top of those:

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `walletAddress` is missing or malformed |
| `MISSING_MANIFEST` | `400` | No manifest object in the body |
| `INVALID_PROOFS` | `400` | `proofs` is not a map of field name to base64 string |
| `NO_ENTRIES` | `400` | `entries` is missing or empty |
| `TOO_MANY_ENTRIES` | `400` | More than 8 entries |
| `INVALID_ENTRY` | `400` | An entry is not an object |
| `INVALID_FIELD` | `400` | An entry has no `fieldName`, or one over 128 characters |
| `FIELD_NOT_IN_MANIFEST` | `400` | An entry names a field the manifest does not carry |
| `INVALID_CLAIM_TYPE` | `400` | The named slot is not a claim type name |
| `SLOT_LOCKED` | `400` | A canonical field names a slot other than its own |
| `SLOT_REQUIRED` | `400` | A leaf with no canonical meaning was filed without naming a slot |
| `SLOT_RESERVED` | `400` | A leaf with no canonical meaning names one of the four canonical slots |
| `CIRCUIT_MISMATCH` | `400` | A canonical field was proved with the wrong circuit |
| `DUPLICATE_FIELD` | `400` | Two entries name the same field |
| `DUPLICATE_SLOT` | `400` | Two entries would occupy the same slot |
| `INVALID_EXPIRY` | `400` | An entry's `expiryDays` is outside 0 to 36500, or the bundle's soft expiry is not earlier than its hard expiry |
| `NOT_VERIFIED` | `400` | The subject carries no root on the registry |
| `IDENTITY_REVOKED` | `400` | The identity is revoked on chain. Re-verify before attaching proofs |
| `IDENTITY_EXPIRED` | `400` | A rotation would keep an expiry that has already passed. Re-verify the identity |
| `ROOT_ROTATION_REQUIRED` | `400` | Confirm leg: the bundle's root is not on chain and no `rootTxHash` was given |
| `INVALID_TX` | `400` | `rootTxHash` is not a 32-byte hex hash |
| `TX_REVERTED` | `400` | The rotation transaction reverted |
| `TX_WRONG_TARGET` | `400` | The rotation transaction was not sent to this instance's register |
| `TX_WRONG_FUNCTION` | `400` | The rotation transaction does not call `updateIdentity` or `verifyIdentity` |
| `TX_TARGET_MISMATCH` | `400` | The rotation transaction targets a different wallet |
| `TX_ROOT_MISMATCH` | `400` | The rotation transaction does not register this bundle's root |
| `NO_PROOFS_ADDED` | `200` | Confirm leg, nothing filed. `success` is `false` |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | None of your instance's wallets holds `KYC_PROVIDER_ROLE` on the register. Calldata leg only |
| `INSTANCE_NOT_FOUND` | `404` | The instance behind your key no longer exists |
| `TX_NOT_FOUND` | `404` | The rotation transaction is not mined yet |
| `RATE_LIMITED` | `429` | More than 30 proof requests from this instance in the current 60-second window |
| `CHAIN_UNAVAILABLE` | `503` | The registry could not be read |
| `ATTEST_PROOF_FAILED` | `400` or `500` | A chain call failed (`400`), or the request failed unexpectedly (`500`) |

<RequestExample>
```bash cURL
BUNDLE=output/0xabCDeF0123456789AbcdEf0123456789aBCDEF01

curl -X POST "https://api.trusset.org/customers/api/identity/proofs" \
  -H "X-API-Key: trusset_your_key_here" \
  -H "Content-Type: application/json" \
  -d "{
    \"walletAddress\": \"0xabCDeF0123456789AbcdEf0123456789aBCDEF01\",
    \"manifest\": $(cat "$BUNDLE/manifest.json"),
    \"manifestSig\": \"$(base64 < "$BUNDLE/manifest.sig" | tr -d '\n')\",
    \"proofs\": { \"country\": \"$(base64 < "$BUNDLE/proofs/country.bin" | tr -d '\n')\" },
    \"entries\": [{ \"fieldName\": \"country\" }]
  }"
```
```typescript TypeScript
import { readFile } from 'node:fs/promises';

const bundle = 'output/0xabCDeF0123456789AbcdEf0123456789aBCDEF01';
const manifest = JSON.parse(await readFile(`${bundle}/manifest.json`, 'utf8'));
const body = {
  walletAddress: manifest.walletAddress,
  manifest,
  manifestSig: (await readFile(`${bundle}/manifest.sig`)).toString('base64'),
  proofs: { country: (await readFile(`${bundle}/proofs/country.bin`)).toString('base64') },
  entries: [{ fieldName: 'country' }]
};

const url = 'https://api.trusset.org/customers/api/identity/proofs';
const headers = { 'X-API-Key': 'trusset_your_key_here', 'Content-Type': 'application/json' };

const built = await fetch(url, { method: 'POST', headers, body: JSON.stringify(body) }).then(r => r.json());

let rootTxHash: string | undefined;
const txResults = [];
for (const step of built.data.steps) {
  const tx = await signer.sendTransaction(step.transaction);
  await tx.wait();
  if (step.stepType === 'ROOT_ROTATION') rootTxHash = tx.hash;
  else txResults.push({ fieldName: step.fieldName, txHash: tx.hash });
}

const confirmed = await fetch(url, {
  method: 'POST',
  headers,
  body: JSON.stringify({ ...body, rootTxHash, txResults })
}).then(r => r.json());

console.log(`${confirmed.data.added} of ${confirmed.data.total} proofs attested`);
```
</RequestExample>
