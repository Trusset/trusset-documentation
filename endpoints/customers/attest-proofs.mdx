---
title: 'Attest Proofs'
api: 'POST /customers/api/identity/proofs'
description: 'File chosen leaves of a 3.1 proof bundle and rotate the on-chain root when the bundle is newer'
---

Files the leaves you choose from a [KYC-STARKs](/tools/kyc-starks/overview) 3.1 bundle and, unlike [Add Claims from Proof](/endpoints/customers/add-claims-from-proof), can rotate the identity's on-chain root to this bundle's root in the same flow. Use it when re-proving a subject against a new batch, where the root on the register is the old one.

It also records a ledger row per confirmed claim, so [List Proofs](/endpoints/customers/list-proofs) can later say which leaf backs which claim.

<Warning>
  Trusset never receives proof bytes. A 3.1 proof reveals the value it is about: an age proof the date of birth, a set-membership proof the country, a tier proof the investor class. Verify the proofs on your side with the tool or the SDK, then send the manifest and its signed header only. A body that carries `proofs`, `proof`, `proofBytes` or `zk` is refused with `400 PROOFS_NOT_ACCEPTED`, and a 2.x or 3.0 bundle with `400 PERSONAL_DATA_IN_MANIFEST`.
</Warning>

Trusset checks the header signature against the operator key the identity hub publishes for the header's attester, or against the key registered with [Set Operator Key](/endpoints/customers/set-operator-key) when the attester has published none. It checks every leaf, the root and the trust anchors as described on [What Trusset checks](/endpoints/customers/add-claims-from-proof#what-trusset-checks). The plan is built for the attester the header names, so that wallet signs it.

On the [instance ID register](/endpoints/customers/introduction#the-instance-id-register) each leaf proves a [predicate](/endpoints/customers/introduction#predicates), and the plan is one `attest` on the identity hub that writes them all. See [Which predicate a leaf proves](#which-predicate-a-leaf-proves). Nothing is verified on chain: the hub stores the root, the investor class and the predicate bits, and the leaf hashes stay in Trusset's proof ledger.

<Warning>
  On the instance ID register the `attest` writes the attestation the bundle describes: its root, investor class and expiries, `KYC_DONE` and the predicates of the leaves you file. From the attester's current attestation it keeps the attester statements (`AML_CLEAR`, `SANCTIONS_CLEAR`, `PEP_CLEAR`, `NOT_US_PERSON`, `CONTRACT_HOLDER`) and, when the root is the same, the bundle's predicates it already carries. The hub stores the attestation under the wallet that sends it, so send the step from the attester the header names.

  On a register of your own with the Trusset interface (`registerKind: TRUSSET`) the register keeps one claim per slot, and filing a slot replaces the claim already there, whoever wrote it.

  A root rotation rewrites the identity record, not only its root. [Root rotation](#root-rotation) lists what it keeps and what it resets.
</Warning>

<Note>
  This endpoint, [Inspect Manifest](/endpoints/customers/inspect-manifest) and Add Claims from Proof share one rate limit per instance: 30 requests in a 60-second window, both legs counted. Past it, they answer `429 RATE_LIMITED` with a `Retry-After` header in seconds.
</Note>

## Body Parameters

<ParamField body="walletAddress" type="string" required>
  The subject. Must already be verified on chain and not revoked.
</ParamField>

<ParamField body="manifest" type="object" required>
  The bundle's `manifest.json`, parsed, version `3.1.0`. At most 64 KiB serialized and 32 leaves.
</ParamField>

<ParamField body="header" type="object" required>
  The bundle's `header.json`, parsed.
</ParamField>

<ParamField body="headerSignature" type="string" required>
  The bundle's `header.sig` as `0x` followed by 128 lowercase hex characters.
</ParamField>

<ParamField body="entries" type="array" required>
  Which leaves to file, 1 to 8 entries. Each names a `fieldName` from the manifest, optionally a `claimType` slot by name, and optionally `expiryDays` for that claim alone. A leaf with no `binding.predicate` is refused with `NOT_ATTESTABLE`.

  On the instance ID register the leaf's predicate decides the claim and `claimType` is ignored. The `INVESTOR_CLASS` leaf is refused with `NOT_ATTESTABLE`: it sets the attestation's investor class and is not a predicate of its own.

  On a register of your own a leaf whose predicate has a slot always files under it, and naming another slot is refused with `SLOT_LOCKED`. An `ADULT` leaf has no slot of its own, so its entry names one of `AML`, `TAX_RESIDENCY`, `SANCTIONS_CHECK` or `PEP_CHECK`.

  `expiryDays` runs from 0 to 36500, where `0` means no expiry. Omitted, the claim inherits the identity's hard expiry when that is in the future, and the rotated one when the root rotates. On the instance ID register the expiries come from the bundle, and a value here only adds an `EXPIRY_FROM_BUNDLE` warning.
</ParamField>

<ParamField body="rootTxHash" type="string">
  Register of your own only. The hash of the mined transaction that registered this bundle's root on the identity. Required on the confirm leg when the bundle's root differs from what the register holds.
</ParamField>

<ParamField body="txResults" type="array">
  Send this to confirm. An array of `{ fieldName, txHash }`, one per claim you broadcast. On the instance ID register one transaction writes every claim, rotation included, so its hash is read for every entry. A field you leave out comes back `skipped`, unless a rotation was confirmed with `rootTxHash`, which then counts for it. Send at least one entry: a body without `txResults` is read as a calldata request.
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 register only. One `{ claimType, signature }` per message from a `SIGN_MESSAGES` answer, with `claimType` by name. `walletAddress` is optional and defaults to the subject. On a T-REX 5 register each entry also carries `issuedAt`, exactly as its message gave it.
</ParamField>

<ParamField body="signerAddress" type="string">
  The wallet you will sign with. When sent, it must be the attester the header names, or the call answers `ATTESTER_MISMATCH`.
</ParamField>

## Which predicate a leaf proves

Each leaf of a 3.1 bundle names its predicate in `binding.predicate`, inside its leaf hash, so it cannot be relabelled. Trusset checks that the predicate fits the leaf:

| Leaf predicate | Leaf | Claim on the instance ID register | Slot on a register of your own |
|---|---|---|---|
| `ADULT` | `age_threshold`, `minAgeDays` at least 6570 | `ADULT` | One you name from the four manual slots |
| `EEA_RESIDENT` | `set_membership` on the `eea` list | `EEA_RESIDENT` | `RESIDENCY` |
| `RESIDENCY_ON_FILE` | `set_membership` on an approved list | `RESIDENCY` | `RESIDENCY` |
| `CITIZENSHIP_ON_FILE` | `set_membership` on an approved list | `CITIZENSHIP` | `CITIZENSHIP` |
| `TAX_RESIDENCY_ON_FILE` | `set_membership` on an approved list | `TAX_RESIDENCY` | `TAX_RESIDENCY` |
| `ACCREDITED` | `tier_threshold`, `minTier` at least 2 | `ACCREDITATION` | `ACCREDITATION` |
| `INVESTOR_CLASS` | `tier_threshold`, `minTier` is the subject's class | Not filed: sets the investor class | `ACCREDITATION` |

`KYC_DONE` is set on every attestation from a bundle. Two entries that file the same claim, such as an `EEA_RESIDENT` and a `RESIDENCY_ON_FILE` leaf on a register of your own, are refused with `DUPLICATE_SLOT`.

## Root rotation

A register holds one root per identity. A bundle proved in a later batch has a different root, and its leaves cannot be checked against the old one.

On the instance ID register the rotation is the whole plan: one `attest`, `stepType: ROOT_ROTATION`, that writes the attestation the new bundle describes:

- The root becomes the bundle's root.
- The investor class becomes the bundle's class.
- The soft and hard expiries become the bundle's.
- The predicates become `KYC_DONE` and those of the leaves you file, plus the attester statements the attester's current attestation carries. Predicates proved under the old root are not carried over.
- The hub records it under the wallet that sends it, with a new issue time.

Confirm with the transaction's hash in `txResults`. `rootTxHash` is not needed there.

On a register of your own with the Trusset interface the rotation is an `updateIdentity` step before one `addClaim` step per claim. It sets the investor type to the bundle's class and the expiries to the bundle's, keeps the current expiry where the bundle states none, and the signing wallet becomes the identity's KYC provider. Broadcast the rotation first, then pass its hash back as `rootTxHash` alongside `txResults`. Confirming without it is refused with `ROOT_ROTATION_REQUIRED`. The receipt must be a mined `updateIdentity` or `verifyIdentity` on your register that targets this wallet (`TX_TARGET_MISMATCH`) and registers this bundle's root (`TX_ROOT_MISMATCH`). A rotation the identity has since moved past, because its root on chain is now another one, is refused with `ROTATION_SUPERSEDED` and changes nothing, so a replayed confirm can never rewrite the customer's stored root to one the chain no longer holds. The root is read at the newest block the node has reached, on every register kind; when it cannot be read the confirm answers `503 CHAIN_UNAVAILABLE` and records nothing. A rotation signed by a wallet outside your instance is logged but not refused.

A bundle whose expiry has already passed is refused with `BUNDLE_EXPIRED`, and an identity whose kept expiry has already passed with `IDENTITY_EXPIRED`; re-verify it instead. A bundle whose soft expiry is not earlier than its hard expiry is refused with `INVALID_EXPIRY`. On the instance ID register a suspended attestation is refused with `409 IDENTITY_SUSPENDED`. Once a rotation is confirmed, the customer record takes the new root.

## Sign and confirm

Before handing out calldata, the API checks that one of your instance's registered wallets can sign the plan. On the instance ID register it must be a trusted attester of the register, or the call is refused with `403 ATTESTER_MISSING`. See [Attesters and trust](/endpoints/customers/introduction#attesters-and-trust). On your own Trusset-interface register it must hold `KYC_PROVIDER_ROLE`, which `addClaim` and `updateIdentity` both require, or the call is refused with `KYC_PROVIDER_ROLE_MISSING`; the register's owner grants that role. Both checks are skipped when the instance has no registered wallet or the role cannot be read.

The confirm leg checks the bundle again, then each claim receipt. On the instance ID register a receipt must be a mined, successful `attest` on the identity hub for this wallet, sent by the bundle's attester, carrying the bundle's root, its investor class and the predicates you filed. On your own Trusset-interface register it must be a mined, successful `addClaim` on that register for this wallet, writing the slot and data hash the server derived. A claim whose hash you omit comes back `skipped`, and one that fails a check comes back `failed` with a reason. Only a confirmed claim writes its ledger row and an `ADD_CLAIM` audit entry.

<Note>
  `success` is `false` with `NO_PROOFS_ADDED` when the confirm leg files nothing, on a `200`. Read `added` against `total`.
</Note>

## On an ERC-3643 register

When the instance is bound to an ERC-3643 register, each claim is written to the subject's ONCHAINID. It carries a signature from a CLAIM key on the register's trusted issuer, so the first call answers `SIGN_MESSAGES`. Sign each `messageHash` as an EIP-191 personal message and call again with `claimSignatures` to receive the transactions.

The rotation step is then a new `KYC` claim on the ONCHAINID carrying the bundle root, and it writes no investor type or expiry. Claims carry no expiry either. The role check becomes an agent check on the register, and `IDENTITY_REVOKED` also covers any identity the register does not count as verified. The ERC-3643 codes on [Add Claims from Proof](/endpoints/customers/add-claims-from-proof#on-an-erc-3643-register) apply here too.

On a T-REX 5 register the messages are EIP-712 typed data with an `issuedAt` to send back, and each claim is an `addClaimTo` step on the trusted issuer identity, sent by the MANAGEMENT key its `signer` names. A rotation there also adds a `rotateClaim` step, `revokeClaimByDigest` on the previous KYC claim, so the old root's signature can never be written back.

## Error Codes

Every verification failure from [Add Claims from Proof](/endpoints/customers/add-claims-from-proof#verification-failures) applies here too, stored verdicts included, except `HASH_MISMATCH` and `NO_SELECTED_CLAIMS`. A root that differs from the chain's leads to a rotation instead. On top of those:

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `walletAddress` is missing or malformed |
| `MISSING_MANIFEST` | `400` | No manifest object in the body |
| `NO_ENTRIES` | `400` | `entries` is missing or empty |
| `TOO_MANY_ENTRIES` | `400` | More than 8 entries |
| `INVALID_ENTRY` | `400` | An entry is not an object |
| `INVALID_FIELD` | `400` | An entry has no `fieldName`, or one over 128 characters |
| `FIELD_NOT_IN_MANIFEST` | `400` | An entry names a field the manifest does not carry |
| `NOT_ATTESTABLE` | `400` | A leaf carries no predicate, or on the instance ID register is the `INVESTOR_CLASS` leaf |
| `INVALID_CLAIM_TYPE` | `400` | Register of your own: the named slot is not a claim type name |
| `SLOT_LOCKED` | `400` | Register of your own: a leaf names a slot other than its predicate's |
| `SLOT_REQUIRED` | `400` | Register of your own: an `ADULT` leaf was filed without naming a slot |
| `SLOT_RESERVED` | `400` | Register of your own: an `ADULT` leaf names one of the reserved slots |
| `DUPLICATE_FIELD` | `400` | Two entries name the same field |
| `DUPLICATE_SLOT` | `400` | Two entries would file the same claim |
| `INVALID_EXPIRY` | `400` | An entry's `expiryDays` is outside 0 to 36500, or the bundle's soft expiry is not earlier than its hard expiry |
| `BUNDLE_EXPIRED` | `400` | A rotation would write a bundle expiry that has already passed. Re-issue the bundle |
| `NOT_VERIFIED` | `400` | The subject carries no root on the register |
| `IDENTITY_REVOKED` | `400` | The identity is revoked on chain. Re-verify before attaching proofs |
| `IDENTITY_EXPIRED` | `400` | A rotation would keep an expiry that has already passed. Re-verify the identity |
| `ROOT_ROTATION_REQUIRED` | `400` | Register of your own, confirm leg: the bundle's root is not on chain and no `rootTxHash` was given |
| `INVALID_TX` | `400` | `rootTxHash` is not a 32-byte hex hash |
| `TX_REVERTED` | `400` | The rotation transaction reverted |
| `TX_WRONG_TARGET` | `400` | The rotation transaction was not sent to your register |
| `TX_WRONG_FUNCTION` | `400` | The rotation transaction does not call `updateIdentity` or `verifyIdentity` |
| `TX_TARGET_MISMATCH` | `400` | The rotation transaction targets a different wallet |
| `TX_ROOT_MISMATCH` | `400` | The rotation transaction does not register this bundle's root |
| `ROTATION_SUPERSEDED` | `409` | The rotation transaction is mined, but the identity's root on chain has moved past it. Nothing was recorded. Attach proofs from a bundle with the current root, or rotate again |
| `NO_PROOFS_ADDED` | `200` | Confirm leg, nothing filed. `success` is `false` |
| `ATTESTER_MISSING` | `403` | Instance ID register: none of your instance's registered wallets is a trusted attester of the register. Calldata leg only |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | Your own Trusset-interface register: none of your instance's wallets holds `KYC_PROVIDER_ROLE` on it. Calldata leg only |
| `INSTANCE_NOT_FOUND` | `404` | The instance behind your key no longer exists |
| `TX_NOT_FOUND` | `404` | The rotation transaction is not mined yet |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance has no instance ID register yet. It is created in the issuer app, under Settings |
| `IDENTITY_SUSPENDED` | `409` | Instance ID register: the attestation is suspended. Calldata leg only |
| `RATE_LIMITED` | `429` | More than 30 proof requests from this instance in the current 60-second window |
| `IDENTITY_HUB_NOT_CONFIGURED` | `501` | The identity hub is not deployed on your instance's network |
| `CHAIN_BEHIND` | `503` | Confirm leg with a rotation: the chain node has not reached the block of the rotation transaction yet. Nothing was recorded. Retry in a moment |
| `CHAIN_UNAVAILABLE` | `503` | The register or the identity hub could not be read. On the confirm leg of a rotation this includes the identity's current root, which is read before anything is recorded |
| `ATTEST_PROOF_FAILED` | `400` or `500` | A chain call failed (`400`), or the request failed unexpectedly (`500`) |

```typescript TypeScript
import { readFile } from 'node:fs/promises';

const bundle = 'output/0xabCDeF0123456789AbcdEf0123456789aBCDEF01';
const manifest = JSON.parse(await readFile(`${bundle}/manifest.json`, 'utf8'));
const body = {
  walletAddress: manifest.walletAddress,
  manifest,
  header: JSON.parse(await readFile(`${bundle}/header.json`, 'utf8')),
  headerSignature: '0x' + (await readFile(`${bundle}/header.sig`)).toString('hex'),
  entries: [{ fieldName: 'country' }, { fieldName: 'dateOfBirth' }]
};

const url = 'https://api.trusset.org/customers/api/identity/proofs';
const headers = { 'X-API-Key': 'trusset_your_key_here', 'Content-Type': 'application/json' };

const built = await fetch(url, { method: 'POST', headers, body: JSON.stringify(body) }).then(r => r.json());

let rootTxHash: string | undefined;
const txResults = [];
for (const step of built.data.steps) {
  const tx = await signer.sendTransaction(step.transaction);
  await tx.wait();
  if (built.data.registerKind === 'INSTANCE') {
    for (const entry of body.entries) txResults.push({ fieldName: entry.fieldName, txHash: tx.hash });
  } else if (step.stepType === 'ROOT_ROTATION') {
    rootTxHash = tx.hash;
  } else if (step.stepType === 'ADD_CLAIM') {
    txResults.push({ fieldName: step.fieldName, txHash: tx.hash });
  }
}

const confirmed = await fetch(url, {
  method: 'POST',
  headers,
  body: JSON.stringify({ ...body, rootTxHash, txResults })
}).then(r => r.json());

console.log(`${confirmed.data.added} of ${confirmed.data.total} proofs attested`);
```
</RequestExample>
