---
title: 'Batch Verify Identities'
api: 'POST /customers/api/identity/batch-verify'
description: 'Register up to 500 wallets on the identity register in one registration'
---

Builds one registration for many wallets. Invalid entries are reported in `rejected` rather than failing the request. When every entry is rejected, the request fails with `NO_VALID_ENTRIES`.

<Warning>
  A record is written only for a wallet the mined transaction actually registered. On a Trusset register, the contract skips any wallet that already holds an unrevoked identity. It also skips an entry with a zero `kycHash` or an invalid expiry, and every entry it runs out of gas for. Skipped wallets come back in `onChainSkipped` on the confirm leg, with their records unchanged. Use [Verify Identity](/endpoints/customers/verify-identity) to update a wallet that is already registered.
</Warning>

Call once without `txHash`, sign what comes back, then send the same `entries` again with `txHash` added. What you sign depends on `registerKind`, as on [Verify Identity](/endpoints/customers/verify-identity).

## Body Parameters

<ParamField body="entries" type="array" required>
  The wallets to register. Minimum 1, maximum 500.
  <Expandable>
    <ParamField body="entries[].walletAddress" type="string" required>
      The wallet. Checksummed or lowercase. A second entry for the same wallet is rejected with `DUPLICATE_ADDRESS`.
    </ParamField>
    <ParamField body="entries[].country" type="string" required>
      ISO 3166-1 code as alpha-2, alpha-3 or numeric. Stored in alpha-3 form.
    </ParamField>
    <ParamField body="entries[].investorType" type="string" default="RETAIL">
      As on [Verify Identity](/endpoints/customers/verify-identity): `RETAIL`, `PROFESSIONAL` or `ELIGIBLE_COUNTERPARTY`, or the key of one of your custom verification profiles, in any letter case. Omitted, `null` or an empty string reads as `RETAIL`. Any other value, a number included, rejects the entry with `INVALID_INVESTOR_TYPE`.
    </ParamField>
    <ParamField body="entries[].softExpiryDays" type="integer">
      Days until soft expiry. Trusset register only.
    </ParamField>
    <ParamField body="entries[].hardExpiryDays" type="integer">
      Days until hard expiry. Trusset register only.
    </ParamField>
    <ParamField body="entries[].kycHash" type="string">
      The KYC hash to register, as 32-byte hex. Without it, the hash is derived from the wallet, the country and the current time, so it changes on every call. An entry takes no `kycData`.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 only. The signatures from the `SIGN_CLAIMS` phase, as `[{ walletAddress, signature }]`.
</ParamField>

<ParamField body="identities" type="object">
  ERC-3643 only. ONCHAINIDs you deployed with your own tooling, keyed by wallet.
</ParamField>

<ParamField body="signerAddress" type="string">
  ERC-3643 only. The wallet that will sign the claims. Refused with `CLAIM_SIGNER_NOT_TRUSTED` when it holds no claim key on the register's trusted issuer. It also becomes the management key of any ONCHAINID the plan deploys, so name a wallet registered to your instance.
</ParamField>

<ParamField body="txHash" type="string">
  The hash of the mined transaction. Send it with the same `entries` to confirm. On an ERC-3643 register, send the hash of `steps[confirmStepIndex]`. Omit it to receive the calldata or the next phase.
</ParamField>

  </Expandable>
  <Expandable title="Confirm leg">
    <ResponseField name="onChainSkipped" type="string[]">Accepted wallets the transaction did not register. Their records were not written.</ResponseField>
    <ResponseField name="txHash" type="string">The confirmed transaction.</ResponseField>
    <ResponseField name="gasUsed" type="string">Gas used.</ResponseField>
  </Expandable>
</ResponseField>

`rejected[].code` is one of `INVALID_ENTRY`, `INVALID_ADDRESS`, `MISSING_COUNTRY`, `INVALID_COUNTRY`, `INVALID_HASH`, `DUPLICATE_ADDRESS`, `INVALID_INVESTOR_TYPE` or `COUNTRY_BLOCKED`. An `INVALID_INVESTOR_TYPE` message lists the values your instance accepts. `COUNTRY_BLOCKED` checks the [verification profile](/endpoints/customers/list-verification-profiles) named after the entry's `investorType`.

## Verify on a Trusset register

Send `transaction` from a wallet that holds `KYC_PROVIDER_ROLE` on the register. The API refuses the calldata with `KYC_PROVIDER_ROLE_MISSING` when it can read that none of your instance's wallets holds the role.

The confirm leg refuses before writing anything when the transaction's wallets differ from the accepted entries (`TX_ENTRIES_MISMATCH`). It also refuses when a written entry's mined investor type differs from the request (`TX_INVESTOR_TYPE_MISMATCH`). On the Trusset ID Register, the transaction must be signed by one of your instance's verified wallets (`UNAUTHORIZED_SIGNER`). On your own register the signer is logged, not checked.

## Verify on an ERC-3643 register

The phases work as on [Verify Identity](/endpoints/customers/verify-identity), across every accepted entry:

| Phase | What you get |
|---|---|
| `DEPLOY_IDENTITY` | One deployment per wallet without an ONCHAINID. Confirm each with [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid), then call again |
| `SIGN_CLAIMS` | One `messages` entry per wallet. Sign each with a CLAIM key on `claimIssuer`, then call again with `claimSignatures` |
| `REGISTER` | One `claim` step per wallet, then one `verify` step (`registerIdentity` for one new wallet, `batchRegisterIdentity` with `walletAddresses` for several), then any `country` steps |

Send `entries` from the first response on every later call, so each wallet keeps its `kycHash`. The claim signatures cover those hashes.

The keys are the same as on Verify Identity. A CLAIM key on `claimIssuer` signs, and the ONCHAINID's management key sends each `claim` step. An agent of the register sends the `verify` and `country` steps. The API refuses up front with `REGISTRY_AGENT_MISSING` or `CLAIM_SIGNER_MISSING` when none of your instance's wallets qualifies. The ERC-3643 example sends everything from one `wallet` that is both, named as `signerAddress`.

<Warning>
  On an ERC-3643 register, batch only wallets that are new to the register. The confirm compares the wallets in the `verify` step with every accepted entry, and a wallet already on the register is left out of that step. The confirm then fails with `TX_ENTRIES_MISMATCH`, and a `claim` or `country` step cannot be confirmed here at all. Use [Verify Identity](/endpoints/customers/verify-identity) for wallets already on the register.
</Warning>

An ERC-3643 register stores no investor type and no expiry, so `TX_INVESTOR_TYPE_MISMATCH` never applies there. `onChainSkipped` lists the wallets whose KYC claim could not be read back after the transaction. Unlike Verify Identity, the batch confirm does not ask the register whether each wallet now counts as verified.

## Records

For every accepted wallet not in `onChainSkipped`, the confirm leg writes the customer record as `verified`, with the profile key the entry's `investorType` resolved to and the `kycHash` read from the chain. A new record takes the entry's country. An existing record keeps the country it already has. Any [pending verification](/endpoints/customers/list-pending-verifications) for those wallets is settled. When the profile an entry's `investorType` names has an eligibility register, the wallet's admission to it is queued for your wallet to sign. See [Eligibility registers](/endpoints/customers/introduction#eligibility-registers).

```typescript TypeScript ERC-3643
import { ethers } from 'ethers';

const base = 'https://api.trusset.org/customers/api/identity';
const headers = {
  'Content-Type': 'application/json',
  'X-API-Key': 'trusset_your_key_here'
};
const post = async (path: string, body: Record<string, unknown>) => {
  const res = await fetch(`${base}${path}`, { method: 'POST', headers, body: JSON.stringify(body) });
  const json = await res.json();
  if (!json.success) throw new Error(`${json.error.code}: ${json.error.message}`);
  return json.data;
};

const signerAddress = await wallet.getAddress();

let plan = await post('/batch-verify', {
  signerAddress,
  entries: [
    { walletAddress: '0xaBc123DEf456789012345678901234567890aBCD', country: 'DE', investorType: 'PROFESSIONAL' },
    { walletAddress: '0x1234567890AbcdEF1234567890aBcdef12345678', country: 'FR', investorType: 'RETAIL' }
  ]
});
const entries = plan.entries;

if (plan.phase === 'DEPLOY_IDENTITY') {
  for (const step of plan.steps) {
    const tx = await wallet.sendTransaction({ data: step.transaction.data });
    await tx.wait();
    await post('/onchainid/confirm', { walletAddress: step.walletAddress, txHash: tx.hash });
  }
  plan = await post('/batch-verify', { signerAddress, entries });
}

if (plan.phase === 'SIGN_CLAIMS') {
  const claimSignatures = [];
  for (const message of plan.messages) {
    const signature = await wallet.signMessage(ethers.utils.arrayify(message.messageHash));
    claimSignatures.push({ walletAddress: message.walletAddress, signature });
  }
  plan = await post('/batch-verify', { signerAddress, entries, claimSignatures });
}

const hashes: string[] = [];
for (const step of plan.steps) {
  const tx = await wallet.sendTransaction(step.transaction);
  await tx.wait();
  hashes.push(tx.hash);
}

const confirmed = await post('/batch-verify', { entries, txHash: hashes[plan.confirmStepIndex] });
```
</RequestExample>

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_INPUT` | `400` | `entries` is not an array of 1 to 500 items |
| `NO_VALID_ENTRIES` | `400` | Every entry was rejected. `data` still carries the counts and `rejected` |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | Trusset register: none of your instance's wallets holds `KYC_PROVIDER_ROLE` |
| `REGISTRY_AGENT_MISSING` | `403` | ERC-3643: none of your instance's wallets is an agent of the register |
| `CLAIM_SIGNER_MISSING` | `403` | ERC-3643: none of your instance's wallets holds a claim key on the trusted issuer |
| `CLAIM_SIGNER_NOT_TRUSTED` | `403` | ERC-3643: `signerAddress`, or the wallet a claim signature recovers to, holds no claim key on the trusted issuer |
| `INVALID_CLAIM_SIGNATURE` | `400` | ERC-3643: a claim signature is not 65-byte hex, or recovers to no signer |
| `REGISTRY_NO_CLAIM_TOPICS` | `409` | ERC-3643: the register requires no claim topic |
| `REGISTRY_NO_TRUSTED_ISSUER` | `409` | ERC-3643: the register names no trusted issuer for its claim topic |
| `ONCHAINID_AUTHORITY_UNKNOWN` | `409` | ERC-3643: a wallet has no ONCHAINID, and no identity on the register reveals the implementation to deploy |
| `OWN_REGISTRY_NOT_CONFIGURED` | `409` | The instance is bound to its own register but no valid register address is set |
| `REGISTRY_PROBE_FAILED` | `503` | Your own register could not be read to tell its kind, or the trusted issuer could not be read to check a claim signer |
| `INVALID_TX` | `400` | `txHash` is not 32-byte hex |
| `TX_NOT_FOUND` | `404` | The transaction is not mined yet |
| `TX_REVERTED` | `400` | The transaction reverted |
| `TX_WRONG_TARGET` | `400` | The transaction does not write to the register, or it deployed a contract |
| `TX_WRONG_FUNCTION` | `400` | The transaction calls a function this endpoint does not confirm |
| `TX_TARGET_MISMATCH` | `400` | ERC-3643: the hash is a `claim` step, which this endpoint cannot confirm |
| `UNAUTHORIZED_SIGNER` | `403` | Trusset ID Register: the transaction was not signed by one of your instance's verified wallets |
| `TX_ENTRIES_MISMATCH` | `400` | The transaction registers a different set of wallets than the accepted entries |
| `TX_INVESTOR_TYPE_MISMATCH` | `400` | Trusset register: a written entry's mined investor type differs from the request |
| `CHAIN_UNAVAILABLE` | `503` | ERC-3643: the transaction could not be read |
| `BATCH_VERIFY_FAILED` | `400`, `500` | Any other failure. `400` when a chain call or the transaction encoding failed |
