---
title: 'Batch Verify Identities'
api: 'POST /customers/api/identity/batch-verify'
description: 'Register up to 500 wallets on the identity register in one registration'
---

Builds one registration for many wallets. Invalid entries are reported in `rejected` rather than failing the request. When every entry is rejected, the request fails with `NO_VALID_ENTRIES`.

<Warning>
  A record is written only for a wallet the mined transaction actually registered. Skipped wallets come back in `onChainSkipped` on the confirm leg, with their records unchanged.

  On the instance ID register the batch is all or nothing: one invalid entry reverts the whole transaction. A wallet that already holds an attestation from the signing wallet is attested again with the new root, and the predicate bits that attestation carried before, such as `AML_CLEAR`, are not kept. Use [Verify Identity](/endpoints/customers/verify-identity) to update a wallet and keep its other bits.

  On a Trusset-compatible register of your own, the contract skips any wallet that already holds an unrevoked identity. It also skips an entry with a zero `kycHash` or an invalid expiry, and every entry it runs out of gas for. Use [Verify Identity](/endpoints/customers/verify-identity) to update a wallet that is already registered.
</Warning>

Call once without `txHash`, sign what comes back, then send the same `entries` again with `txHash` added. What you sign depends on `registerKind`, as on [Verify Identity](/endpoints/customers/verify-identity).

## Body Parameters

<ParamField body="entries" type="array" required>
  The wallets to register. Minimum 1, maximum 500.
  <Expandable>
    <ParamField body="entries[].walletAddress" type="string" required>
      The wallet. Checksummed or lowercase. A second entry for the same wallet is rejected with `DUPLICATE_ADDRESS`.
    </ParamField>
    <ParamField body="entries[].country" type="string" required>
      ISO 3166-1 code as alpha-2, alpha-3 or numeric. Stored on the customer record in alpha-3 form. On the instance ID register it never goes on chain: it only decides whether `EEA_RESIDENT` is set, as on [Verify Identity](/endpoints/customers/verify-identity).
    </ParamField>
    <ParamField body="entries[].investorType" type="string" default="RETAIL">
      As on [Verify Identity](/endpoints/customers/verify-identity): `RETAIL`, `PROFESSIONAL` or `ELIGIBLE_COUNTERPARTY`, or the key of one of your custom verification profiles, in any letter case. Omitted, `null` or an empty string reads as `RETAIL`. A disabled profile rejects the entry with `INVALID_INVESTOR_TYPE` on the build call unless the wallet's customer record is already under it. Any other value, a number included, rejects the entry with `INVALID_INVESTOR_TYPE`.
    </ParamField>
    <ParamField body="entries[].softExpiryDays" type="integer">
      Days until soft expiry. Not written to an ERC-3643 register.
    </ParamField>
    <ParamField body="entries[].hardExpiryDays" type="integer">
      Days until hard expiry. Not written to an ERC-3643 register. On the instance ID register an expiry in the past, or a soft expiry not earlier than the hard expiry, refuses the whole call with `400 INVALID_EXPIRY`.
    </ParamField>
    <ParamField body="entries[].kycHash" type="string">
      The KYC hash to register, as 32-byte hex. On the instance ID register every entry needs one on the calldata leg: the root of the customer's KYC proof bundle, or your own salted commitment. One missing, or any entry carrying `kycData`, refuses the whole call with `400 KYC_HASH_REQUIRED`, and the message names the entries. On a register of your own, an entry without it gets a random 32-byte hash over no personal data, so it changes on every call.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 only. The signatures from the `SIGN_CLAIMS` phase, as `[{ walletAddress, signature }]`. On a T-REX 5 register each entry also carries `issuedAt`, exactly as its message gave it.
</ParamField>

<ParamField body="identities" type="object">
  ERC-3643 only. ONCHAINIDs you deployed with your own tooling, keyed by wallet.
</ParamField>

<ParamField body="signerAddress" type="string">
  ERC-3643 only. The instance ID register ignores it. The wallet that will sign the claims. Refused with `CLAIM_SIGNER_NOT_TRUSTED` when it holds no claim key on the register's trusted issuer. It also becomes the management key of any ONCHAINID the plan deploys, so name a wallet registered to your instance.

  On a T-REX 5 register it names the wallet you will sign the current phase with, and a phase it lacks a role for answers `403 SIGNER_ROLE_MISSING`, as on [Verify Identity](/endpoints/customers/verify-identity#verify-on-an-erc-3643-t-rex-5-register).
</ParamField>

<ParamField body="txHash" type="string">
  The hash of the mined transaction. Send it with the same `entries` to confirm. On an ERC-3643 register, send the hash of `steps[confirmStepIndex]`. Omit it to receive the calldata or the next phase.
</ParamField>

`rejected[].code` is one of `INVALID_ENTRY`, `INVALID_ADDRESS`, `MISSING_COUNTRY`, `INVALID_COUNTRY`, `INVALID_HASH`, `DUPLICATE_ADDRESS`, `INVALID_INVESTOR_TYPE` or `COUNTRY_BLOCKED`. An `INVALID_INVESTOR_TYPE` message lists the values your instance accepts. `COUNTRY_BLOCKED` checks the [verification profile](/endpoints/customers/list-verification-profiles) named after the entry's `investorType`.

## Verify on the instance ID register

Send `transaction` from a wallet your instance ID register trusts as an attester. It calls `attestBatch` on the identity hub, which writes one attestation per wallet under the signing wallet's own address. Each carries the entry's `kycHash` as its root, its investor class and expiries, and the predicate bits `KYC_DONE` and `RESIDENCY_ON_FILE`, plus `EEA_RESIDENT` for a country in the EEA. See [Predicates](/endpoints/customers/introduction#predicates).

A batch on the instance ID register holds at most 200 accepted entries. More are refused with `400 INVALID_BATCH_SIZE`: split them across calls.

The calldata leg refuses with `409 INSTANCE_REGISTER_REQUIRED` when your instance has not created its register yet, with `403 ATTESTER_MISSING` when it can read that the register trusts none of your instance's registered wallets as an attester, and with `501 IDENTITY_HUB_NOT_CONFIGURED` when the hub is not deployed on your network. See [Attesters and trust](/endpoints/customers/introduction#attesters-and-trust).

The confirm leg accepts only an `attestBatch` on the hub. It refuses with `403 UNTRUSTED_ATTESTER` when the signing wallet is not a trusted attester of your register, with `TX_ENTRIES_MISMATCH` when the attested wallets differ from the accepted entries, and with `TX_INVESTOR_TYPE_MISMATCH` when a mined investor class differs from the request.

## Verify on a Trusset-compatible register of your own

Send `transaction` from a wallet that holds `KYC_PROVIDER_ROLE` on your register. The API refuses the calldata with `KYC_PROVIDER_ROLE_MISSING` when it can read that none of your instance's wallets holds the role.

The confirm leg refuses before writing anything when the transaction's wallets differ from the accepted entries (`TX_ENTRIES_MISMATCH`). It also refuses when a written entry's mined investor type differs from the request (`TX_INVESTOR_TYPE_MISMATCH`). The signer is logged, not checked.

## Verify on an ERC-3643 register

The phases work as on [Verify Identity](/endpoints/customers/verify-identity), across every accepted entry:

| Phase | What you get |
|---|---|
| `DEPLOY_IDENTITY` | One deployment per wallet without an ONCHAINID. Confirm each with [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid), then call again |
| `SIGN_CLAIMS` | One `messages` entry per wallet. Sign each with a CLAIM key on `claimIssuer`, then call again with `claimSignatures` |
| `REGISTER` | One `claim` step per wallet, then one `verify` step (`registerIdentity` for one new wallet, `batchRegisterIdentity` with `walletAddresses` for several), then any `country` steps |

Send `entries` from the first response on every later call, so each wallet keeps its `kycHash`. The claim signatures cover those hashes.

The keys are the same as on Verify Identity. A CLAIM key on `claimIssuer` signs, and the ONCHAINID's management key sends each `claim` step. An agent of the register sends the `verify` and `country` steps. The API refuses up front with `REGISTRY_AGENT_MISSING` or `CLAIM_SIGNER_MISSING` when none of your instance's wallets qualifies. The ERC-3643 example sends everything from one `wallet` that is both, named as `signerAddress`.

On a T-REX 5 register (`trexVersion: 5`) the phases differ as on [Verify Identity](/endpoints/customers/verify-identity#verify-on-an-erc-3643-t-rex-5-register):

| Phase | What you get |
|---|---|
| `CREATE_IDENTITY` | One `createIdentityFor` step per wallet without an ONCHAINID, sent to the identity factory. The factory links each identity to its wallet, so nothing is confirmed: call again once they are mined |
| `SIGN_CLAIMS` | One `messages` entry per wallet, as EIP-712 typed data. Sign each with a CLAIM_SIGNER key on `claimIssuer`, then call again with `claimSignatures`, each carrying its message's `issuedAt` |
| `REGISTER` | One `addClaimTo` step per wallet, a `rotateClaim` step (`revokeClaimByDigest`) for each wallet whose previous KYC claim from the same issuer is replaced, then one `verify` step for the wallets not yet on the register |

Every step names the wallet that must sign it in `signer`. There are no `country` steps: a T-REX 5 register records no country, so each country stays on the customer record, and `warnings` carries `COUNTRY_NOT_ON_REGISTER`.

<Warning>
  On an ERC-3643 register, batch only wallets that are new to the register. The confirm compares the wallets in the `verify` step with every accepted entry, and a wallet already on the register is left out of that step. The confirm then fails with `TX_ENTRIES_MISMATCH`, and a `claim` or `country` step cannot be confirmed here at all. Use [Verify Identity](/endpoints/customers/verify-identity) for wallets already on the register.
</Warning>

An ERC-3643 register stores no investor type and no expiry, so `TX_INVESTOR_TYPE_MISMATCH` never applies there. `onChainSkipped` lists the wallets whose KYC claim could not be read back after the transaction. Unlike Verify Identity, the batch confirm does not ask the register whether each wallet now counts as verified.

## Records

For every accepted wallet not in `onChainSkipped`, the confirm leg writes the customer record as `verified`, with the profile key the entry's `investorType` resolved to and the `kycHash` read from the chain. A new record takes the entry's country. An existing record keeps the country it already has. Any [pending verification](/endpoints/customers/list-pending-verifications) for those wallets is settled, and the batch is recorded once in your instance's verification history as a `BATCH_VERIFY` entry with the wallets it registered, the transaction and its signer. When the profile an entry's `investorType` names has an eligibility register, the wallet's admission to it is queued for your wallet to sign. See [Eligibility registers](/endpoints/customers/introduction#eligibility-registers). On the instance ID register a profile is checked by its [profile gate](/endpoints/customers/introduction#profile-gates), which reads the attestation itself, so nothing is queued.

```typescript TypeScript ERC-3643
import { ethers } from 'ethers';

const base = 'https://api.trusset.org/customers/api/identity';
const headers = {
  'Content-Type': 'application/json',
  'X-API-Key': 'trusset_your_key_here'
};
const post = async (path: string, body: Record<string, unknown>) => {
  const res = await fetch(`${base}${path}`, { method: 'POST', headers, body: JSON.stringify(body) });
  const json = await res.json();
  if (!json.success) throw new Error(`${json.error.code}: ${json.error.message}`);
  return json.data;
};

const signerAddress = await wallet.getAddress();

let plan = await post('/batch-verify', {
  signerAddress,
  entries: [
    { walletAddress: '0xaBc123DEf456789012345678901234567890aBCD', country: 'DE', investorType: 'PROFESSIONAL' },
    { walletAddress: '0x1234567890AbcdEF1234567890aBcdef12345678', country: 'FR', investorType: 'RETAIL' }
  ]
});
const entries = plan.entries;

if (plan.phase === 'DEPLOY_IDENTITY') {
  for (const step of plan.steps) {
    const tx = await wallet.sendTransaction({ data: step.transaction.data });
    await tx.wait();
    await post('/onchainid/confirm', { walletAddress: step.walletAddress, txHash: tx.hash });
  }
  plan = await post('/batch-verify', { signerAddress, entries });
}

if (plan.phase === 'SIGN_CLAIMS') {
  const claimSignatures = [];
  for (const message of plan.messages) {
    const signature = await wallet.signMessage(ethers.utils.arrayify(message.messageHash));
    claimSignatures.push({ walletAddress: message.walletAddress, signature });
  }
  plan = await post('/batch-verify', { signerAddress, entries, claimSignatures });
}

const hashes: string[] = [];
for (const step of plan.steps) {
  const tx = await wallet.sendTransaction(step.transaction);
  await tx.wait();
  hashes.push(tx.hash);
}

const confirmed = await post('/batch-verify', { entries, txHash: hashes[plan.confirmStepIndex] });
```

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_INPUT` | `400` | `entries` is not an array of 1 to 500 items |
| `NO_VALID_ENTRIES` | `400` | Every entry was rejected. `data` still carries the counts and `rejected` |
| `KYC_HASH_REQUIRED` | `400` | Instance ID register: an entry carries `kycData`, or, on the calldata leg, has no `kycHash`. `data.indexes` lists the entries, zero-based. Send each entry's bundle root or your own salted commitment |
| `INVALID_BATCH_SIZE` | `400` | Instance ID register: more than 200 entries were accepted |
| `INVALID_EXPIRY` | `400` | Instance ID register: an entry's expiry lies in the past, or its soft expiry is not earlier than its hard expiry |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance is in Trusset mode and has not created its instance ID register yet |
| `ATTESTER_MISSING` | `403` | Instance ID register: none of your instance's registered wallets is a trusted attester of the register |
| `IDENTITY_HUB_NOT_CONFIGURED` | `501` | The identity hub is not deployed on your instance's network |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | Trusset-compatible register of your own: none of your instance's wallets holds `KYC_PROVIDER_ROLE` |
| `REGISTRY_AGENT_MISSING` | `403` | ERC-3643: none of your instance's wallets is an agent of the register |
| `CLAIM_SIGNER_MISSING` | `403` | ERC-3643: none of your instance's wallets holds a claim key on the trusted issuer |
| `CLAIM_SIGNER_NOT_TRUSTED` | `403` | ERC-3643: `signerAddress`, or the wallet a claim signature recovers to, holds no claim key on the trusted issuer |
| `INVALID_CLAIM_SIGNATURE` | `400` | ERC-3643: a claim signature is not 65-byte hex, or recovers to no signer. On T-REX 5, also one that is not a valid EIP-712 signature over the claim |
| `CLAIM_MANAGER_MISSING` | `403` | T-REX 5: none of your instance's wallets holds a MANAGEMENT key on the trusted issuer identity |
| `IDENTITY_ISSUER_MISSING` | `403` | T-REX 5: a wallet has no ONCHAINID, and none of your instance's wallets holds the IDENTITY_ISSUER role of the identity factory's authority |
| `SIGNER_ROLE_MISSING` | `403` | T-REX 5: `signerAddress` lacks the role a step or message of this phase needs. The message names the role and the wallets that hold it |
| `REGISTRY_NO_CLAIM_TOPICS` | `409` | ERC-3643: the register requires no claim topic |
| `REGISTRY_NO_TRUSTED_ISSUER` | `409` | ERC-3643: the register names no trusted issuer for its claim topic |
| `ONCHAINID_AUTHORITY_UNKNOWN` | `409` | ERC-3643: a wallet has no ONCHAINID, and no identity on the register reveals the implementation to deploy |
| `IDENTITY_TYPE_NOT_ENABLED` | `409` | T-REX 5: the identity factory has no policy for a wallet's identity type |
| `IDENTITY_BINDING_REVOKED` | `409` | T-REX 5: a wallet's binding on the identity factory is revoked. Leave it out, or use another wallet for that customer |
| `CLAIM_NOT_VALID` | `409` | T-REX 5: the trusted issuer does not accept a signed claim. Sign it again |
| `OWN_REGISTRY_NOT_CONFIGURED` | `409` | The instance is bound to its own register but no valid register address is set |
| `REGISTRY_PROBE_FAILED` | `503` | Your own register could not be read to tell its kind, or the trusted issuer could not be read to check a claim signer |
| `INVALID_TX` | `400` | `txHash` is not 32-byte hex |
| `TX_NOT_FOUND` | `404` | The transaction is not mined yet |
| `TX_REVERTED` | `400` | The transaction reverted |
| `TX_WRONG_TARGET` | `400` | The transaction does not write to the identity hub or the register, or it deployed a contract |
| `TX_WRONG_FUNCTION` | `400` | The transaction calls a function this endpoint does not confirm. On the instance ID register, anything but `attestBatch` |
| `TX_TARGET_MISMATCH` | `400` | ERC-3643: the hash is a `claim` step, which this endpoint cannot confirm |
| `UNTRUSTED_ATTESTER` | `403` | Instance ID register: the transaction was signed by a wallet the register does not trust as an attester |
| `TX_ENTRIES_MISMATCH` | `400` | The transaction registers a different set of wallets than the accepted entries |
| `TX_INVESTOR_TYPE_MISMATCH` | `400` | Instance ID register or Trusset-compatible register: a written entry's mined investor type differs from the request |
| `CHAIN_UNAVAILABLE` | `503` | ERC-3643: the transaction could not be read |
| `BATCH_VERIFY_FAILED` | `400`, `500` | Any other failure. `400` when a chain call or the transaction encoding failed |
