---
title: 'Confirm Transactions'
api: 'POST /customers/api/onboarding/{customer}/transactions/confirm'
description: 'Record the transactions your wallet signed for an onboarding'
---

Records the outcome of the transactions [Build Transactions](/endpoints/customers/build-onboarding-transactions) returned. Trusset reads the receipt from the chain and records only what it shows: the transaction must be mined, successful, sent by a wallet of your instance, and cover this customer's wallet. On your [instance ID register](/endpoints/customers/introduction#the-instance-id-register) a registration is accepted from any wallet the register trusts as an attester, and the register must then report the wallet as verified.

The call confirms the step the onboarding waits for. Send `kind` with the kind you signed. A repeat of a confirmation that is already recorded then answers `alreadyRecorded: true` instead of being applied to the next step.

After a confirmed registration the onboarding reads `COMPLETED`, or `AWAITING_SIGNATURE` again with `ELIGIBILITY_ADMISSION` when the profile has an eligibility register.

## Path Parameters

<ParamField path="customer" type="string" required>
  The customer `id`, your `externalId`, the reference key or a wallet address of the customer.
</ParamField>

## Body Parameters

<ParamField body="kind" type="string">
  `IDENTITY_REGISTRATION`, `ELIGIBILITY_ADMISSION` or `WHITELIST_ADMISSION`: the kind you built and signed. Recommended on every call.
</ParamField>

<ParamField body="txHash" type="string">
  The hash of the transaction, `0x` followed by 64 hex characters. For a registration it is the `attestBatch` transaction on the identity hub when your instance writes to its instance ID register, otherwise the `batchVerifyIdentities` (or `registerIdentity`) transaction. Required for the two admission kinds.
</ParamField>

<ParamField body="claimTxResults" type="array">
  For a registration: `{ id, txHash }` for the residency claim transaction, with `id` the `pendingId`.
</ParamField>

<ParamField body="updateTxResults" type="array">
  For a registration that renews an identity (`operations` reads `update`): `{ id, txHash }` for the `updateIdentity` transaction, with `id` the `pendingId`.
</ParamField>

<ParamField body="listId" type="string">
  For `WHITELIST_ADMISSION`: the whitelist this transaction listed the wallet on. Optional while exactly one whitelist is still open.
</ParamField>

## Response Fields

<ResponseField name="data" type="object">
  <Expandable>
    <ResponseField name="kind" type="string">The kind that was confirmed, or `null` for a repeat on a completed onboarding that named none.</ResponseField>
    <ResponseField name="alreadyRecorded" type="boolean">`true` when the step was recorded before and nothing was read or written now.</ResponseField>
    <ResponseField name="result" type="object">What the confirmation recorded, as [Confirm Pending Registration](/endpoints/customers/confirm-pending-registration), [Confirm Admission](/endpoints/customers/confirm-admission) or [Confirm Record Admission](/endpoints/customers/confirm-kyc-record-admission) returns it. `null` with `alreadyRecorded`.</ResponseField>
    <ResponseField name="onboarding" type="object">The onboarding after the confirmation.</ResponseField>
  </Expandable>
</ResponseField>

<Warning>
  A registration answers `200` even when the chain could not be read or the transaction did not register the wallet. `result.results[0].status` then reads `CHAIN_READ_UNAVAILABLE` or `NOT_REGISTERED_ON_CHAIN`, and the onboarding stays `AWAITING_SIGNATURE`. Read `onboarding.status`, and confirm again or sign again.
</Warning>

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_TX_HASH` | `400` | `txHash` is missing where it is required, or is not a 32-byte hex string |
| `INVALID_INPUT` | `400` | `kind` is unknown, or a result list is malformed |
| `VALIDATION_ERROR` | `400` | A registration was confirmed without `txHash`, `updateTxResults` or `claimTxResults` |
| `LIST_REQUIRED` | `400` | Several whitelists are still open and `listId` names none. `error.details.lists` names them |
| `TX_ENTRIES_MISMATCH` | `400` | The transaction does not cover this customer's wallet |
| `UNAUTHORIZED_SIGNER` | `403` | The transaction was signed by a wallet that is not registered to your instance |
| `UNTRUSTED_ATTESTER` | `403` | On an instance ID register: the attestation was signed by a wallet the register does not trust as an attester |
| `CUSTOMER_NOT_FOUND` | `404` | No customer of your instance matches `customer` |
| `NOTHING_TO_CONFIRM` | `409` | The onboarding expects no signed transaction. `error.details` carries its `status` |
| `ONBOARDING_STATE_CHANGED` | `409` | The onboarding waits for another kind than the one named. Build the transactions again |
| `RATE_LIMIT_EXCEEDED` | `429` | More than 120 onboarding writes in the minute |
| `ONBOARDING_CONFIRM_FAILED` | `500` | The confirmation failed on the server |
| `CHAIN_UNAVAILABLE` | `503` | The chain could not be read. Retry shortly |

A transaction that is not mined, reverted, sent to another contract or signed by a wallet that is not registered to your instance is refused with the code the confirmation of its kind documents.
