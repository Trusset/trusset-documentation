---
title: 'Build Transactions'
api: 'POST /customers/api/onboarding/{customer}/transactions'
description: 'The unsigned transactions an onboarding waits for your wallet to sign'
---

Returns the transactions your wallet has to sign while the onboarding reads `AWAITING_SIGNATURE`. Nothing is submitted for you: a wallet of your instance signs and broadcasts them, and [Confirm Transactions](/endpoints/customers/confirm-onboarding-transactions) records the result. The call can be repeated and builds the same step again until it is confirmed.

`kind` says what is signed, and matches `nextAction.kind` of the onboarding:

| Kind | Built here | Signed by |
|---|---|---|
| `IDENTITY_REGISTRATION` | `plan`, as [Build Pending Registration](/endpoints/customers/build-pending-registration) returns it for this one customer | A trusted attester of your [instance ID register](/endpoints/customers/introduction#attesters-and-trust), a wallet holding `KYC_PROVIDER_ROLE` on a Trusset-compatible register of your own, or an agent of an ERC-3643 registry |
| `ELIGIBILITY_ADMISSION` | `plan`, as [Build Admission](/endpoints/customers/build-admission) returns it for this wallet | An agent of the profile's eligibility register. `signerAddress` is required |
| `WHITELIST_ADMISSION` | `admissions`, one `setListed` plan for each whitelist that does not list the wallet yet | An owner or manager of the whitelist |

On an ERC-3643 register a registration is built in phases, as [Verify Identity](/endpoints/customers/verify-identity) sets out. Send the claim signatures of the previous phase back as `claimSignatures`, and confirm a deployed ONCHAINID with [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid).

## Path Parameters

<ParamField path="customer" type="string" required>
  The customer `id`, your `externalId`, the reference key or a wallet address of the customer.
</ParamField>

## Body Parameters

<ParamField body="signerAddress" type="string">
  The wallet of your instance that will sign. Required for `ELIGIBILITY_ADMISSION`.
</ParamField>

<ParamField body="claimSignatures" type="array">
  For an ERC-3643 registration: `{ walletAddress, signature, claimType }` for each claim message the previous phase asked you to sign. At most 400 entries.
</ParamField>

## Response Fields

<ResponseField name="data" type="object">
  <Expandable>
    <ResponseField name="kind" type="string">`IDENTITY_REGISTRATION`, `ELIGIBILITY_ADMISSION` or `WHITELIST_ADMISSION`.</ResponseField>
    <ResponseField name="pendingId" type="string">With `IDENTITY_REGISTRATION`: the row in the pending queue. Use it as `id` in `claimTxResults` and `updateTxResults`.</ResponseField>
    <ResponseField name="recordId" type="string">With `WHITELIST_ADMISSION`: the sealed record.</ResponseField>
    <ResponseField name="plan" type="object">The transactions of a registration or an eligibility admission. `plan.steps` holds one entry per transaction with `transaction.to`, `transaction.data` and `chainId`.</ResponseField>
    <ResponseField name="admissions" type="array">With `WHITELIST_ADMISSION`: `listId`, `listName`, `listAddress`, `alreadyListed` and `plan` for each whitelist.</ResponseField>
    <ResponseField name="confirmWith" type="object">The confirm call: `method`, `endpoint`, `kind` and the `fields` it takes.</ResponseField>
    <ResponseField name="onboarding" type="object">The onboarding the transactions were built for.</ResponseField>
  </Expandable>
</ResponseField>

```typescript TypeScript
const response = await fetch(
  'https://api.trusset.org/customers/api/onboarding/client-48213/transactions',
  {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-API-Key': 'trusset_your_key_here' },
    body: JSON.stringify({ signerAddress: await signer.getAddress() })
  }
);
const { data } = await response.json();
for (const step of data.plan.steps) {
  const sent = await signer.sendTransaction({ to: step.transaction.to, data: step.transaction.data });
  await sent.wait();
}
```
</RequestExample>

The example shortens `onboarding` and the calldata. On an instance ID register the registration is one `attestBatch` call on the identity hub, which writes the attestation under the signing wallet's own address, so `transaction.to` is the hub. `plan` also carries the `confirmWith` of the pending queue, which names the same confirmation on its own endpoint.

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `signerAddress` is malformed |
| `INVALID_INPUT` | `400` | `claimSignatures` is not a list, or holds more than 400 entries |
| `COUNTRY_BLOCKED` | `403` | The profile now blocks the customer's country |
| `ATTESTER_MISSING` | `403` | No registered wallet of your instance is a trusted attester of your instance ID register. See [Attesters and trust](/endpoints/customers/introduction#attesters-and-trust) |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | On a Trusset-compatible register of your own, no wallet of your instance holds the role the registration needs. See [Which register you write to](/endpoints/customers/introduction#which-register-you-write-to) |
| `CUSTOMER_NOT_FOUND` | `404` | No customer of your instance matches `customer` |
| `NOTHING_TO_SIGN` | `409` | The onboarding does not read `AWAITING_SIGNATURE`. `error.details` carries its `status` and `nextAction` |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance writes to an instance ID register and has not created it yet |
| `RATE_LIMIT_EXCEEDED` | `429` | More than 120 onboarding writes in the minute |
| `ONBOARDING_BUILD_FAILED` | `500` | The build failed on the server |
| `CHAIN_UNAVAILABLE` | `503` | The chain could not be read. Retry shortly |

The builders behind each kind refuse with their own codes as well. [Build Pending Registration](/endpoints/customers/build-pending-registration), [Build Admission](/endpoints/customers/build-admission) and [Approve KYC Record](/endpoints/customers/approve-kyc-record) list them.
