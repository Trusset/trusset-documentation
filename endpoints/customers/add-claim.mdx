---
title: 'Add Claim'
api: 'POST /customers/api/identity/add-claim'
description: 'File one of the four manual claims on an identity'
---

Files one of the four claims that are not backed by a proof: `AML`, `TAX_RESIDENCY`, `SANCTIONS_CHECK` or `PEP_CHECK`.

On the instance ID register a claim is a predicate bit of the wallet's attestation on the identity hub: `AML_CLEAR`, `TAX_RESIDENCY_ON_FILE`, `SANCTIONS_CLEAR` or `PEP_CLEAR`. The calldata attests the wallet again with the same root, investor class and expiries, and that one bit added. The hash you supply is not written on chain. See [Claims](/endpoints/customers/introduction#claims). On a Trusset-compatible register of your own, and on an ERC-3643 register, the claim is written with the hash you supply.

<Warning>
  On a Trusset-compatible register of your own the register keeps one claim per slot, and filing a slot replaces the claim already there, whoever wrote it. The API does not check there that the wallet holds an active identity, and the register reverts `addClaim` for one that does not.
</Warning>

<Warning>
  `KYC`, `ACCREDITATION`, `RESIDENCY` and `CITIZENSHIP` are refused here with `PROOF_REQUIRED`. Those four are reserved on this API for claims filed from a proof bundle. File them with [Add Claims from Proof](/endpoints/customers/add-claims-from-proof) or [Attest Proofs](/endpoints/customers/attest-proofs). The one exception is the `RESIDENCY` claim that [Build Pending Registration](/endpoints/customers/build-pending-registration) files with a queued approval.

  The contracts do not enforce the reservation. On the instance ID register any attester can attest any predicate bits about a wallet under its own name by calling the identity hub directly, and your register decides which bits it accepts from which attester. On a Trusset-compatible register a wallet holding `KYC_PROVIDER_ROLE` can write any slot.
</Warning>

## Body Parameters

<ParamField body="walletAddress" type="string" required>The subject.</ParamField>

<ParamField body="claimType" type="string | integer" required>
  One of `AML`, `TAX_RESIDENCY`, `SANCTIONS_CHECK`, `PEP_CHECK`, by name or index.
</ParamField>

<ParamField body="dataHash" type="string">
  The claim's payload as a 32-byte hex hash, `0x` and 64 hex characters. What it commits to is your convention. When both fields are sent, a valid `dataHash` wins. On the instance ID register it is not written on chain: it is kept in your instance's verification history with the claim.
</ParamField>

<ParamField body="dataInput" type="string">
  On a register of your own, a string to derive the hash from instead. The hash is `keccak256` over the UTF-8 JSON `{"claimType":"<name>","data":"<input>","wallet":"<wallet>"}`, with the input trimmed and the wallet lowercased. It has no salt, so do not put personal data here. Supply this or `dataHash`.

  The instance ID register refuses it with `400 DATA_HASH_REQUIRED`, because claim data never goes to Trusset. Send `dataHash`, your own salted commitment.
</ParamField>

<ParamField body="expiryDays" type="integer">
  Days until the claim expires, between 0 and 36500. `0` or omitted means no expiry. The instance ID register does not use it: the bit lasts as long as the attestation, whose expiries stay as they are.
</ParamField>

<ParamField body="txHash" type="string">
  Send it to confirm. Omit it to receive the calldata.
</ParamField>

<ParamField body="claimSignature" type="string">
  ERC-3643 register only. The EIP-191 signature over the `messageHash` from a `SIGN_MESSAGES` answer, as 65-byte hex.
</ParamField>

<ParamField body="claimSignatures" type="array">
  T-REX 5 register only, in place of `claimSignature`. `[{ walletAddress, signature, claimType, issuedAt }]`, where `signature` signs the message's `typedData` and `issuedAt` is sent back exactly as the message gave it.
</ParamField>

<ParamField body="signerAddress" type="string">
  On the instance ID register, the wallet you will sign with. When it holds an active or suspended attestation about the wallet, the calldata updates that one. Otherwise it copies the attestation the register resolves for the wallet. See [Sign and confirm](#sign-and-confirm).

  On an ERC-3643 register, the instance wallet that signs the claim. It must hold a CLAIM key on the register's trusted issuer.

  On a T-REX 5 register it names the wallet you will sign the current answer with: a CLAIM_SIGNER key for the message, a MANAGEMENT key of the trusted issuer identity for the `addClaimTo` step. Lacking that key, the call answers `403 SIGNER_ROLE_MISSING`.
</ParamField>

## Sign and confirm

### On the instance ID register

The calldata calls `attest` on the identity hub. It copies an existing attestation and adds the claim's predicate bit: the attestation of `signerAddress` when that wallet holds an active or suspended one about the subject, otherwise the attestation the register resolves for the wallet. `attester` in the answer names the wallet whose attestation was copied. Sign with that wallet to update its attestation. The hub writes under the address that signs, so another trusted attester signing it writes an attestation of its own with the same root, class and expiries.

Before handing out calldata, the API refuses with:

- `409 INSTANCE_REGISTER_REQUIRED` when your instance has not created its register yet
- `403 ATTESTER_MISSING` when it can read that the register trusts none of your instance's registered wallets as an attester. A register admin trusts a wallet on the wallet page of the issuer app. See [Attesters and trust](/endpoints/customers/introduction#attesters-and-trust)
- `409 IDENTITY_NOT_REGISTERED` when the register reports no unrevoked identity for the wallet, and `409 IDENTITY_NOT_ACTIVE` when no active attestation can be found to copy
- `409 IDENTITY_SUSPENDED`, `IDENTITY_EXPIRED` or `IDENTITY_SOFT_EXPIRED` when the attestation to copy is suspended, past its hard expiry or past its soft expiry. Verify the wallet again with [Verify Identity](/endpoints/customers/verify-identity) first

The confirm leg requires a mined, successful `attest` on the hub for this wallet whose attestation carries the claim's bit (`TX_PREDICATES_MISMATCH` otherwise), signed by a trusted attester of your register (`403 UNTRUSTED_ATTESTER` otherwise). It reports the mined `predicates` and `root`.

### On a Trusset-compatible register of your own

The calldata calls `addClaim` on the register, which needs a wallet holding `KYC_PROVIDER_ROLE`. Before handing it out, the API checks that one of your instance's registered wallets holds that role, and refuses with `KYC_PROVIDER_ROLE_MISSING` otherwise. It skips the check when the instance has no registered wallet or the role cannot be read.

The confirm leg requires a mined, successful `addClaim` on this instance's register that targets this wallet. It reads the slot, hash and expiry back out of the transaction and reports them, rather than comparing them with your request. The signer is logged, not checked.

### Every register

The claim is recorded once in your instance's verification history as an `ADD_CLAIM` entry with the claim type, hash, expiry, transaction and signer, and on the instance ID register also the mined predicates, root and attester. Confirming the same `txHash` again writes no second entry.

## On an ERC-3643 register

When the instance is bound to an ERC-3643 register, the claim is written to the subject's ONCHAINID. It needs a signature from a CLAIM key on the register's trusted issuer.

1. The first call answers `SIGN_MESSAGES`. Sign the `messageHash` in `messages` as an EIP-191 personal message with a wallet that holds a CLAIM key on `claimIssuer`.
2. Call again with `claimSignature`. The answer is `SIGN_TRANSACTIONS`, with one `addClaim` step addressed to the ONCHAINID.
3. Broadcast it and confirm with `txHash`.

A wallet with no ONCHAINID is refused with `NOT_REGISTERED`. Deploy one first with `POST /customers/api/identity/onchainid` and confirm it, so it is recorded. The claim carries no expiry, so `expiryDays` is not written and the confirm leg reports `expiry: 0`. The role check becomes an agent check on the register.

On a T-REX 5 register (`trexVersion: 5`) the two rounds work the same way with these differences:

1. The `SIGN_MESSAGES` answer carries a message with `scheme: eip712`, `typedData` and `issuedAt`. Sign `typedData` as EIP-712 typed data with a wallet that holds a CLAIM_SIGNER key on `claimIssuer`.
2. Call again with `claimSignatures`, each entry carrying its message's `issuedAt`. The `SIGN_TRANSACTIONS` answer holds one `addClaimTo` step addressed to the trusted issuer identity, which writes the claim onto the subject's ONCHAINID. A MANAGEMENT key of the issuer identity sends it, and the step names that wallet in `signer`.
3. The confirm leg accepts an `addClaimTo` that writes onto this wallet's ONCHAINID.

A wallet with no ONCHAINID on the register's identity factory yet is refused with `NOT_REGISTERED`: verify the wallet first with [Verify Identity](/endpoints/customers/verify-identity), which creates its identity.

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_CLAIM_SIGNATURE` | `400` | The signature is not 65-byte hex, or does not recover for this identity, topic and data |
| `REGISTRY_AGENT_MISSING` | `403` | None of your instance's wallets is an agent of the register |
| `CLAIM_SIGNER_MISSING` | `403` | None of your instance's wallets holds a CLAIM key on the register's trusted issuer |
| `CLAIM_SIGNER_NOT_TRUSTED` | `403` | `signerAddress`, or the wallet the signature recovers to, holds no CLAIM key on the trusted issuer |
| `CLAIM_MANAGER_MISSING` | `403` | T-REX 5: none of your instance's wallets holds a MANAGEMENT key on the trusted issuer identity |
| `SIGNER_ROLE_MISSING` | `403` | T-REX 5: `signerAddress` lacks the key this answer needs. The message names the wallets that hold it |
| `NOT_REGISTERED` | `409` | The wallet has no ONCHAINID yet. On T-REX 5, none on the register's identity factory |
| `CLAIM_NOT_VALID` | `409` | T-REX 5: the trusted issuer does not accept the signed claim. Sign it again |
| `REGISTRY_NO_CLAIM_TOPICS` | `409` | The register requires no claim topics, so there is nothing to file |
| `REGISTRY_NO_TRUSTED_ISSUER` | `409` | The register names no trusted issuer for its claim topic |
| `CHAIN_UNAVAILABLE` | `503` | The confirmed transaction could not be read |

    <ResponseField name="transaction" type="object">The unsigned call: `attest` on the identity hub on the instance ID register, `addClaim` on the register on a Trusset-compatible register. Calldata leg only.</ResponseField>

    <ResponseField name="attester" type="string">The attester whose attestation the calldata copies. Instance ID register, calldata leg only.</ResponseField>
    <ResponseField name="registerKind" type="string">`INSTANCE`, `TRUSSET` or `TREX`. Calldata leg only.</ResponseField>
    <ResponseField name="messages" type="array">ERC-3643 register only: the claim message to sign, with `messageHash`, `claimType`, `identity`, `topic` and `claimIssuer`. On a T-REX 5 register it adds `scheme: eip712`, `typedData` and `issuedAt`.</ResponseField>
    <ResponseField name="steps" type="array">ERC-3643 register only: the `addClaim` transaction to the ONCHAINID, once the signature is in. On a T-REX 5 register, the `addClaimTo` transaction to the trusted issuer identity, with `signer`.</ResponseField>
    <ResponseField name="walletAddress" type="string">The subject, checksummed.</ResponseField>
    <ResponseField name="claimType" type="string">The claim, by name. On the confirm leg it is read back from the mined transaction, not echoed, except on the instance ID register, where the confirm checks the bit and echoes the request.</ResponseField>

    <ResponseField name="predicates" type="string">The predicate bits as a decimal string of the 128-bit mask: the bits the calldata attests, and on the confirm leg the bits mined. Instance ID register only.</ResponseField>
    <ResponseField name="root" type="string">The root of the mined attestation. Instance ID register, confirm leg only.</ResponseField>
    <ResponseField name="txHash" type="string">The confirmed transaction. Confirm leg only.</ResponseField>
    <ResponseField name="gasUsed" type="string">Gas used. Confirm leg only.</ResponseField>
    <ResponseField name="confirmWith" type="object">`{ endpoint, field: "txHash" }`. Calldata leg only.</ResponseField>
  </Expandable>

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `walletAddress` is missing or malformed |
| `INVALID_CLAIM_TYPE` | `400` | `claimType` is not a claim name or an index from 0 to 7 |
| `PROOF_REQUIRED` | `400` | One of the four reserved claims was named |
| `INVALID_HASH` | `400` | Neither a valid `dataHash` nor a non-empty `dataInput` was supplied |
| `DATA_HASH_REQUIRED` | `400` | Instance ID register: the request carries `dataInput`. Send `dataHash` instead |
| `INVALID_EXPIRY` | `400` | `expiryDays` is outside 0 to 36500 |
| `INVALID_TX` | `400` | `txHash` is not a 32-byte hex hash |
| `TX_REVERTED` | `400` | The transaction reverted |
| `TX_WRONG_TARGET` | `400` | The transaction was not sent to the identity hub or this instance's register |
| `TX_WRONG_FUNCTION` | `400` | The transaction does not call `attest` on the hub or `addClaim` on the register |
| `TX_TARGET_MISMATCH` | `400` | The confirmed transaction targets a different wallet, or attests nothing about it |
| `TX_PREDICATES_MISMATCH` | `400` | Instance ID register: the mined attestation does not carry the claim's predicate bit |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance is in Trusset mode and has not created its instance ID register yet |
| `ATTESTER_MISSING` | `403` | Instance ID register: none of your instance's registered wallets is a trusted attester of the register. Calldata leg only |
| `IDENTITY_NOT_REGISTERED` | `409` | Instance ID register: the register reports no unrevoked identity for the wallet. Calldata leg only |
| `IDENTITY_NOT_ACTIVE` | `409` | Instance ID register: no active attestation about the wallet can be found to add the claim to. Calldata leg only |
| `IDENTITY_SUSPENDED` | `409` | Instance ID register: the attestation is suspended. Calldata leg only |
| `IDENTITY_EXPIRED` | `409` | Instance ID register: the attestation is past its hard expiry. Verify the wallet again. Calldata leg only |
| `IDENTITY_SOFT_EXPIRED` | `409` | Instance ID register: the attestation is past its soft expiry. Verify the wallet again. Calldata leg only |
| `IDENTITY_HUB_NOT_CONFIGURED` | `501` | The identity hub is not deployed on your instance's network |
| `UNTRUSTED_ATTESTER` | `403` | Instance ID register, confirm leg: the transaction was signed by a wallet the register does not trust as an attester |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | Trusset-compatible register of your own: none of your instance's wallets holds `KYC_PROVIDER_ROLE` on the register. Calldata leg only |
| `CHAIN_UNAVAILABLE` | `503` | Instance ID register: the register could not be read to check the wallet. Retry |
| `TX_NOT_FOUND` | `404` | The transaction is not mined yet |
| `OWN_REGISTRY_NOT_CONFIGURED` | `409` | The instance is bound to its own register but has no valid register address |
| `REGISTRY_PROBE_FAILED` | `503` | The instance's own register, or its trusted issuer, could not be read |
| `ADD_CLAIM_FAILED` | `400` or `500` | A chain call failed (`400`), or the request failed unexpectedly (`500`) |
