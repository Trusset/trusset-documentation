---
title: 'Verify Identity'
api: 'POST /customers/api/identity/verify'
description: 'Register a wallet on the identity register and record the customer as verified'
---

Puts a wallet on the identity register your instance writes to. Once you confirm the mined transaction, the customer record is created or updated as `verified`. Nothing is broadcast for you: every call returns what to sign.

<Note>
  `investorType` must name a preset or one of your [verification profiles](/endpoints/customers/list-verification-profiles). Any other value, `INSTITUTIONAL`, `NONE` or a number included, is refused with `400 INVALID_INVESTOR_TYPE` on both legs, and the message lists the values your instance accepts.
</Note>

What you sign depends on the register. Every calldata response names it in `registerKind`.

| `registerKind` | Register | The calldata leg returns |
|---|---|---|
| `TRUSSET` | The Trusset ID Register, or your own deployment of the same contract | One transaction, `verifyIdentity` or `updateIdentity` |
| `TREX` | Your own ERC-3643 (T-REX) identity registry, with ONCHAINID identities | A plan in up to three phases, one call per phase |

## Body Parameters

<ParamField body="walletAddress" type="string" required>
  The wallet to register. Checksummed or lowercase. A mixed-case address with a wrong checksum is refused.
</ParamField>

<ParamField body="country" type="string" required>
  ISO 3166-1 code as alpha-2 (`DE`), alpha-3 (`DEU`) or numeric (`276`). Stored in alpha-3 form. An ERC-3643 register also receives it, as the numeric code.

  Refused with `COUNTRY_BLOCKED` when it is on the blocked list of the [verification profile](/endpoints/customers/list-verification-profiles) named after `investorType`.
</ParamField>

<ParamField body="investorType" type="string" default="RETAIL">
  `RETAIL`, `PROFESSIONAL` or `ELIGIBLE_COUNTERPARTY` in any letter case, or the key of one of your custom [verification profiles](/endpoints/customers/list-verification-profiles), also in any letter case. A custom key registers with that profile's on-chain investor type. Omitted, `null` or an empty string reads as `RETAIL`. A disabled profile is refused with `INVALID_INVESTOR_TYPE` on the build call unless the wallet's customer record is already under it, so a customer of a disabled profile can still be verified again. The confirm call records what was signed. Anything else, a number included, is refused with `INVALID_INVESTOR_TYPE`.

  A Trusset register stores the type on chain as `1`, `2` or `3`. An ERC-3643 register has no investor type, so there it is kept on the customer record only. The record keeps the profile key as the profile spells it, so `professional` is stored as `PROFESSIONAL`.
</ParamField>

<ParamField body="softExpiryDays" type="integer">
  Days until the identity is soft-expired. `0` or omitted sets none. Trusset register only: an ERC-3643 register does not store it.
</ParamField>

<ParamField body="hardExpiryDays" type="integer">
  Days until the identity is hard-expired and stops counting as verified. `0` or omitted sets none. Trusset register only.

  The API does not check either expiry. A Trusset register reverts the transaction when the soft expiry is not earlier than the hard expiry, or when either lies in the past.
</ParamField>

<ParamField body="kycHash" type="string">
  The KYC hash to register, as 32-byte hex (`0x` and 64 hex characters). Stored lowercased. For a KYC proof bundle this is its Merkle root. On an ERC-3643 register it becomes the data of the KYC claim.
</ParamField>

<ParamField body="kycData" type="object">
  Data to derive the hash from when `kycHash` is omitted: the keccak256 of its JSON serialisation. With neither, the hash covers the wallet, the country and the current time, so it changes on every call.
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 only. The signatures from the `SIGN_CLAIMS` phase, as `[{ walletAddress, signature }]`. An entry may add `claimType`, such as `KYC`.
</ParamField>

<ParamField body="claimSignature" type="string">
  ERC-3643 only. A single claim signature for `walletAddress`, instead of `claimSignatures`.
</ParamField>

<ParamField body="identities" type="object">
  ERC-3643 only. An ONCHAINID you deployed with your own tooling, keyed by wallet: `{ "<wallet>": "<onchainid>" }`. It is used when the register holds no identity for the wallet and the contract answers as an ONCHAINID. Otherwise it is ignored.
</ParamField>

<ParamField body="signerAddress" type="string">
  ERC-3643 only. The wallet that will sign the claim. Refused with `CLAIM_SIGNER_NOT_TRUSTED` when it holds no claim key on the register's trusted issuer. Defaults to the first of your instance's wallets, primary first, that holds one.

  It also becomes the management key of any ONCHAINID the plan deploys. Name a wallet registered to your instance, because [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid) refuses any other management key.
</ParamField>

<ParamField body="txHash" type="string">
  The hash of the mined transaction. Send it with the same body to confirm. On an ERC-3643 register, send the hash of `steps[confirmStepIndex]`. Omit it to receive the calldata or the next phase.
</ParamField>

</Warning>

## Verify on a Trusset register

Call once without `txHash` and send `transaction` from a wallet that holds `KYC_PROVIDER_ROLE` on the register. Then send the same body again with `txHash` added.

The endpoint picks `updateIdentity` when the wallet already holds an identity that is not revoked, expired ones included. It picks `verifyIdentity` when the wallet has none or was revoked. If the register cannot be read, it falls back to `verifyIdentity`, which reverts for a wallet that already holds an unrevoked identity.

Before handing out calldata, the API checks that one of your instance's wallets holds `KYC_PROVIDER_ROLE`. It refuses with `KYC_PROVIDER_ROLE_MISSING` only when it can read every wallet and none holds the role. With no wallet registered, or when the read fails, it lets the call through. The verdict is cached for 60 seconds, so a refusal can outlast a new role grant by up to a minute.

## Verify on an ERC-3643 register

Each call answers the next phase. Call again with what the previous phase produced until `phase` is `REGISTER`, carrying the same `kycHash` throughout.

<Steps>
  <Step title="Deploy an ONCHAINID (DEPLOY_IDENTITY)">
    Returned when the wallet has no ONCHAINID. Send each step's `transaction` as a contract creation, then confirm each deployment with [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid) so it is recorded. Confirming a deployment here returns `TX_WRONG_TARGET`, whatever `confirmWith` says.

    You can deploy ahead of time with [Deploy ONCHAINID](/endpoints/customers/deploy-onchainid), or pass an ONCHAINID you deployed yourself in `identities`.
  </Step>
  <Step title="Sign the claim (SIGN_CLAIMS)">
    Sign each `messageHash` as an EIP-191 personal message over its 32 bytes. Use a wallet that holds a CLAIM key on `claimIssuer`, such as one in `claimSigners`. Call again with `claimSignatures: [{ walletAddress, signature }]`.
  </Step>
  <Step title="Register (REGISTER)">
    Send `steps` in order. The `claim` step adds the claim to the wallet's ONCHAINID. The `verify` step registers a new wallet, and a `country` step corrects the country of a wallet already on the register. Confirm with the hash of `steps[confirmStepIndex]`.
  </Step>
</Steps>

| Transaction or signature | Who must hold what |
|---|---|
| ONCHAINID deployment | Any wallet can send it. The management key is fixed in the deployment data, and is `signerAddress`. |
| Claim signature | A CLAIM key (purpose 3) on `claimIssuer`. |
| `addClaim` on the ONCHAINID | A management or claim key of that ONCHAINID. For one the plan deployed, that is `signerAddress`. |
| `registerIdentity`, `updateCountry` | An agent of the register. |

The API refuses up front with `REGISTRY_AGENT_MISSING` when none of your instance's wallets is an agent, and with `CLAIM_SIGNER_MISSING` when none holds a claim key. It does not check that the agent and `signerAddress` are the same wallet.

An ERC-3643 register stores no investor type and no expiry. `investorType` reaches the customer record only, and the two expiry fields are not stored anywhere.

The ERC-3643 example sends everything from one `wallet` that is both an agent of the register and a claim signer. Passing its address as `signerAddress` makes it the management key of any ONCHAINID it deploys, so it can also send the `claim` step.

## Confirm

The confirm leg reads the mined transaction and refuses it before writing anything when:

- it is not mined, reverted, or is not a register or ONCHAINID write this endpoint confirms (`TX_WRONG_TARGET`, `TX_WRONG_FUNCTION`)
- it targets a different wallet, or an ONCHAINID that is not this wallet's (`TX_TARGET_MISMATCH`)
- on the Trusset ID Register, it was not signed by one of your instance's verified wallets (`UNAUTHORIZED_SIGNER`). On your own register the signer is logged, not checked
- on a Trusset register, the mined investor type differs from this request's (`TX_INVESTOR_TYPE_MISMATCH`)
- on an ERC-3643 register, the register does not yet report the wallet as verified (`NOT_VERIFIED_ON_REGISTER`)

Then it writes the customer record with `country`, the profile key `investorType` resolved to, `status: "verified"`, `verifiedAt` and the `kycHash` read from the chain. When the profile `investorType` names has an eligibility register, the wallet's admission to it is queued for your wallet to sign. See [Eligibility registers](/endpoints/customers/introduction#eligibility-registers).

<Note>
  Confirming also settles any [pending verification](/endpoints/customers/list-pending-verifications) for the same wallet. Its row is marked confirmed with this transaction, so the queue does not ask for the signature again.
</Note>

```typescript TypeScript ERC-3643
import { ethers } from 'ethers';

const base = 'https://api.trusset.org/customers/api/identity';
const headers = {
  'Content-Type': 'application/json',
  'X-API-Key': 'trusset_your_key_here'
};
const post = async (path: string, body: Record<string, unknown>) => {
  const res = await fetch(`${base}${path}`, { method: 'POST', headers, body: JSON.stringify(body) });
  const json = await res.json();
  if (!json.success) throw new Error(`${json.error.code}: ${json.error.message}`);
  return json.data;
};

const request: Record<string, unknown> = {
  walletAddress: '0xaBc123DEf456789012345678901234567890aBCD',
  country: 'DE',
  investorType: 'PROFESSIONAL',
  signerAddress: await wallet.getAddress()
};

let plan = await post('/verify', request);
request.kycHash = plan.kycHash;

if (plan.phase === 'DEPLOY_IDENTITY') {
  for (const step of plan.steps) {
    const tx = await wallet.sendTransaction({ data: step.transaction.data });
    await tx.wait();
    await post('/onchainid/confirm', { walletAddress: step.walletAddress, txHash: tx.hash });
  }
  plan = await post('/verify', request);
}

if (plan.phase === 'SIGN_CLAIMS') {
  const claimSignatures = [];
  for (const message of plan.messages) {
    const signature = await wallet.signMessage(ethers.utils.arrayify(message.messageHash));
    claimSignatures.push({ walletAddress: message.walletAddress, signature });
  }
  plan = await post('/verify', { ...request, claimSignatures });
}

const hashes: string[] = [];
for (const step of plan.steps) {
  const tx = await wallet.sendTransaction(step.transaction);
  await tx.wait();
  hashes.push(tx.hash);
}

const confirmed = await post('/verify', { ...request, txHash: hashes[plan.confirmStepIndex] });
```

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `walletAddress` is missing or not a valid address |
| `MISSING_COUNTRY` | `400` | `country` is missing, not a string, or shorter than 2 characters |
| `INVALID_COUNTRY` | `400` | `country` is not an ISO 3166-1 code |
| `INVALID_HASH` | `400` | `kycHash` is not 32-byte hex |
| `INVALID_INVESTOR_TYPE` | `400` | `investorType` names neither a preset nor one of your verification profiles, or is not a string. The message lists the accepted values. Also a disabled profile, on the build call, for a wallet whose customer is not already under it |
| `COUNTRY_BLOCKED` | `403` | `country` is blocked on the verification profile named after `investorType` |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | Trusset register: none of your instance's wallets holds `KYC_PROVIDER_ROLE` |
| `REGISTRY_AGENT_MISSING` | `403` | ERC-3643: none of your instance's wallets is an agent of the register |
| `CLAIM_SIGNER_MISSING` | `403` | ERC-3643: none of your instance's wallets holds a claim key on the trusted issuer |
| `CLAIM_SIGNER_NOT_TRUSTED` | `403` | ERC-3643: `signerAddress`, or the wallet a claim signature recovers to, holds no claim key on the trusted issuer |
| `INVALID_CLAIM_SIGNATURE` | `400` | ERC-3643: a claim signature is not 65-byte hex, or recovers to no signer |
| `REGISTRY_NO_CLAIM_TOPICS` | `409` | ERC-3643: the register requires no claim topic, so there is no claim to register |
| `REGISTRY_NO_TRUSTED_ISSUER` | `409` | ERC-3643: the register names no trusted issuer for its claim topic |
| `ONCHAINID_AUTHORITY_UNKNOWN` | `409` | ERC-3643: the wallet has no ONCHAINID, and no identity on the register reveals the implementation to deploy |
| `OWN_REGISTRY_NOT_CONFIGURED` | `409` | The instance is bound to its own register but no valid register address is set |
| `REGISTRY_PROBE_FAILED` | `503` | Your own register could not be read to tell its kind, or the trusted issuer could not be read to check a claim signer |
| `INVALID_TX` | `400` | `txHash` is not 32-byte hex |
| `TX_NOT_FOUND` | `404` | The transaction is not mined yet |
| `TX_REVERTED` | `400` | The transaction reverted |
| `TX_WRONG_TARGET` | `400` | The transaction does not write to the register, or it deployed a contract |
| `TX_WRONG_FUNCTION` | `400` | The transaction calls a function this endpoint does not confirm |
| `TX_TARGET_MISMATCH` | `400` | The transaction targets a different wallet, or an ONCHAINID that is not this wallet's |
| `UNAUTHORIZED_SIGNER` | `403` | Trusset ID Register: the transaction was not signed by one of your instance's verified wallets |
| `TX_INVESTOR_TYPE_MISMATCH` | `400` | Trusset register: the mined investor type differs from `investorType` in this request |
| `NOT_VERIFIED_ON_REGISTER` | `409` | ERC-3643: the register does not report the wallet as verified yet |
| `CHAIN_UNAVAILABLE` | `503` | ERC-3643: the transaction or the register could not be read |
| `VERIFY_FAILED` | `400`, `500` | Any other failure. `400` when a chain call or the transaction encoding failed |
