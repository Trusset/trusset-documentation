---
title: 'Verify Identity'
api: 'POST /customers/api/identity/verify'
description: 'Register a wallet on the identity register and record the customer as verified'
---

Puts a wallet on the identity register your instance writes to. Once you confirm the mined transaction, the customer record is created or updated as `verified`. Nothing is broadcast for you: every call returns what to sign.

<Note>
  `investorType` must name a preset or one of your [verification profiles](/endpoints/customers/list-verification-profiles). Any other value, `INSTITUTIONAL`, `NONE` or a number included, is refused with `400 INVALID_INVESTOR_TYPE` on both legs, and the message lists the values your instance accepts.
</Note>

What you sign depends on the register. Every calldata response names it in `registerKind`.

| `registerKind` | Register | The calldata leg returns |
|---|---|---|
| `INSTANCE` | Your [instance ID register](/endpoints/customers/introduction#the-instance-id-register), reading attestations on the identity hub. The register of every instance in Trusset mode | One transaction, `attest` on the identity hub |
| `TRUSSET` | A register of your own that answers the Trusset register interface | One transaction, `verifyIdentity` or `updateIdentity` |
| `TREX` | Your own ERC-3643 (T-REX) identity registry, with ONCHAINID identities | A plan in up to three phases, one call per phase |

An ERC-3643 plan also carries `trexVersion`: `4` for a T-REX 4 register with ONCHAINID 2 identities, `5` for a T-REX 5 register with ONCHAINID 3 identities. The two versions differ in their first two phases. See [Verify on an ERC-3643 register](#verify-on-an-erc-3643-register) and [Verify on an ERC-3643 T-REX 5 register](#verify-on-an-erc-3643-t-rex-5-register).

## Body Parameters

<ParamField body="walletAddress" type="string" required>
  The wallet to register. Checksummed or lowercase. A mixed-case address with a wrong checksum is refused.
</ParamField>

<ParamField body="country" type="string" required>
  ISO 3166-1 code as alpha-2 (`DE`), alpha-3 (`DEU`) or numeric (`276`). Stored on the customer record in alpha-3 form.

  On the instance ID register the country never goes on chain. It decides one predicate: `EEA_RESIDENT` is set when the country is in the EEA. `RESIDENCY_ON_FILE` is always set, because a country is always given. An ERC-3643 register receives the country as the numeric code. A T-REX 5 register records no country: it stays on the customer record only, and the plan's `warnings` carries `{ code: 'COUNTRY_NOT_ON_REGISTER' }`.

  Refused with `COUNTRY_BLOCKED` when it is on the blocked list of the [verification profile](/endpoints/customers/list-verification-profiles) named after `investorType`.
</ParamField>

<ParamField body="investorType" type="string" default="RETAIL">
  `RETAIL`, `PROFESSIONAL` or `ELIGIBLE_COUNTERPARTY` in any letter case, or the key of one of your custom [verification profiles](/endpoints/customers/list-verification-profiles), also in any letter case. A custom key registers with that profile's on-chain investor type. Omitted, `null` or an empty string reads as `RETAIL`. A disabled profile is refused with `INVALID_INVESTOR_TYPE` on the build call unless the wallet's customer record is already under it, so a customer of a disabled profile can still be verified again. The confirm call records what was signed. Anything else, a number included, is refused with `INVALID_INVESTOR_TYPE`.

  The instance ID register writes it into the attestation as the investor class `1`, `2` or `3`. A Trusset-compatible register of your own stores it as the investor type. An ERC-3643 register has no investor type, so there it is kept on the customer record only. The record keeps the profile key as the profile spells it, so `professional` is stored as `PROFESSIONAL`.
</ParamField>

<ParamField body="softExpiryDays" type="integer">
  Days until the identity is soft-expired. `0` or omitted sets none. An ERC-3643 register does not store it.
</ParamField>

<ParamField body="hardExpiryDays" type="integer">
  Days until the identity is hard-expired and stops counting as verified. `0` or omitted sets none. An ERC-3643 register does not store it.

  On the instance ID register the API checks both before it builds, and refuses with `400 INVALID_EXPIRY` when either lies in the past or the soft expiry is not earlier than the hard expiry. On a Trusset-compatible register of your own the API does not check them, and the register reverts such a transaction.
</ParamField>

<ParamField body="kycHash" type="string">
  The KYC hash to register, as 32-byte hex (`0x` and 64 hex characters). Stored lowercased. On the instance ID register it is the root of the attestation and required on the calldata leg: send the root of the customer's KYC proof bundle, built over salted commitments, or your own salted commitment. Without it, the call is refused with `400 KYC_HASH_REQUIRED`, and an all-zero hash with `400 INVALID_KYC_HASH`. On an ERC-3643 register it becomes the data of the KYC claim.
</ParamField>

<ParamField body="kycData" type="object">
  On the instance ID register this field is refused on both legs with `400 KYC_HASH_REQUIRED`: KYC data never goes to Trusset, so hash it yourself, with a secret salt, and send `kycHash`.

  On a register of your own, data to derive the hash from when `kycHash` is omitted: the keccak256 of its JSON serialisation, with no salt. With neither field, the hash is a random 32-byte value over no personal data, so it changes on every call. See the warning below before you send anything here.
</ParamField>

<ParamField body="claimSignatures" type="array">
  ERC-3643 only. The signatures from the `SIGN_CLAIMS` phase, as `[{ walletAddress, signature }]`. An entry may add `claimType`, such as `KYC`.

  On a T-REX 5 register each entry also carries `issuedAt`, exactly as its message gave it: `[{ walletAddress, signature, claimType, issuedAt }]`. A signature without it is not used, and the call answers `SIGN_CLAIMS` again.
</ParamField>

<ParamField body="claimSignature" type="string">
  ERC-3643 only. A single claim signature for `walletAddress`, instead of `claimSignatures`. On a T-REX 5 register send `claimSignatures`, since the signature needs its `issuedAt`.
</ParamField>

<ParamField body="identities" type="object">
  ERC-3643 only. An ONCHAINID you deployed with your own tooling, keyed by wallet: `{ "<wallet>": "<onchainid>" }`. It is used when the register holds no identity for the wallet and the contract answers as an ONCHAINID. Otherwise it is ignored. A T-REX 5 register ignores it and reads the identity its identity factory links to the wallet.
</ParamField>

<ParamField body="signerAddress" type="string">
  On the instance ID register, the wallet you will sign the attestation with. It decides what an update keeps: see [Verify on the instance ID register](#verify-on-the-instance-id-register). The calldata leg does not check that it is a trusted attester. The confirm leg does.

  On an ERC-3643 register, the wallet that will sign the claim. Refused with `CLAIM_SIGNER_NOT_TRUSTED` when it holds no claim key on the register's trusted issuer. Defaults to the first of your instance's wallets, primary first, that holds one.

  It also becomes the management key of any ONCHAINID the plan deploys. Name a wallet registered to your instance, because [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid) refuses any other management key.

  On a T-REX 5 register it names the wallet you will sign the current phase with, and is never a management key of the investor's ONCHAINID. When it lacks the role a step or a message of that phase needs, the call answers `403 SIGNER_ROLE_MISSING`, and the message names the role and the wallets that hold it. Omitted, each step names a wallet of your instance that holds the role.
</ParamField>

<ParamField body="txHash" type="string">
  The hash of the mined transaction. Send it with the same body to confirm. On an ERC-3643 register, send the hash of `steps[confirmStepIndex]`. Omit it to receive the calldata or the next phase.
</ParamField>

</Warning>

## Verify on the instance ID register

Call once without `txHash` and send `transaction` from a wallet your instance ID register trusts as an attester. Then send the same body again with `txHash` added.

The transaction calls `attest` on the identity hub. The hub writes the attestation under the address that sends it, so a wallet can only ever attest in its own name. The attestation carries the `kycHash` as its root, the investor class, both expiries and the predicate bits: `KYC_DONE` and `RESIDENCY_ON_FILE`, plus `EEA_RESIDENT` when `country` is in the EEA. Names, the country itself and other personal data are not written. See [Predicates](/endpoints/customers/introduction#predicates).

The endpoint answers `updateIdentity` when the register already reports an identity for the wallet that is not revoked, expired ones included, and `verifyIdentity` otherwise. Both build the same `attest`. An update keeps the other predicate bits, such as `AML_CLEAR`, of the attestation it replaces: the one `signerAddress` already holds about the wallet, or with `signerAddress` omitted, the one the register resolves. `EEA_RESIDENT` is always set again from `country`. When `signerAddress` holds no attestation about the wallet and is not the attester the register resolves, it writes a new attestation of its own and nothing is carried over. If the register cannot be read, the endpoint answers `verifyIdentity`.

Before handing out calldata, the API checks the register:

- An instance in Trusset mode without its own register yet is refused with `409 INSTANCE_REGISTER_REQUIRED`. Create the register in the issuer app under Settings, Identity Register. See [The instance ID register](/endpoints/customers/introduction#the-instance-id-register).
- It refuses with `403 ATTESTER_MISSING` when it can read every registered wallet of your instance and the register trusts none of them as an attester. With no wallet registered, or when the read fails, it lets the call through. The verdict is cached for 60 seconds, so a refusal can outlast a new trust by up to a minute. A register admin trusts a wallet on the wallet page of the issuer app. Trusset never does. See [Attesters and trust](/endpoints/customers/introduction#attesters-and-trust).
- It refuses with `501 IDENTITY_HUB_NOT_CONFIGURED` when the identity hub is not deployed on your instance's network.

The confirm leg decodes the `Attested` event the hub emitted for the wallet. It refuses with `403 UNTRUSTED_ATTESTER` when the signing wallet is not a trusted attester of your register, and with `409 NOT_VERIFIED_ON_REGISTER` when the register still does not resolve the wallet as verified afterwards, for example because it does not accept `KYC_DONE` from that attester.

## Verify on a Trusset-compatible register of your own

Call once without `txHash` and send `transaction` from a wallet that holds `KYC_PROVIDER_ROLE` on your register. Then send the same body again with `txHash` added.

The endpoint picks `updateIdentity` when the wallet already holds an identity that is not revoked, expired ones included. It picks `verifyIdentity` when the wallet has none or was revoked. If the register cannot be read, it falls back to `verifyIdentity`, which reverts for a wallet that already holds an unrevoked identity.

Before handing out calldata, the API checks that one of your instance's wallets holds `KYC_PROVIDER_ROLE`. It refuses with `KYC_PROVIDER_ROLE_MISSING` only when it can read every wallet and none holds the role. With no wallet registered, or when the read fails, it lets the call through. The verdict is cached for 60 seconds. Your register's owner grants the role.

## Verify on an ERC-3643 register

This section covers a T-REX 4 register (`trexVersion: 4`). A T-REX 5 register follows [the next section](#verify-on-an-erc-3643-t-rex-5-register).

Each call answers the next phase. Call again with what the previous phase produced until `phase` is `REGISTER`, carrying the same `kycHash` throughout.

<Steps>
  <Step title="Deploy an ONCHAINID (DEPLOY_IDENTITY)">
    Returned when the wallet has no ONCHAINID. Send each step's `transaction` as a contract creation, then confirm each deployment with [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid) so it is recorded. Confirming a deployment here returns `TX_WRONG_TARGET`, whatever `confirmWith` says.

    You can deploy ahead of time with [Deploy ONCHAINID](/endpoints/customers/deploy-onchainid), or pass an ONCHAINID you deployed yourself in `identities`.
  </Step>
  <Step title="Sign the claim (SIGN_CLAIMS)">
    Sign each `messageHash` as an EIP-191 personal message over its 32 bytes. Use a wallet that holds a CLAIM key on `claimIssuer`, such as one in `claimSigners`. Call again with `claimSignatures: [{ walletAddress, signature }]`.
  </Step>
  <Step title="Register (REGISTER)">
    Send `steps` in order. The `claim` step adds the claim to the wallet's ONCHAINID. The `verify` step registers a new wallet, and a `country` step corrects the country of a wallet already on the register. Confirm with the hash of `steps[confirmStepIndex]`.
  </Step>
</Steps>

| Transaction or signature | Who must hold what |
|---|---|
| ONCHAINID deployment | Any wallet can send it. The management key is fixed in the deployment data, and is `signerAddress`. |
| Claim signature | A CLAIM key (purpose 3) on `claimIssuer`. |
| `addClaim` on the ONCHAINID | A management or claim key of that ONCHAINID. For one the plan deployed, that is `signerAddress`. |
| `registerIdentity`, `updateCountry` | An agent of the register. |

The API refuses up front with `REGISTRY_AGENT_MISSING` when none of your instance's wallets is an agent, and with `CLAIM_SIGNER_MISSING` when none holds a claim key. It does not check that the agent and `signerAddress` are the same wallet.

An ERC-3643 register stores no investor type and no expiry. `investorType` reaches the customer record only, and the two expiry fields are not stored anywhere.

The ERC-3643 example sends everything from one `wallet` that is both an agent of the register and a claim signer. Passing its address as `signerAddress` makes it the management key of any ONCHAINID it deploys, so it can also send the `claim` step.

## Verify on an ERC-3643 T-REX 5 register

A T-REX 5 register (`trexVersion: 5`) answers with the same plan, with `identityFactory` added, in up to three phases. Repeat the same call after each phase, with the same `kycHash`, until `phase` is `REGISTER`.

<Steps>
  <Step title="Create the ONCHAINID (CREATE_IDENTITY)">
    Returned when the wallet has no ONCHAINID. One step per wallet without an identity, `stepType: createIdentity`, calls `createIdentityFor` on `identityFactory`. `identityType` is `CORPORATE` for a customer of type company and `INDIVIDUAL` otherwise, and the salt is `trusset-<chainId>-<wallet>`, which carries no personal data. The investor wallet becomes the only MANAGEMENT key of its ONCHAINID, and your issuer wallets hold no key on it.

    The factory links the identity to the wallet, so nothing needs confirming: once the transactions are mined, repeat the call. [Confirm ONCHAINID](/endpoints/customers/confirm-onchainid) still works and records the identity on the customer record. This phase replaces `DEPLOY_IDENTITY`, which stays T-REX 4 only.
  </Step>
  <Step title="Sign the claim (SIGN_CLAIMS)">
    Each message has `scheme: eip712`, `typedData`, `issuedAt`, `messageHash` and `claimType`. `typedData` is the EIP-712 claim `Claim(topic, subject, ClaimData{issuedAt, validUntil, Metadata{scheme, uri}, payload})` in the signing domain of the trusted issuer's own identity. `issuedAt` is the latest block time in unix seconds, and `messageHash` is the EIP-712 digest.

    Sign `typedData` (`eth_signTypedData_v4`) with a wallet that holds a CLAIM_SIGNER key on `claimIssuer`, then call again with `claimSignatures: [{ walletAddress, signature, claimType, issuedAt }]`. Send `issuedAt` back exactly as the message gave it, because the signature covers it.
  </Step>
  <Step title="Register (REGISTER)">
    Send `steps` in order. A `claim` step calls `addClaimTo` on the trusted issuer, which writes the signed claim onto the wallet's ONCHAINID. When a wallet is verified again with a different KYC claim from the same issuer, a `rotateClaim` step follows, calling `revokeClaimByDigest` with the previous claim's digest so its signature can never be written back. A `verify` step calls `registerIdentity(wallet, identity, 0)` when the wallet is not on the register yet. Confirm with the hash of `steps[confirmStepIndex]`.
  </Step>
</Steps>

| Transaction or signature | Who must hold what |
|---|---|
| `createIdentityFor` on the identity factory | The IDENTITY_ISSUER role of the factory's authority |
| Claim signature | A CLAIM_SIGNER key (purpose 3) on `claimIssuer` |
| `addClaimTo`, `revokeClaimByDigest` on the trusted issuer | A MANAGEMENT key (purpose 1) on the trusted issuer identity |
| `registerIdentity` | The AGENT role of the register, which the suite's AccessManager grants |

Every step names the wallet that must sign it in `signer`, so several wallets of your instance can share the work. When you send `signerAddress` and it lacks the role a step or message of the phase needs, the call answers `403 SIGNER_ROLE_MISSING` before anything is built, and the message names the role and the wallets that hold it.

The API refuses up front with `REGISTRY_AGENT_MISSING` when no wallet of your instance holds the AGENT role, `CLAIM_SIGNER_MISSING` when none holds a CLAIM_SIGNER key on a trusted issuer, and `CLAIM_MANAGER_MISSING` when none holds a MANAGEMENT key on it. For a wallet without an ONCHAINID it refuses with `IDENTITY_ISSUER_MISSING` when none holds the IDENTITY_ISSUER role, `IDENTITY_TYPE_NOT_ENABLED` when the factory has no policy for the identity type, and `IDENTITY_BINDING_REVOKED` when the wallet's binding on the factory is revoked: register another wallet for the customer then.

A T-REX 5 register records no country, no investor type and no expiry. The country stays on the customer record, and `warnings` carries `{ code: 'COUNTRY_NOT_ON_REGISTER' }`. The wallet counts as verified once its ONCHAINID holds valid claims for the register's required topics. The plan registers it on the register as well, but the contract does not require that.

The T-REX 5 example sends everything from one `wallet` that holds every role above. With the roles spread over several wallets, send each step from the wallet its `signer` names.

## Confirm

The confirm leg reads the mined transaction and refuses it before writing anything when:

- it is not mined, reverted, or is not a hub, register or ONCHAINID write this endpoint confirms (`TX_WRONG_TARGET`, `TX_WRONG_FUNCTION`)
- it targets a different wallet, or an ONCHAINID that is not this wallet's (`TX_TARGET_MISMATCH`)
- on the instance ID register, it was signed by a wallet the register does not trust as an attester (`UNTRUSTED_ATTESTER`), or the mined attestation lacks `KYC_DONE` (`TX_PREDICATES_MISMATCH`)
- on a Trusset-compatible register of your own, the signer is logged, not checked
- on the instance ID register or a Trusset-compatible register, the mined investor type differs from this request's (`TX_INVESTOR_TYPE_MISMATCH`)
- on the instance ID register or an ERC-3643 register, the register does not report the wallet as verified afterwards (`NOT_VERIFIED_ON_REGISTER`)

On a T-REX 5 register the confirmed transaction may call `registerIdentity` on the register, or `addClaimTo` or `revokeClaimByDigest` on one of its trusted issuers, sent directly or through a smart-account wallet. One that calls none of them is refused with `TX_WRONG_FUNCTION`, and a claim written onto another wallet's ONCHAINID with `TX_TARGET_MISMATCH`.

Then it writes the customer record with `country`, the profile key `investorType` resolved to, `status: "verified"`, `verifiedAt` and the `kycHash` read from the chain, and records the write in your instance's verification history as a `VERIFY_DIRECT` entry with the operation (`verify` or `update`), the mined investor type, the transaction and its signer. A reclassification through this endpoint therefore shows in the history like one made in the issuer app. When the profile `investorType` names has an eligibility register, the wallet's admission to it is queued for your wallet to sign. See [Eligibility registers](/endpoints/customers/introduction#eligibility-registers). On the instance ID register a profile is checked by its [profile gate](/endpoints/customers/introduction#profile-gates) instead, which reads the attestation itself, so nothing is queued.

<Note>
  Confirming also settles any [pending verification](/endpoints/customers/list-pending-verifications) for the same wallet. Its row is marked confirmed with this transaction, so the queue does not ask for the signature again.
</Note>

  const res = await fetch(`${base}${path}`, { method: 'POST', headers, body: JSON.stringify(body) });
  const json = await res.json();
  if (!json.success) throw new Error(`${json.error.code}: ${json.error.message}`);
  return json.data;
};

const request: Record<string, unknown> = {
  walletAddress: '0xaBc123DEf456789012345678901234567890aBCD',
  country: 'DE',
  investorType: 'PROFESSIONAL',
  signerAddress: await wallet.getAddress()
};

let plan = await post('/verify', request);
request.kycHash = plan.kycHash;

if (plan.phase === 'DEPLOY_IDENTITY') {
  for (const step of plan.steps) {
    const tx = await wallet.sendTransaction({ data: step.transaction.data });
    await tx.wait();
    await post('/onchainid/confirm', { walletAddress: step.walletAddress, txHash: tx.hash });
  }
  plan = await post('/verify', request);
}

if (plan.phase === 'SIGN_CLAIMS') {
  const claimSignatures = [];

    const signature = await wallet.signMessage(ethers.utils.arrayify(message.messageHash));
    claimSignatures.push({ walletAddress: message.walletAddress, signature });

}

  await tx.wait();

## Error Codes

| Code | HTTP | Cause |
|---|---|---|
| `INVALID_ADDRESS` | `400` | `walletAddress` is missing or not a valid address |
| `MISSING_COUNTRY` | `400` | `country` is missing, not a string, or shorter than 2 characters |
| `INVALID_COUNTRY` | `400` | `country` is not an ISO 3166-1 code |
| `INVALID_HASH` | `400` | `kycHash` is not 32-byte hex |
| `INVALID_INVESTOR_TYPE` | `400` | `investorType` names neither a preset nor one of your verification profiles, or is not a string. The message lists the accepted values. Also a disabled profile, on the build call, for a wallet whose customer is not already under it |
| `COUNTRY_BLOCKED` | `403` | `country` is blocked on the verification profile named after `investorType` |
| `INVALID_EXPIRY` | `400` | Instance ID register: an expiry lies in the past, or the soft expiry is not earlier than the hard expiry |
| `KYC_HASH_REQUIRED` | `400` | Instance ID register: the request carries `kycData`, or the calldata leg carries no `kycHash`. Send your bundle root or your own salted commitment |
| `INVALID_KYC_HASH` | `400` | Instance ID register: `kycHash` is all zeros |
| `INSTANCE_REGISTER_REQUIRED` | `409` | Your instance is in Trusset mode and has not created its instance ID register yet |
| `ATTESTER_MISSING` | `403` | Instance ID register: none of your instance's registered wallets is a trusted attester of the register |
| `IDENTITY_HUB_NOT_CONFIGURED` | `501` | The identity hub is not deployed on your instance's network |
| `KYC_PROVIDER_ROLE_MISSING` | `403` | Trusset-compatible register of your own: none of your instance's wallets holds `KYC_PROVIDER_ROLE` |
| `REGISTRY_AGENT_MISSING` | `403` | ERC-3643: none of your instance's wallets is an agent of the register |
| `CLAIM_SIGNER_MISSING` | `403` | ERC-3643: none of your instance's wallets holds a claim key on the trusted issuer |
| `CLAIM_SIGNER_NOT_TRUSTED` | `403` | ERC-3643: `signerAddress`, or the wallet a claim signature recovers to, holds no claim key on the trusted issuer |
| `INVALID_CLAIM_SIGNATURE` | `400` | ERC-3643: a claim signature is not 65-byte hex, or recovers to no signer. On T-REX 5, also one that is not a valid EIP-712 signature over the claim |
| `CLAIM_MANAGER_MISSING` | `403` | T-REX 5: none of your instance's wallets holds a MANAGEMENT key on the trusted issuer identity, which writes the claim |
| `IDENTITY_ISSUER_MISSING` | `403` | T-REX 5: the wallet has no ONCHAINID, and none of your instance's wallets holds the IDENTITY_ISSUER role of the identity factory's authority |
| `SIGNER_ROLE_MISSING` | `403` | T-REX 5: `signerAddress` lacks the role a step or message of this phase needs. The message names the role and the wallets that hold it |
| `REGISTRY_NO_CLAIM_TOPICS` | `409` | ERC-3643: the register requires no claim topic, so there is no claim to register |
| `REGISTRY_NO_TRUSTED_ISSUER` | `409` | ERC-3643: the register names no trusted issuer for its claim topic |
| `ONCHAINID_AUTHORITY_UNKNOWN` | `409` | ERC-3643: the wallet has no ONCHAINID, and no identity on the register reveals the implementation to deploy |
| `IDENTITY_TYPE_NOT_ENABLED` | `409` | T-REX 5: the identity factory has no policy for the wallet's identity type, `INDIVIDUAL` or `CORPORATE` |
| `IDENTITY_BINDING_REVOKED` | `409` | T-REX 5: the wallet's binding on the identity factory is revoked, so no identity can be created or linked for it. Use another wallet |
| `CLAIM_NOT_VALID` | `409` | T-REX 5: the trusted issuer does not accept the signed claim (`isClaimValid` answers `false`), for example because its digest is revoked. Sign it again |
| `CLAIM_ISSUER_UNREADABLE` | `409` | T-REX 5: the trusted issuer does not answer as an ONCHAINID 3 identity, so no claim can be signed for it |

| `OWN_REGISTRY_NOT_CONFIGURED` | `409` | The instance is bound to its own register but no valid register address is set |
| `REGISTRY_PROBE_FAILED` | `503` | Your own register could not be read to tell its kind, or the trusted issuer could not be read to check a claim signer |
| `INVALID_TX` | `400` | `txHash` is not 32-byte hex |
| `TX_NOT_FOUND` | `404` | The transaction is not mined yet |
| `TX_REVERTED` | `400` | The transaction reverted |
| `TX_WRONG_TARGET` | `400` | The transaction does not write to the identity hub or the register, or it deployed a contract |
| `TX_WRONG_FUNCTION` | `400` | The transaction calls a function this endpoint does not confirm |
| `TX_TARGET_MISMATCH` | `400` | The transaction targets a different wallet, or an ONCHAINID that is not this wallet's. On the instance ID register, also a transaction that attests nothing about this wallet |
| `TX_PREDICATES_MISMATCH` | `400` | Instance ID register: the mined attestation does not carry `KYC_DONE` |
| `UNTRUSTED_ATTESTER` | `403` | Instance ID register: the transaction was signed by a wallet the register does not trust as an attester |

| `VERIFY_FAILED` | `400`, `500` | Any other failure. `400` when a chain call or the transaction encoding failed |
