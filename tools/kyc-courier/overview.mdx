The KYC courier moves an investor's KYC file from your verifier to your bank as ciphertext that only the bank can open. Trusset relays the sealed envelope and never holds a key that opens it.

`trusset-kyc` is the command line tool for [sealed KYC records](/protocol/infrastructure/sealed-kyc-records). It runs on your own machine and has two sides:

- **The verifier** seals the KYC file of an investor so that only the bank can read it, signs it, and posts it to the bank's inbox on Trusset.
- **The bank** downloads the sealed envelope, verifies and decrypts it locally, files the record, and proves to Trusset that it opened it. Trusset then deletes the ciphertext.

The bank also uses the tool to open [disclosures from holders](#disclosures-from-holders), which a holder encrypts to the same record key.

Banks follow the [bank walkthrough](/tools/kyc-courier/bank-walkthrough). Fintechs and other verifiers follow the [verifier walkthrough](/tools/kyc-courier/verifier-walkthrough). [Trusset for banks](/protocol/banks) and [Trusset for fintechs](/protocol/fintechs) show where KYC fits in each path.

## Who uses it

| Role | What they do with the tool |
|---|---|
| Bank | Creates the record key, pins each verifier's signing key, opens the records and disclosures that arrive, and can verify a filed record again offline at any time |
| Verifier | Creates a signing key, stores the bank's invite, seals and sends records, follows their status, and revokes a record when needed |
| Auditor | Runs `trusset-kyc verify` on a filed record directory with the verifier's fingerprint, which the bank gives it (`--fingerprint`). Needs no network and no private key |

Approving a record and listing its wallet on a whitelist are not part of the tool. The bank does that in the Issuer Portal or through the [API](/endpoints/customers/approve-kyc-record), and its own wallet signs.

## What Trusset sees

- The envelope header: envelope ID, source ID, wallet address, profile key, recipient key ID, two digests and three timestamps.
- The size of the ciphertext and the time of delivery.
- Whether and when the bank opened, approved or rejected a record, and whether the verifier revoked it.

## What Trusset cannot do

- **Read a record.** Records are encrypted to the bank's X25519 key with HPKE (RFC 9180). The private key never leaves the bank's keystore.
- **Forge or alter a record.** Each record is signed twice with the verifier's Ed25519 key: once inside the ciphertext, once over the header and the ciphertext. The bank's tool checks both against a key the bank pinned itself.
- **Move a record to another wallet, source or profile.** Those fields are in the signed header, the header is bound into the encryption, and the same fields are repeated inside the signed record.
- **Claim that a record was opened.** Opening is proven with a random value that exists only inside the ciphertext.

## The two pinning rules

These two rules are what make the list above hold even if Trusset were compromised:

1. **The verifier pins the bank's key from the invite.** The tool never encrypts to a key that Trusset reports. If Trusset reports a different key than the invite holds, `send` refuses.
2. **The bank pins each verifier's signing key in its own keystore.** The signing key Trusset reports is shown as a hint and is never used to verify a record.

<Warning>
  The invite itself is issued through Trusset. Compare fingerprints over a channel that does not run through Trusset, for example by phone, before the first record is sent:

  - The bank reads the verifier the fingerprint of its recipient key from `trusset-kyc key show` on its own machine, never from the Trusset app, which is served by Trusset like the invite. The verifier passes it to `invite add --fingerprint`, which stores the invite only when the key in it has exactly this fingerprint. `seal` and `send` refuse an invite that was never checked this way.
  - The verifier reads the bank the fingerprint of its signing key before the bank runs `source add`, and the bank compares it with what `source add` prints.

  A fingerprint is the first 32 hex characters of SHA-256 over the raw public key, in 8 groups of 4, for example `b961 9d9b e69e d903 c31c 6f1a f3c6 a7d2`. A key pinned without this comparison is only the key Trusset relayed.
</Warning>

A compromised relay could still drop or delay envelopes, replay an old valid envelope, report wrong status values and report wrong key hints. It could not make the bank accept a record the pinned verifier did not sign, and it could not read anything.

When a verifier changes its signing key, the bank's tool holds the records signed with the new key. It neither opens nor rejects them, and it prints both fingerprints. The bank first opens every record still waiting under the old key, then compares the new fingerprint with the verifier and pins the new key with `source add --replace --former-key retire`, or `--former-key revoke` when the old key was exposed. A former key never opens a new record, whatever date the envelope claims. A retired key keeps the records filed under it verifying; a revoked key does not, and it can never be pinned again, not even after `source remove`.

`verify` checks a filed record against a key the person running it trusts: the pin in the local keystore, one of its retired keys, or the key or fingerprint given on the command line. Without one of these the record does not verify, because the key that comes with the folder proves nothing on its own.

## Disclosures from holders

A holder can answer a [disclosure request](/endpoints/customers/create-disclosure-request) of the bank with facts from their KYC proof bundle. Their browser encrypts the disclosed proofs to the bank's record key, and their wallet signs a consent that names that exact envelope. No source key is pinned for a disclosure. Its authenticity rests on the attester's signed header inside each disclosed leaf, checked against the operator key on the identity hub, and on the holder's consent over the envelope.

The bank lists, opens, verifies and rejects disclosures with four commands, described in the [CLI reference](/tools/kyc-courier/cli-reference#disclosure-commands). Opening one works in this order and stops at the first step that fails:

1. It downloads the envelope and checks its header against the request.
2. It recomputes the envelope digest, rebuilds the consent from the request, and checks that the holder's wallet signed it.
3. It decrypts with the record key and checks the plaintext against the digests in the header.
4. With `--verifier` and `--rpc`, it verifies every disclosed proof with `verify_disclosure` of [KYC-STARKs](/tools/kyc-starks/verification#a-single-disclosed-leaf) 3.1, against the operator key the identity hub publishes for the attester, and checks the root against the wallet's attestation on the hub. Without them it prints the commands to run later, or `disclosures verify` runs them.
5. It checks that the disclosures answer the scope of the request.
6. It stores the result, and only then proves the opening to Trusset, which deletes the ciphertext.

A disclosure that fails decryption, the digests, a proof or the scope is rejected with the matching [reason](/endpoints/customers/reject-disclosure#reasons), and Trusset deletes the ciphertext as well. A failed header or consent check, or a verifier or RPC that cannot run, rejects nothing, and the envelope stays at Trusset for 30 days. What the bank holds after opening is the value each proof shows, such as a date of birth or a country.

## What the tool does not decide

The tool moves a file and proves where it came from. It does not judge whether the verification behind it is sufficient. Whether a bank may rely on a verifier's KYC, and how personal data may pass between the two, is governed by the agreements between the bank and the verifier.

The tool does not check what a verifier seals. A record with wrong content is still validly signed, so the review of the file stays with the bank.

## Getting the tool

The tool is not published to a package registry. Trusset provides it during onboarding.

It needs Node.js 18 or newer. It has two runtime dependencies, pinned to exact versions: `@noble/hashes` 1.7.0 and `@noble/curves` 1.8.0, used only to check a holder's wallet signature on a disclosure. All other cryptography uses the `crypto` module built into Node.js. From the folder you received:

```bash
npm install -g .
trusset-kyc --version
```

Or run `npm ci` once, then `node bin/trusset-kyc.js --help` without installing it.

File modes are not enforced on Windows. Use a directory there that only your account can read.
